# [V1] 슬롯 구성별 자원 실측 — 가중치 변경 없이 (2026-08-18)

> 목적: **모델(RF-DETR 가중치)을 바꾸지 않고 설정만으로** 엣지박스 최저 사양을 얼마나
> 내릴 수 있는지. 여기서는 "무엇을 켜느냐(슬롯 구성)"만 바꿔 잰다.
>
> 방법론은 [E1](e1_bottleneck_report.md) 재사용: 워커 N 스레드 + 공유 `RLock` + 같은
> `guard.detect`, 카메라당 2fps. 구성마다 **새 프로세스**로 돌렸다(모델이 지연 로드라
> 한 프로세스에서 이어 재면 VRAM 이 섞인다).
>
> 원자료·스크립트: `benchmarks/e1_bottleneck/v1_*`

## 0. 결론 3줄

1. **슬롯을 잘라도 CPU 는 거의 안 준다** — 4슬롯→1슬롯으로 기능을 1/4 로 줄여도 CPU 는
   2.16→1.83코어(**−15%**)뿐이다. 비용의 대부분(**1.07코어**)이 슬롯 수와 무관한 고정비다.
2. **검출 지연은 4배 차이난다**(73.2→18.8ms). GPU 에서 슬롯은 순차 추론이라 시간엔 비례하지만
   그 시간이 CPU 를 거의 안 먹는다.
3. ★**VRAM 은 크게 준다** — 4슬롯 1,474MiB → 1슬롯 477MiB. 그리고 **기존 "3.2GB" 표기는
   과대평가였다**(§4 정정).

## 1. 슬롯 구성 4종 — 라벨 정정 포함

| 라벨 | 구성 | 슬롯 | 비고 |
|---|---|---|---|
| ① | person + ppe + fire_smoke + **forklift** | 4 | **코드상 최대**(현행 아님) |
| ③ | person + ppe + fire_smoke | 3 | ★**현행 런타임 기본값** |
| ② | person + ppe | 2 | 화재/연기 포기 |
| ④ | person 단독 | 1 | 침입 감지만 |

★**현행은 4슬롯이 아니라 3슬롯이다.** [`worker.py:87-94`](../vigent-core/worker.py#L87-L94)
`_default_detectors()` 가 `["person","ppe","fire_smoke"]` 를 반환하고, **forklift 는
F-7(과소학습 오탐, conf~0.002)로 기본 제외**돼 있다. `config/tuning.yaml` 에
`detect.include_forklift` 키가 없어 기본값 0 이다.

## 2. CPU·지연 실측 (카메라당 2fps)

| 구성 | 슬롯 | 검출 p50 (1대) | p95 (1대) | 검출 p50 (4대) | CPU (1대) | CPU (4대) | **카메라당 검출 CPU** | **총 추정 코어** |
|---|---|---|---|---|---|---|---|---|
| ① 최대 | 4 | 73.2ms | 112.6ms | 149.4ms | 168.2% | 622.5% | **151.4% (1.51코어)** | **2.16** |
| ③ **현행** | 3 | 56.6ms | 102.5ms | 93.0ms | 157.6% | 567.8% | **136.7% (1.37코어)** | **2.02** |
| ② | 2 | 41.5ms | 58.9ms | 70.5ms | 142.9% | 533.7% | **130.3% (1.30코어)** | **1.95** |
| ④ | 1 | 18.8ms | 44.1ms | 28.8ms | 125.3% | 479.5% | **118.1% (1.18코어)** | **1.83** |

- **카메라당 검출 CPU** = (4대 CPU − 1대 CPU) ÷ 3 — E1 §7 과 같은 증분법.
- **총 추정 코어** = 검출 CPU + **0.65코어**(E1 §7 실측: 검출 밖 파이프라인 — JPEG 인코딩·
  추적·존 판정·익명화·WS 송신 + pose. 슬롯 구성과 무관해 상수로 더한다).

**교차검증**: 현행(3슬롯) 검출 CPU **1.37코어**는 E1 이 같은 구성에서 잰 **1.43코어**와
4% 이내로 일치한다.

### 2-1. ★비용 구조 — 고정비가 지배한다

슬롯 수에 대한 최소자승 적합:

```
카메라당 검출 CPU = 1.07코어(고정) + 0.106코어 × 슬롯수
```

**슬롯 하나를 더 켜는 한계비용은 0.11코어에 불과**하고, 슬롯 수와 무관한 고정비가
**1.07코어**다. 그래서 기능을 팔아도 CPU 가 별로 안 준다.

> **함의**: GPU 박스에서는 **슬롯을 줄여 대수를 늘리는 전략이 거의 통하지 않는다.**
> 현행 3슬롯(2.02코어)에서 person 단독(1.83코어)까지 내려가도 한계 대수는
> 8.0대 → 8.8대로 **1대도 못 늘린다**(E1 §7 산정식, 24스레드 기준).

## 3. VRAM 실측

| 구성 | 슬롯 | torch 할당 | torch 예약 | **프로세스 실점유**(CUDA 컨텍스트 포함) |
|---|---|---|---|---|
| ① 최대 | 4 | 967.6 MiB | 1,258.0 MiB | **1,474 MiB** |
| ③ **현행** | 3 | 734.5 MiB | 1,024.0 MiB | **1,397 MiB** |
| ② | 2 | 501.3 MiB | 790.0 MiB | **1,019 MiB** |
| ④ | 1 | 267.9 MiB | 556.0 MiB | **477 MiB** |

torch 할당은 **완벽히 선형**이다: 267.9 → 501.3 → 734.5 → 967.6.

```
슬롯 1개 = 233.2 MiB   (절편 34.7 MiB)
```

## 4. 🔴 정정 — "상주 VRAM 3.2GB" 는 과대평가였다 (규칙7)

E1 리포트와 `docs/edgebox_purchase_guide.md` 에 **"상주 VRAM 3.2GB"** 로 적고 이를 근거로
**"VRAM 6GB 최소"** 를 제시했다. **이 3.2GB 는 VIGENT 단독이 아니라 GPU 총 사용량이었다.**

`nvidia-smi --query-compute-apps` 로 프로세스를 열거하면 GPU 를 함께 쓰는 것들이 나온다:

```
explorer.exe · SearchHost.exe · StartMenuExperienceHost.exe · TextInputHost.exe
Code.exe(VS Code) · msedgewebview2.exe · NVIDIA Overlay.exe · AMDRSSrcExt.exe · LockApp.exe
```

(Windows WDDM 은 per-PID 메모리를 보고하지 않아 전부 `N/A` 다 — 그래서 총량만 보고
"전부 VIGENT" 로 오독했다.)

**통제된 측정으로 다시 잰 VIGENT 단독 VRAM 은 현행 3슬롯 기준 약 1.4GB** 다.
E1 에서 카메라를 1→7대로 늘렸을 때 GPU 메모리가 3,205→3,239 MiB(**+34 MiB**, 카메라당 약
5 MiB)였던 것도 이와 부합한다 — 카메라 수는 VRAM 을 거의 안 늘린다.

> ### 구매 판단 영향
> **VRAM 하한이 6GB → 4GB 로 내려간다.** GTX 1650(4GB)급이 사양 안에 들어온다.
> 정식 반영은 V4 에서 한다.

## 5. pose(RTMPose) CPU — GPU-less 에서도 같은 CPU 를 쓴다

★**RTMPose 는 이미 CPU(onnxruntime)로 돈다**([`pose/rtmpose_adapter.py:22`](../vigent-core/pose/rtmpose_adapter.py#L22),
`device="cpu"`·`backend="onnxruntime"`). **GPU 를 빼도 이 비용은 그대로다.**
그리고 카메라마다 실제로 돈다([`worker.py:894`](../vigent-core/worker.py#L894) pose 스레드 기동,
`vision.yaml judgment.ergonomics.joints` 설정돼 있어 활성).

**사람 수별(초당 2회 호출 — 워커 캐던스)**

| 사람 수 | 지연 p50 | p95 | 프로세스 CPU |
|---|---|---|---|
| 1명 | 7.5ms | 11.0ms | 86.5% |
| 2명 | 15.6ms | 27.6ms | 107.5% |
| 3명 | 23.0ms | 33.1ms | 125.8% |

지연은 사람당 약 **7.7ms** 로 선형이다.

### 5-1. ★그런데 CPU 수치는 '스핀 대기'가 지배한다

1명·초당 2회면 실제 추론은 **초당 15ms(1.5%)** 인데 CPU 는 **86.5%** 다. 앞뒤가 안 맞아
호출 빈도를 바꿔 분해했다:

| 호출 빈도 | 지연 p50 | 프로세스 CPU | **호출당 CPU** |
|---|---|---|---|
| 0.2 Hz | 7.4ms | 7.1% | 35.5 %·s |
| 2.0 Hz | 7.5ms | 90.4% | 45.2 %·s |
| 10.0 Hz | 7.5ms | 427.0% | 42.7 %·s |

**호출당 CPU 가 ~43 %·s 로 거의 일정**하고 지연은 변하지 않는다 → 추론 자체가 아니라
**호출마다 onnxruntime 스레드풀이 스핀(busy-wait)** 하며 CPU 를 태우는 구조다.

⚠ **이 수치를 그대로 "pose = 0.9코어" 로 쓰면 안 된다.** 측정이 **다른 부하가 없는 유휴
프로세스**에서 이뤄져 스핀 스레드가 자유롭게 돌았다. 실제 서비스는 이미 바쁘므로 스핀
스레드가 선점당해 훨씬 적게 먹는다 — 실제로 E1 실측 총합(카메라당 2.05코어)에서 검출
1.37코어를 빼면 pose 를 포함한 나머지가 **0.68코어**이므로, 서비스에서의 pose 는 그보다 작다.

**정직한 결론**: pose 의 **실연산은 작다**(7.5ms/호출). 다만 **ORT 기본 스핀 설정 때문에
CPU 를 크게 태운다.** → §5-2 에서 실험으로 확정했다.

### 5-2. ★스핀 낭비 실재 확정 — 세션 옵션만 바꿔 CPU 89% 감소

`rtmlib/tools/base.py:80` 이 `ort.InferenceSession(..., providers=[...])` 만 넘기고
**`SessionOptions` 를 주지 않는다**(= ORT 기본값: intra_op 스레드 = 코어 수, **스핀 켜짐**).
같은 모델 파일로 **세션만 다시 만들어** 옵션을 바꾸고 동일 부하(1명·초당 2회)를 재측정했다.
★서비스 코드는 건드리지 않았다 — 실험 프로세스 안에서만 교체했다.

| 조건 | 지연 p50 | **프로세스 CPU** | 호출당 CPU |
|---|---|---|---|
| **기본값**(rtmlib 그대로) | 7.3ms | **82.5% (0.82코어)** | 41.2 %·s |
| 스핀OFF · 4스레드 | 12.3ms | **9.4% (0.09코어)** | 4.7 %·s |
| 스핀OFF · 2스레드 | 17.1ms | 8.6% (0.09코어) | 4.3 %·s |
| 스핀OFF · 1스레드 | 15.7ms | **4.6% (0.05코어)** | 2.3 %·s |

> ## ✅ 판정: **스핀 낭비 실재**
> CPU 가 **0.82 → 0.09코어(−89%)** 로 떨어지는데 지연은 **7.3 → 12.3ms** 만 늘었다.
> 즉 기본 설정에서 태우던 CPU 의 **대부분이 연산이 아니라 busy-wait** 였다.
>
> **카메라당 회복량: 최대 0.73~0.78 코어**(격리 프로세스 기준).

### 5-3. ★서비스 내 실제 회복량은 이보다 작다 (규칙7)

위 수치는 **다른 부하가 없는 유휴 프로세스**에서 잰 것이라 스핀 스레드가 자유롭게 돌았다.
실제 서비스는 이미 바빠 스핀 스레드가 선점당한다. 그 증거:

- E1 실측 카메라당 총 **2.05코어** − V1 검출 **1.37코어** = 비검출 전체가 **0.68코어**.
- pose 스핀이 서비스에서도 0.82코어를 태웠다면 이 합이 성립하지 않는다.

→ **서비스 내 회복 가능량의 상한은 0.68코어**(비검출 총량)이고, 하한은 모른다.
**정확한 값은 측정하지 않았다.** 확인하려면 서비스에 세션 옵션을 적용하고 E1 절차를
재실행해야 한다 — **적용은 이 세션 범위 밖(백로그)**.

### 5-4. ★같은 문제가 검출 경로에도 있다

[`rfdetr_adapter.py:70`](../vigent-core/detectors/rfdetr_adapter.py#L70) 도
`ort.InferenceSession(str(onnx_path), providers=["CPUExecutionProvider"])` 로
**`SessionOptions` 없이** 세션을 만든다. [V2 §4-2](v2_onnx_report.md) 에서
**ONNX-CPU 가 torch 보다 CPU 를 1.7~2.2배 더 쓴** 것이 정확히 이 패턴이다
(지연은 2.2~2.3배 빠른데 CPU 는 더 씀 = 스핀).
→ **스핀을 끄면 V2 의 "ONNX 채택 손해" 결론이 뒤집힐 수 있다.** 미측정.

## 6. 기능 범위 결정에 필요한 질문 (★사람 몫)

이 표는 "어디까지 팔면 어느 사양이면 되는가"를 보여줄 뿐, **무엇을 팔지는 결정하지 않는다.**

| # | 질문 | 이 결정이 바꾸는 것 |
|---|---|---|
| **Q1** | 파일럿에서 **화재·연기 감지**를 판매 범위에 넣는가? | ③(3슬롯)↔②(2슬롯). CPU **−0.07코어**, VRAM **−378 MiB**, 지연 −15ms |
| **Q2** | 파일럿에서 **PPE(안전모·조끼) 미착용 감지**를 넣는가? | ②↔④. CPU **−0.12코어**, VRAM **−542 MiB**, 지연 −23ms |
| **Q3** | **지게차/중장비**를 넣는가? | ③↔①. CPU **+0.14코어**, VRAM **+77 MiB**. ⚠F-7 과소학습 오탐으로 **현재 기본 비활성** — 켜려면 모델 개선이 선행돼야 한다 |
| **Q4** | **근골격 자세(pose)** 기능을 파일럿에 넣는가? | GPU-less 시나리오에서 특히 중요(§5 — CPU 를 나눠 쓴다). 끄면 `vision.yaml judgment.ergonomics.joints` 를 비우면 된다 |

★**CPU 관점에서는 Q1·Q2 의 이득이 작다**(합쳐도 0.19코어, 한계 대수 변화 없음).
**VRAM·지연 관점에서는 이득이 크다** — GPU 를 4GB 이하로 내리거나 GPU-less 를 노린다면
그때 의미가 생긴다(V2·V4).
