모의 카메라는 `runs/rfdetr/accident/*.mp4`(**실제 현장 장면**)를 파일 소스로 등록해 워커가

판정)을 탄다. ★정적 이미지 반복은 쓰지 않았다 — 검출 부하가 실장면보다 가벼워 결과가 후해진다.

## 3. 합격 기준 (★측정 전에 선언 — 사후 조정 금지)

기준은 `scripts/capacity_probe.py` 의 `PASS_CRITERIA` 에 박아뒀다.

| 기준 | 값 | 근거 |
|---|---|---|
| 실카메라 detect p95 | 기준 주기의 **2배 이내** | 1대 기준 검출주기 0.40s → 상한 800ms. 침입 디바운스(`zone.enter_s` 1.0초)가 성립하려면 검출이 그 안에 최소 1회는 들어와야 한다 |
| 실카메라 검출주기 p95 | 기준 주기의 2배 이내 | 위와 동일 |
| GPU 메모리 | **90% 이내** | 초과 시 OOM·성능 절벽 위험 |
| 프레임 드랍 | 증가 없음 | 지속 증가 = 처리 못 따라감 |
| status=degraded | **0샘플** | 하나라도 있으면 불합격 |
| 권장 N | 한계 × **0.75** | 야간(조명 변화로 검출 증가)·재연결 폭주 여유 |

**판정은 실카메라 단독 지표로 한다** — 전 카메라 평균은 모의 카메라가 많아질수록 저하를
희석한다(§6 실패 이력 참조).

## 4. 결과 — N별 저하 곡선

1대 기준: detect p50 **94ms** / p95 **105ms** · 검출주기 p95 **0.40s** · GPU 16.9%

| N | 전체 p50 | 전체 p95 | **실카 p95** | **실카 주기 p95** | GPU 메모리 | GPU util p95 | 판정 |
|---|---|---|---|---|---|---|---|
| 2 | 66ms | 95ms | 109ms | 0.40s | 17.2% | 40% | ✅ PASS |
| 3 | 56ms | 125ms | 126ms | 0.50s | 17.5% | 35% | ✅ PASS |
| 4 | 45ms | 95ms | 104ms | 0.50s | 17.8% | 33% | ✅ PASS |
| 5 | 43ms | 82ms | 96ms | 0.50s | 18.0% | 37% | ✅ **PASS(권장 상한)** |
| 6 | 44ms | 83ms | 93ms | 0.50s | 18.3% | 34% | ✅ PASS |
| **7** | 70ms | 116ms | 103ms | 0.50s | 18.5% | 31% | ✅ **PASS(한계)** |
| **8** | 103ms | **309ms** | **255ms** | 0.50s | 18.8% | 23% | ❌ **FAIL** — degraded 1샘플 |

### 해석

- **7대까지는 실카메라 지연이 거의 변하지 않는다**(93~126ms, 기준 105ms 대비 미미).
- **8대에서 급격히 무너진다**: 전체 p95 116ms → **309ms(2.7배)**, 실카메라 p95도 255ms.
  degraded 샘플이 발생해 불합격.
- ★**병목은 GPU 가 아니다**: GPU 메모리는 8대에서도 **18.8%**, util p95 는 오히려 23%로 낮다.
  카메라가 늘수록 util 이 내려가는 것은 **GPU 가 놀고 있다**는 뜻이다.
- ★**[E1, 2026-08-18 갱신] 병목이 특정됐다 — 추론 파이프라인의 CPU 측 연산이다.**
  → [`benchmarks/e1_bottleneck_report.md`](e1_bottleneck_report.md)
  - **CPU 디코드 기각**: 디코드는 프레임당 **0.4~1.2ms**(추론 48ms 의 2% 미만). 픽셀을
    1/9 로 줄여도 한계가 풀리지 않았다.
  - **GIL 기각**: 포화 시 프로세스 CPU **1,479~1,755%**(=14.8~17.6 코어), 24 코어 중
    17~24 개가 >80%. 단일 코어 포화가 아니다.
  - **`DETECT_LOCK` 은 부차적**: 락을 없애면 상한이 21→28.3 검출/초(+33%)로 오르지만
    거기서 멈춘다. N=7 에서는 락을 없애도 **전 코어 99.3% 포화**로 무너진다.
- 따라서 **더 좋은 GPU 를 넣어도 대수가 늘어나지 않는다.** 확장은 **CPU 코어 수·코어당
  성능**이며, 카메라당 소요는 실측 **2.1 논리코어 @2fps** 다. 구매 기준은
  [`docs/edgebox_purchase_guide.md`](../docs/edgebox_purchase_guide.md) 참조.

## 6. ★1차 측정 무효 이력 (감사 기록)

**1차 측정(같은 날)은 무효였다.** 9대까지 전부 PASS 로 나왔으나 실제로는 **부하가 0대**였다.

- **원인 ①**: `POST /cameras` 에 `enabled: true` 를 빠뜨려 등록만 되고 **워커가 기동하지 않았다**
  (`/cameras` 에 enabled=false, `/health` 에 모의 카메라 미등장).
- **원인 ②**: 지표를 전 카메라 평균으로 내 실카메라 저하가 희석됐다. 검출주기 p95 가 기준
  (0.5s)보다 **작아지는**(0.2s) 역설이 나왔는데 이것이 이상 신호였다.
- **발견 경위**: 카메라를 8대 늘렸는데 GPU util 이 46% 에 머물고 지연이 안 늘어난 것이
  부자연스러워 파고들었다.
- **수정**: `enabled: true` 전송 + **워커가 `/health` 에 실제로 나타나는지 확인한 뒤** 다음
  단계로 진행 + 판정을 **실카메라 단독 지표**로 변경.

이 이력을 남기는 이유는, 같은 실수가 재발하면 "측정했는데 아무 부하도 없었다"는 결과가
그럴듯한 합격으로 보이기 때문이다.
