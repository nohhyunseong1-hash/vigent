## 0. 측정 환경 정리

`vmmem`(WSL2)이 802MB 를 잡고 있어 하네스가 "시간 측정 오염" 경고를 냈다. 종료 전 확인 결과
**Docker 데몬 정지 · 컨테이너 0개 · WSL 배포판 Stopped** — 돌고 있는 작업이 없었다.
`wsl --shutdown` 후에도 vmmem 이 남아 **실제 CPU 사용을 직접 쟀다: 8초간 증가 0초**.
즉 메모리만 점유하고 CPU 는 쓰지 않는다(경고는 프로세스 존재만으로 뜨는 보수적 경고).
24코어·부하 37% 에서 측정했다.

## 2. ★경보 폭주 재생 검증 — 오탐 증가를 백오프가 감당하는가

dev 를 영상별 순차 입력하고, 구역=화면 대부분(경보 부하 상한 시나리오)으로 `_derive` →
`alert_gate` 를 실제로 태웠다.

| 후보 | 이벤트 발화 | **폰 알림** | ID없음이라 무시된 검출 |
|---|---|---|---|
| 현행 bytetrack | 7 | **3** | 0 |
| MIN_FRAMES=0 | 8 | **4** | 0 |
| iou 복귀 | **50** | **5** | 0 |
| 하이브리드 | **59** | **5** | 0 |
| 검출통과 | 7 | **3** | **99** |

**① 백오프가 오탐을 잘 흡수한다** — 발화가 7→50(7배)로 늘어도 **폰 알림은 3→5(1.7배)** 에
그친다. "오탐 다발로 현장이 시스템을 꺼버리는" 위험은 **알림 기준으로는 낮다.**
다만 이벤트 기록은 7배로 늘어 디스크·검수 부담이 생긴다.

**② ★검출통과는 경보에 도달하지 못한다** — 발화·알림이 현행과 **완전히 동일**하고,
ID 없는 person **99건이 전부 무시**됐다.

## 3. ★검출통과 후보의 ID 의존 기능 충돌 (요구사항 검토)

검출통과는 **검출 재현율은 38.2% → 61.1% 로 올리지만, 그 이득이 경보에 하나도 전달되지
않는다.** 원인은 [D1-C] 다:

```python
tid = d.get("tid")
if tid is not None:            # ★tid 없는 검출은 구역 판정에서 통째로 빠진다
    inside_tids.append(int(tid))
```

D1-C 에서 구역 침입을 **사람(track) 단위**로 바꾸면서 판정 키가 tid 가 됐다. 검출통과가
만드는 `tid=None` 검출은 이 경로를 못 탄다.

| ID 의존 기능 | 검출통과와의 충돌 |
|---|---|
| **구역 침입 디바운스**(D1-C) | 🔴 **차단** — tid 없으면 판정 자체에 안 들어간다(실측 99건 무시) |
| **사람 단위 쿨다운**(D1-C) | 🔴 키가 `rule\|t<tid>` 라 tid 없으면 규칙 단위로 퇴화 |
| 운전자 제외(`onboard_vehicle`) | 🟢 무영향 — bbox 포함비로 판정, tid 미사용 |
| 근접(협착) 판정 | 🟢 무영향 — bbox 기반 |
| crowd_density | 🟢 무영향 — 개수만 센다 |

**→ 검출통과를 쓰려면 D1-C 를 함께 고쳐야 한다.** 예: tid 없는 검출에 **위치 기반 대체 키**
(발끝점 격자)를 부여해 디바운스를 태우는 방식. 그러면 "같은 자리에 계속 있는 오탐"은
디바운스가 억제하고, 새 위치의 진입은 살아난다. **미구현 — 별도 단계로 제안한다.**

## 5. 권고

**결론부터: 지금 바꾸기에는 근거가 한쪽으로 기울지 않았다.** 두 단계로 나눈다.

### 즉시 적용 권고 — `BYTETRACK_MIN_FRAMES = 0`

| | 이득 | 대가 |
|---|---|---|
| dev | 재현율 **+3.8%p**(38.2→42.0) · 작은박스 0→8% | 정밀도 −2.0%p · FP 11→14 · 알림 3→4 |

거의 공짜다. 원거리 재현율이 0% 에서 벗어나는 유일한 저비용 수단이다.

### 조건부 — `iou 복귀`는 **2fps 확인 후** 결정

큰 이득(dev +31.2%p / test +20.4%p, 원거리 0→83%)이고, 알림 폭주도 백오프가 흡수한다
(3→5). 이전 운영 설정이라 **롤백 성격**이라는 점도 유리하다. 그럼에도 지금 권고하지 않는 이유:

1. **측정이 1fps 표본이라 ByteTrack 에 불리하다.** 추적 생존율 실측: 1fps 67.4% vs
   **2fps(운영) 73.9%**. 운영에서는 격차가 지금보다 좁다.
2. **dev 와 test 의 현행 성능이 크게 다르다**(38.2% vs 59.1%) — 표본에 따라 흔들린다.
3. **정밀도 대가가 크다**: test 에서 FP 0 → 27. 이벤트 기록이 7배로 늘어 검수 부담이 생긴다.

**→ 학원 방문에서 2fps 실데이터로 확인한 뒤 결정하는 것을 권한다.**
(이미 절차서에 `VIGENT_TRACK_DEBUG=1` 20분 수집이 들어가 있다 — 같은 수집으로 판단 가능.)

### 기각

| 후보 | 사유 |
|---|---|
| 하이브리드 | 정밀도 38.3%·FP 185·**고유ID 99개(5배 churn)**. D1-C 의 사람 단위 쿨다운이 ID churn 으로 무력화돼 기록이 폭증한다 |
| 검출통과(현 형태) | §3 대로 **경보에 도달하지 못한다**. D1-C 위치 기반 대체 키를 먼저 구현해야 후보가 된다 |
