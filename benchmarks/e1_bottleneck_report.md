# [E1] 카메라 수용량 병목 원인 특정 (2026-08-18)

> 배경: `benchmarks/capacity_report.md` §5 가 **"병목 원인 미확정 — GPU 가 아니라는 것만 확인"**
> 으로 남겨둔 공백을 메운다. 목적은 **특정**이며, 병목 *해소*는 이 실험의 범위가 아니다.
>
> **본 판정은 실서비스 직접 계측(§2)** 이고, 저해상 대조군(§3)·per-core(§4)·별도 프로세스(§5)로
> 교차 검증했다. **세 갈래가 어긋난 지점은 §6 에 그대로 남겼다 — 하나로 꿰맞추지 않았다.**
>
> 원자료·스크립트: `benchmarks/e1_bottleneck/`

## 0. 결론 한 줄

**병목은 CPU 다. 그러나 가설로 세웠던 "영상 디코드"가 아니라 "추론 파이프라인 전반의
CPU 연산"이다.** 픽셀을 1/9 로 줄여도 CPU 는 **5% 밖에** 줄지 않는다.

★따라서 **GPU 를 올려도 카메라 대수는 늘지 않는다**(8대에서도 GPU util 16~42%).
예산은 GPU 가 아니라 **CPU** 에 써야 한다. → `docs/edgebox_purchase_guide.md`

## 1. 가설별 판정

| 가설 | 판정 | 근거 수치(본판정 = 실서비스 직접 계측) |
|---|---|---|
| **H1** CPU 영상 디코드가 병목 | ❌ **기각** | 모의 카메라 픽셀을 **1/9** 로 줄였을 때 카메라당 CPU 는 **208.4% → 196.9%(−5.5%)** 에 그쳤다. 디코드가 병목이면 나올 수 없는 값이다. 보조 근거(§5): 디코드 실측 **0.4~1.2ms**(추론 47ms 의 2% 미만) |
| **H2** `DETECT_LOCK` 추론 직렬화가 병목 | 🔸 **부분 지지(부차적) — CPU 보다 늦게 막는다** | 락 점유율 ρ = N×추론×fps → N=7 에서 **65%**, N=8 에서 **74%**. 락만으로 포화하는 지점은 **N≈10.7대**인데, **CPU 는 N=8 에서 이미 막힌다**(§2-3). 보조 근거(§5): 락 제거 시 상한 21→28.3 검출/초(+33%)로 오르지만 N=7 에서는 전 코어 99.3% 포화로 붕괴 |
| **H3** GIL 단일 코어 포화 | ❌ **기각** | 단일 코어 고정 포화가 **없다**. N=8 에서 프로세스 CPU **1,541~1,600%**(= 15.4~16.0 코어), 24 코어 중 **10~15 개가 >80%**. GIL 이 지배적이면 프로세스 CPU 가 ~100~200% 를 넘을 수 없다 |
| **H4** 기타 — **추론 파이프라인의 CPU 연산 포화** | ✅ **지지(주원인)** | **8번째 카메라의 한계 CPU 증분이 208% → 109% 로 반토막**나면서 실카메라 지연 p95 가 139 → 159ms 로 악화됐다(§2-3). 자원을 더 못 받아 **성능으로 값을 치르기 시작한 것** — 전형적 CPU 포화 신호. 이때 코어 평균 **79.2%**, GPU 는 **20%** |

### H4 를 주원인으로 보는 이유

포화 시점에 **CPU 는 79~99%, GPU 는 16~42%** 다. 그리고 그 CPU 는 디코드가 아니다(H1 기각).
남는 것은 **추론 호출 전후의 CPU 작업**(전처리 리사이즈·정규화, 후처리·NMS, 텐서 마샬링,
슬롯 반복)과 **검출 밖 파이프라인**(JPEG 인코딩·추적·존 판정·익명화·WS 송신)이다.
§7 에서 이 둘의 비중을 실측으로 나눴다 — **검출이 약 70%** 다.

### ★[V1, 2026-08-19] H4 재해석 — 그 CPU 의 일부는 '연산'이 아니라 '스핀 낭비'다

[V1 §5-2](v1_slot_config_report.md) 에서 **pose(RTMPose/onnxruntime)의 CPU 소모 대부분이
실연산이 아니라 busy-wait 임이 실증**됐다 — 세션 옵션만 바꿔 **0.82 → 0.09코어(−89%)**,
지연은 7.3 → 12.3ms 만 증가.

이 서비스에서 ORT 를 쓰는 경로는 **pose 뿐**이고(검출은 torch, backend=torch), pose 는
§7 의 **검출 밖 0.65~0.68코어** 안에 들어 있다. 따라서:

| 항목 | 값 |
|---|---|
| H4 판정 자체 | **유효** — 병목이 CPU 이고 디코드·GIL 이 아니라는 결론은 그대로다 |
| 그러나 **성격이 달라진다** | 측정된 CPU 의 일부는 **필요한 계산이 아니라 설정으로 없앨 수 있는 낭비**다 |
| 서비스 내 회복 가능량 | **0 ~ 0.68코어/카메라**(상한 = 검출 밖 총량). **정확한 값은 측정하지 않았다** |
| 그에 따른 한계 대수 | 현재 **8.3대** → 회복분에 따라 최대 **12.3대**(24스레드 기준, 상한 가정) |

★**즉 "카메라 7~8대"라는 한계가 하드웨어의 물리적 한계가 아닐 수 있다.** 설정 한 줄로
일부가 회복될 여지가 있다. **적용·검증은 이 세션 범위 밖(백로그, §11).**

★**"CPU 병목 = 디코드"** 라는 통념이 여기서 깨진다. 해상도를 낮추는 대응은 효과가 없다.

## 2. 본 판정 — 실서비스 직접 계측

`/health` 의 `lock_wait_ms`·`infer_ms` 를 부하 단계별로 수집했다(`e1_live.py`, 구간 90초,
2초 간격 표본). 실카메라 1대(Tapo RTSP) + 모의 카메라 N−1대, 카메라당 2fps.

★**C5 실패 재발 방지**: `enabled:true` 로 등록하고 **워커가 `/health` 에 실제로 검출을 돌리는
것을 확인한 뒤에만** 측정을 시작했다(등록만 되고 부하가 0인 채로 합격이 나오는 사고 방지).

### 2-1. 단계별 결과 (고해상, 모의 카메라 집계 / N=7·8 은 3회 평균)

| N | 락대기 p50 | 락대기 p95 | 추론 p50 | 추론 p95 | 실카 지연 p95 | 코어 평균 | >80% 코어 | 프로세스 CPU | GPU util |
|---|---|---|---|---|---|---|---|---|---|
| 1 | — | — | — | — | 148.2ms | 20.4% | 0 | 215.5% | 39% |
| 4 | 12.8 | 45.0 | 38.6 | 61.5 | 102.6ms | 48.4% | 1 | 862.5% | 22% |
| **7** | **12.9** | **83.3** | **46.6** | **66.3** | **139.1ms** | **74.6%** | 8~9 | **1465.7%** | 23% |
| **8** | **16.1** | **103.5** | **46.4** | **65.9** | **159.0ms** | **79.2%** | 10~15 | **1574.7%** | 20% |

### 2-2. 재현성 — 무엇이 안정적이고 무엇이 아닌가 (3회 반복)

| 지표 | N=7 3회 | N=8 3회 | 재현성 |
|---|---|---|---|
| 프로세스 CPU | 1443.2 / 1459.8 / 1494.0 | 1599.6 / 1583.2 / 1541.2 | ✅ **±2% 이내 — 매우 안정** |
| 코어 평균 | 74.4 / 74.2 / 75.1 | 80.2 / 79.7 / 77.8 | ✅ **안정** |
| 추론 p50 | 46.0 / 47.7 / 46.2 | 46.2 / 46.4 / 46.6 | ✅ **±2% 이내 — 매우 안정** |
| **락 대기 p50** | **6.0 / 32.6 / 0.0** | **0.0 / 0.0 / 48.2** | ❌ **재현되지 않음** |
| 실카 지연 p95 | 177.8 / 103.4 / 136.0 | 137.2 / 125.5 / 214.4 | ❌ **분산 큼** |

**해석**: **CPU 소모와 추론 시간은 결정론적**이고, **락 대기는 운(워커 위상)에 좌우된다.**
워커들이 우연히 겹치는 위상으로 자리잡은 회차에는 락 대기가 튀고, 흩어진 회차에는 0 이다.
→ **락은 "항상 있는 벽"이 아니라 "가끔 터지는 지연"** 이다. H2 를 부차적으로 판정한 근거.

### 2-3. ★핵심 — 8번째 카메라에서 나타난 포화 신호

| 구간 | 프로세스 CPU | **카메라 1대 추가당 CPU 증분** | 실카 지연 p95 |
|---|---|---|---|
| N=1 → N=7 | 215.5 → 1465.7 | **+208.4%/대** | 148.2 → 139.1ms |
| **N=7 → N=8** | 1465.7 → 1574.7 | **+109.0%/대 (반토막)** | 139.1 → **159.0ms (악화)** |

8번째 카메라는 **앞선 카메라들이 받던 CPU 의 절반밖에 받지 못했고**, 부족분을 **지연으로
값을 치렀다**. 이것이 CPU 포화의 직접 증거다. C5 가 **8대에서 불합격**으로 판정한 지점과
정확히 일치한다.

**락은 이 시점에 아직 여유가 있다**: 점유율 ρ = 8 × 0.0464s × 2/s = **74%**.
락만으로 포화하려면 N ≈ 1 ÷ (0.0464 × 2) = **10.7대**가 필요하다.
→ **CPU 가 락보다 먼저 막는다.**

## 3. 저해상도 대조군 — H1 결정적 기각 (실서비스)

같은 장면을 **가로·세로 1/3(픽셀 1/9)** 로 줄인 소스로 모의 카메라를 돌렸다.
실카메라(1080p RTSP)는 그대로다 — 즉 **N−1대의 디코드 부하만** 9분의 1로 줄인 조건.

| N | 프로세스 CPU (고해상) | (저해상) | 절감 | 코어 평균 hi→lo | 추론 p50 hi→lo |
|---|---|---|---|---|---|
| 4 | 862.5% | 810.4% | **−6.0%** | 48.4 → 45.1% | 38.6 → 29.4ms |
| 7 | 1465.7% | 1397.3% | **−4.7%** | 74.6 → 70.9% | 46.6 → 33.5ms |
| 8 | 1574.7% | 1516.7% | **−3.7%** | 79.2 → 76.4% | 46.4 → 35.0ms |

**카메라당으로 환산하면 208.4% → 196.9%, 즉 −5.5%.**

디코드 부하를 **9분의 1** 로 줄였는데 CPU 는 **5% 남짓** 줄었다. 게다가 그 절감분마저
디코드가 아니라 **추론이 46.6→33.5ms 로 줄어든 결과**(전처리 리사이즈 감소)로 보인다.
→ **H1 기각.**

★참고: 저해상에서는 실카메라 지연 p95 가 **99.8~106.1ms 로 평탄**해졌다(고해상 139~159ms).
경쟁 카메라가 가벼워지면 실카메라가 덜 밀린다 — 부하가 실제로 걸렸다는 방증이기도 하다.

## 5. 교차검증 ③ — 별도 프로세스 재현 (보조)

서비스와 무관한 프로세스에서 같은 구조(워커 N 스레드 + 공유 `RLock` + 같은 `guard.detect`)를
재현했다. 검출만 돌리므로 **검출 밖 파이프라인이 빠져 있다.** `e1_standalone.py` / `e1_saturate.py`.

**5-1. 단계 분해(2fps 고정) — 디코드를 직접 잰 유일한 실험**

| N | 디코드 p95 | 락 대기 p50 | 추론 p50 | 프로세스 CPU |
|---|---|---|---|---|
| 1 | **0.4ms** | 0.0 | 47.2ms | 152.0% |
| 4 | **0.9ms** | 53.2 | 46.7ms | 577.8% |
| 7 | **1.0ms** | 104.5 | 50.4ms | 1009.0% |

→ **디코드는 프레임당 1ms 미만**. H1 기각의 직접 근거다.

**5-2. 포화 처리량 — 락 제거 대조군(측정 전용, 서비스는 변경하지 않음)**

| N | 처리량(락 있음) | 처리량(락 없음) | 코어 평균(락 없음) | GPU(락 없음) |
|---|---|---|---|---|
| 1 | 20.24 검출/초 | 20.27 | 34.2% | 22.7% |
| 2 | 22.62 | **27.36** | 52.1% | 35.8% |
| 4 | 21.33 | **28.29** | 79.2% | 30.7% |
| 7 | 20.98 | **19.98(붕괴)** | **99.3%(24/24 코어)** | 20.5% |

락을 없애면 상한이 **21 → 28.3(+33%)** 로 오르지만 거기서 멈추고, N=7 에서는 **전 코어
포화로 오히려 떨어진다.** GPU 는 끝까지 논다. → **락은 부차적, CPU 가 진짜 벽.**

## 6. ★세 갈래가 어긋난 지점 (꿰맞추지 않고 그대로 보고)

### 모순 1 — 락 대기가 ③에서 실서비스보다 8배 크다 (**미해명**)

| | N=7 락 대기 p50 |
|---|---|
| 실서비스 직접 계측(본판정) | **12.9ms**(3회: 6.0 / 32.6 / 0.0) |
| ③ 별도 프로세스 | **104.5ms** |

**추정(미검증)**: ③은 N개 스레드를 **동시에 기동**해 위상이 겹친 채 유지됐고, 실서비스
워커는 등록 시각이 수 초씩 달라 위상이 흩어진다. 대기행렬 근사(점유율 65%)로 계산한
평균 대기는 41ms 로 **실서비스 쪽에 가깝다** — 즉 **③이 과대평가했을 가능성**이 높다.
다만 이는 계산에 의한 추론이며 **위상을 직접 관측해 확인하지 않았다.**

**영향**: H2 판정이 "주원인"에서 "부차적"으로 내려간다. 본판정(실서비스)을 채택했다.

### 모순 2 — N=8 이 N=7 보다 나은 회차가 있었다 (**해소됨: 회차 분산**)

1회차만 보면 실카 지연 p95 가 N=7 177.8ms > N=8 137.2ms 로 역전이었다.
**3회 반복 결과 평균은 N=7 139.1ms < N=8 159.0ms 로 정상 순서**이며, 회차별 범위가
크게 겹친다(N=7 103~178, N=8 126~214). → **1회 측정으로 순서를 논할 수 없다.**
지연 지표는 락 대기와 함께 움직이는 **비재현성 지표**다(§2-2).

### 모순 3 — 초판 리포트의 "검출 단독 0.4 코어"는 오류였다 (**정정**)

초판에서 *"검출은 카메라당 0.4 코어, 나머지 1.7 코어는 검출 밖 파이프라인"* 이라고 적었다.
이는 **포화 상태 CPU(407%)를 처리량(20.24검출/초)으로 나눠 저부하로 선형 환산**한 값인데,
**CPU 사용량은 처리율에 선형이 아니다**(포화 시 스레드 경합으로 추론당 코어 수가 줄어든다).
같은 2fps 조건에서 직접 잰 값은 **1.43 코어**다(§7). **비중이 19% → 70% 로 뒤집힌다.**

## 7. 카메라당 자원 예산 (E2 사양 도출의 근거)

| 측정 | 카메라당 CPU @2fps | 포함 범위 |
|---|---|---|
| 실서비스 직접 계측(§2) | **208.4%** | 전체 파이프라인 |
| per-core 프로브(§4) | **209.8%** | 전체 파이프라인 |
| 별도 프로세스(§5-1) | **142.8%** | **검출만**(디코드+락+추론) |

> ### 카메라 1대 = **약 2.1 논리코어 @ 2fps**
> 그중 **검출이 약 1.43 코어(약 70%)**, **검출 밖 파이프라인**(JPEG 인코딩·추적·존 판정·
> 익명화·WS 송신)이 **약 0.65 코어(약 30%)**.

**대수 산정식**(같은 코어당 성능 가정):

```
한계 N ≈ 논리코어 수 × 0.70 ÷ 2.1     권장 N = 한계 × 0.75
```

- **검산 1**: 24코어 → 8.0대. C5 실측 한계 **7대**, 그리고 §2-3 에서 **8대째에 포화 신호**가
  나타났다 — 부합한다.
- **검산 2(독립)**: C-1(2026-08-11)이 **같은 개발기**에서 **1fps** 로 "16대까지 미포화"를
  실측했다. 2.1코어를 1fps 로 환산하면 1.05코어/대 → 24×0.70÷1.05 = **16.0대**. 일치한다.

⚠ **이 식은 코어당 성능이 같을 때만 성립한다.** 다른 CPU 는 **측정하지 않았다**(규칙7).
구매 후 `capacity_probe.py` 재측정 필수.

## 9. 한계 (규칙7 — 측정하지 않은 것)

| 항목 | 내용 |
|---|---|
| **실서비스 디코드 미계측** | `/health` 의 `read_ms` 는 **디코드 시간이 아니다** — 스트림에서는 네트워크 대기를 포함하고 파일 소스에서는 기록되지 않는다(`worker.py:918`). 이를 위해 `decode_ms` 계측을 추가했으나 **다음 재시작 전까지는 값이 나오지 않는다.** 따라서 H1 의 실서비스 근거는 **저해상 대조군(§3)** 이고, 디코드 절대값은 ③(§5-1)에만 있다 |

| **다른 CPU 미측정** | 카메라당 2.1코어는 **이 CPU 에서만** 잰 값이다. 코어당 성능 환산은 **추정**이며 검증되지 않았다 |
| **파일 디코드 ≠ RTSP 디코드** | 모의 카메라는 로컬 mp4 다. 실카메라 1080p H.264 네트워크 스트림은 더 비쌀 수 있다. 다만 §3 의 저해상 대조군은 그 비용까지 포함해 −5.5% 였다 |
| **전·후처리 내부 미분해** | "추론 CPU측 연산"을 전처리/후처리/NMS/마샬링으로 더 쪼개지 않았다. 어느 항이 지배적인지는 **모른다** |
| **락 제거는 측정 전용** | ③의 대조군만 락을 뺐다. 서비스의 `DETECT_LOCK` 은 **변경하지 않았다**(스레드 안전성 미검증) |
| **구간 90초 · 회차 제한** | N=7·8 만 3회, N=1·4 는 1회다 |
