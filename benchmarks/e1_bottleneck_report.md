# [E1] 카메라 수용량 병목 원인 특정 (2026-08-18)

> 배경: `benchmarks/capacity_report.md` §5 가 **"병목 원인 미확정 — GPU 가 아니라는 것만 확인"**
> 으로 남겨둔 공백을 메운다. 목적은 **특정**이며, 병목 *해소*는 이 실험의 범위가 아니다.
>
> 원자료·스크립트: `benchmarks/e1_bottleneck/`
> 재현: `python e1_saturate.py 45` · `E1_NOLOCK=1 python e1_saturate.py 45` · `python e1_standalone.py hi|lo 60`

## 0. 결론 한 줄

**병목은 CPU 가 맞다. 그러나 가설로 세웠던 "영상 디코드"가 아니라 "추론 파이프라인의
CPU 측 연산"이다.** 디코드는 프레임당 **0.4~1.2ms** 로 전체의 2% 미만이다.

★따라서 **GPU 를 올려도 카메라 대수는 늘지 않는다**(7대에서도 GPU util 20~37%).
예산은 GPU 가 아니라 **CPU** 에 써야 한다. → `docs/edgebox_purchase_guide.md`

## 1. 가설별 판정

| 가설 | 판정 | 근거 수치 |
|---|---|---|
| **H1** CPU 영상 디코드가 병목 | ❌ **기각** | 디코드 p95 = **0.4 / 0.9 / 1.0ms**(N=1/4/7). 같은 프레임의 추론은 **47~50ms** — 디코드는 **2% 미만**. 픽셀을 **1/9 로 줄인** 저해상 소스로 동일 실험 시 디코드는 1.0→0.3ms 만 줄었고 **처리량 한계는 그대로**였다 |
| **H2** `DETECT_LOCK` 추론 직렬화가 병목 | 🔸 **부분 지지(부차적)** | 락 제거 시 최대 처리량 **21.3 → 28.3 검출/초(+33%, N=4)**. 그러나 **N=7 에서는 락을 없애도 19.98 로 붕괴** — 락은 상한을 33% 깎지만 **최종 한계를 만드는 원인은 아니다** |
| **H3** GIL 단일 코어 포화 | ❌ **기각** | 단일 코어 고정 포화가 **없다**. N=7 에서 24 코어 중 **17~24 개가 >80%**, 프로세스 CPU **1479~1755%**(= 14.8~17.6 코어). GIL 이 지배적이면 프로세스 CPU 가 ~100~200% 를 넘을 수 없다 |
| **H4** 기타 — **추론 전·후처리의 CPU 연산 포화** | ✅ **지지(주원인)** | 락을 없앤 N=7 에서 **전 코어(24/24)가 >80%, 코어 평균 99.3%** 인데 **GPU util 은 오히려 20.5% 로 하락**, 처리량은 28.3→**20.0 으로 역전**. 게다가 **검출 1회가 단독으로도 CPU 403%(≈4코어)** 를 쓴다(N=1, GPU 24.7%) |

### H4 를 주원인으로 보는 이유

포화 시점에 **CPU 는 100%, GPU 는 20%** 다. 자원 하나가 100% 이고 다른 하나가 20% 이면
100% 인 쪽이 한계다. 그리고 그 CPU 는 디코드(1ms)가 아니므로 남는 것은 **추론 호출 내부의
CPU 측 작업**(전처리 리사이즈·정규화, 후처리·NMS, 텐서 마샬링, 4슬롯 반복)이다.

★**"CPU 병목 = 디코드"** 라는 통념이 여기서 깨진다. 해상도를 낮추는 대응은 효과가 없고
(저해상 실험이 증명), 유효한 방향은 **코어 수·코어당 성능·슬롯 수·전후처리 최적화**다.

## 2. 실험 A — 포화 처리량과 자원 점유 (핵심 근거)

fps 제한을 풀고 낼 수 있는 최대 처리량을 측정했다. `e1_saturate.py`, 구간당 45초.

**A-1. 현재 구조(락 있음)**

| N | 처리량(검출/초) | 지연 p50 | 코어 평균 | >80% 코어 | 프로세스 CPU | GPU util 평균 |
|---|---|---|---|---|---|---|
| 1 | 20.24 | 48.5ms | 35.4% | 2 | 407.0% | 24.7% |
| 2 | 22.62 | 88.0ms | 46.8% | 5 | 687.8% | 27.1% |
| 4 | 21.33 | 190.0ms | 71.4% | 9 | 1254.8% | 23.5% |
| 7 | 20.98 | 341.7ms | 80.8% | 17 | 1479.5% | 32.0% |

→ **처리량이 N 과 무관하게 ~21 검출/초로 고정**되고 지연만 N 배로 늘어난다.
이는 락이 직렬화하는 구조상 당연하다(21 ≈ 1 ÷ 48.5ms).

**A-2. 대조군(락 제거 — 측정 전용, 서비스는 변경하지 않음)**

| N | 처리량(검출/초) | 지연 p50 | 코어 평균 | >80% 코어 | 프로세스 CPU | GPU util 평균 |
|---|---|---|---|---|---|---|
| 1 | 20.27 | 48.6ms | 34.2% | 2 | 403.3% | 22.7% |
| 2 | **27.36** | 73.2ms | 52.1% | 5 | 746.7% | 35.8% |
| 4 | **28.29** | 136.7ms | 79.2% | 13 | 1383.2% | 30.7% |
| 7 | **19.98** | 353.9ms | **99.3%** | **24** | 1755.0% | 20.5% |

→ 락을 없애면 상한이 **21 → 28.3(+33%)** 로 오르지만 거기서 멈춘다. N=7 에서는
**모든 코어가 포화(99.3%)** 되며 처리량이 오히려 **떨어진다**. GPU 는 계속 논다.

## 3. 실험 B — 단계 분해(디코드 / 락대기 / 추론)

카메라당 2fps 로 고정하고 단계별 소요를 분리 계측했다. `e1_standalone.py hi 60`.

| N | 디코드 p95 | 락 대기 p50 | 락 대기 p95 | 추론 p50 | 추론 p95 |
|---|---|---|---|---|---|
| 1 | 0.4ms | 0.0 | 0.0 | 47.2ms | 68.7ms |
| 4 | 0.9ms | 53.2 | 118.4 | 46.7ms | 64.7ms |
| 7 | 1.0ms | **104.5** | **231.0** | 50.4ms | 67.8ms |

- **디코드는 사실상 0**(1ms 미만) — H1 기각의 직접 근거.
- **락 대기만 N 에 비례해 자란다**(0 → 53 → 105ms). N=7 에서 프레임 한 장의 지연 중
  **약 3분의 2가 순수 대기**다.
- **추론 시간 자체는 N 과 무관하게 일정**(47~50ms) → GPU 가 밀리는 것이 아니다.

## 4. 실험 C — 저해상도 대조군 (H1 결정적 기각)

같은 장면을 **가로·세로 1/3(픽셀 1/9)** 로 줄여 동일 실험. `e1_standalone.py lo 60`.

| N | 디코드 p95 | 락 대기 p50 | 추론 p50 |
|---|---|---|---|
| 1 | 0.0ms | 0.0 | 32.6ms |
| 4 | 0.3ms | 47.3 | 32.7ms |
| 7 | 0.3ms | **93.2** | 34.8ms |

디코드 부하를 **9분의 1** 로 줄였는데 락 대기는 104.5 → 93.2ms, **11% 밖에 줄지 않았다.**
그나마도 디코드가 아니라 **추론이 50.4→34.8ms 로 줄어든 결과**다(전처리 리사이즈 감소).
→ **디코드는 병목이 아니다.**

## 5. 카메라당 자원 예산 (E2 사양 도출의 근거)

실제 서비스 프로세스에서 모의 카메라를 늘리며 측정(`e1_probe.py`, 2fps/대).

| N | 코어 최대 | 코어 평균 | >50% 코어 | 프로세스 CPU | GPU util p95 | GPU 메모리 |
|---|---|---|---|---|---|---|
| 1 | 39.9% | 15.7% | 0 | 204.9% | 25.0% | 3205 MiB |
| 4 | 67.7% | 43.7% | 7 | 841.1% | 27.0% | 3209 MiB |
| 7 | 93.2% | 70.4% | 22 | 1463.5% | 26.0% | 3239 MiB |

**증분이 일정하다**: (841.1−204.9)/3 = **212.1%/대**, (1463.5−841.1)/3 = **207.5%/대**.

> ### 카메라당 **≈2.1 코어 @ 2fps** (아래 §6 측정 사양 기준)
> 선형 회귀 시 절편 ≈ 0 → 기준선 상주 비용은 무시할 수준이고 **비용이 전부 카메라 수에 비례**한다.

**내역 분해**: 검출 호출(`detect()`) 단독은 카메라당 약 **0.4 코어**다
(포화 시 403% ÷ 20.24검출/초 = 검출당 0.199 코어초 × 2fps). 나머지 **≈1.7 코어**는
검출 밖 파이프라인(JPEG/dataurl 인코딩·추적·존 판정·얼굴 익명화·WS 송신)이 쓴다.

**대수 산정식**(같은 코어당 성능 가정):

```
한계 N ≈ 논리코어 수 × 0.70 ÷ 2.1     권장 N = 한계 × 0.75
```

검산: 24코어 → 한계 8.0대. **C5 실측 한계는 7대**(코어 평균 70.4%에서 붕괴) — 식이 실측과
부합하며 약간 낙관적이므로 **구매 판단에는 실측값(7대)을 쓴다.**

⚠ **이 식은 코어당 성능이 같을 때만 성립한다.** 구형·저클럭 CPU 는 코어 수가 같아도
느리다. 우리는 **다른 CPU 에서 측정하지 않았다**(규칙7) → 구매 후 `capacity_probe.py` 재측정 필수.

## 7. 한계 (규칙7 — 측정하지 않은 것)

| 항목 | 내용 |
|---|---|
| **다른 CPU 미측정** | 카메라당 2.1코어는 **이 CPU 에서만** 잰 값이다. 코어당 성능이 다른 CPU 로의 환산은 **추정**이며 검증되지 않았다 |
| **파일 디코드 ≠ RTSP 디코드** | 실험은 로컬 mp4 를 디코드했다. 실카메라 1080p H.264 네트워크 스트림은 더 비쌀 수 있다. 다만 **10배로 잡아도 10ms 대 추론 50ms** 로 결론은 바뀌지 않는다 |
| **전·후처리 내부 미분해** | "추론 CPU측 연산"을 전처리/후처리/NMS/마샬링으로 더 쪼개지는 않았다. 어느 항이 지배적인지는 **모른다** |
| **대조군의 부하 간섭** | 별도 프로세스 실험 중 서비스(실카메라 1대)가 함께 돌고 있었다. 그 몫은 프로세스 CPU 측정에서는 분리됐지만 코어 점유율에는 포함돼 있다 |
| **락 제거는 측정 전용** | 대조군은 별도 프로세스에서만 락을 뺐다. 서비스의 `DETECT_LOCK` 은 **변경하지 않았다**(스레드 안전성 미검증) |

## 8. 기존 문서 정정 (규칙7)

`benchmarks/capacity_report.md` §4 해석에 *"CPU 디코드·`DETECT_LOCK` 직렬화·GIL 이 먼저 막는
구조로 **보인다**"* 라고 적혀 있었다. 이번 실측 결과 **CPU 디코드와 GIL 은 기각**,
**락은 부차적(상한 33% 손실)**, **주원인은 추론 파이프라인의 CPU 측 연산**이다.
해당 문서 §4·§5 를 이 결과로 갱신했다.

## 9. 후속(이 세션 범위 밖 — 병목 *해소* 백로그)
