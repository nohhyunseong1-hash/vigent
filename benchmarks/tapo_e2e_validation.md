## 2. 지연 예산표 (실측)

한 프레임의 여정(person 박스 기준). 측정: 시계 촬영(카메라가 밀리초 시계 화면을 촬영 → 스냅샷 속 시각과 수신 시각의 차, 전부 PC 시계 기준), 10ms 밀착 폴링, 실보행 캡처 재생 시뮬.

| 구간 | p50 | 비고 |
|---|---|---|
| 카메라 인코딩→RTSP 도달 | **~1.35s** | 시계 촬영 실측. go2rtc(Go 클라이언트) 경유 WebRTC 영상도 동일 ~1.4s → 카메라 자체 지연으로 확정(§3) |
| 워커 캡처 큐(수정 전) | 성장형 +0.09s/s | grab-드레인 도입 후 성장 0(21초간 1.40→1.35s 안정) |
| 프레임 읽기→추론→응답 가용 | 111ms (p95 135) | 10ms 폴링, ts 대비 |
| 프론트 폴링 발견 | ~25ms (max 50) | 50ms 주기 — 병목 아님 |
| 표시 스택 이동시작 관성(수정 전) | 283ms (p95 885) | 재생 시뮬. 클램프 80ms 후 p50 0ms(p95 467) |
| 렌더 | ~8ms | 60fps rAF |

**영상 대비 박스 정렬**: 영상(WebRTC)·박스 모두 카메라 ~1.4s를 공유하므로, 화면 속 사람 대비 박스의 체감 지연은 카메라 이후 구간(추론+폴링+관성 ≈ 0.15~0.4s)이다. 확대뷰 설정 패널의 "표시 오프셋"(음수 = 외삽 선행, extrapCap 상한 내)으로 카메라별 미세 정렬 가능.

## 3. 카메라 자체 지연 ~1.4s — 판정 근거와 함의

- 우리 캡처 경로(OpenCV/FFmpeg): 시계 촬영 1.35~1.47s (grab-드레인·FFmpeg nobuffer 적용 후에도 불변)
- go2rtc 경로(자체 Go RTSP 클라이언트, FFmpeg 무관) → WebRTC 브라우저 재생: 사용자 동시 비교 ~1.4s
- **서로 다른 두 클라이언트가 같은 값 → 공통 구간인 카메라 내부(인코더·GOP 버퍼)로 확정**
- 함의: ① 클라이언트 튜닝으로 더 못 줄인다 ② 파일럿 안내 시 "경보 시점은 실제 상황보다 ~1.5+α초 후"를 명시할 것 ③ 후속 후보: 카메라 설정(해상도/fps/GOP) 하향 실험, stream2(저해상) 전환 실험, 저지연 펌웨어/타 기종 비교 — P3 백로그로
- 안전 판정(경보) 관점: PPE·침입 등은 수 초 지속 상황이라 1.4s 지연은 기능 유효성을 해치지 않음. 단 "실시간 관제 화면"으로 팔 때는 지연 고지 필요

## 4. go2rtc 8555 전체 바인딩 — 보안 트레이드오프 (S2 일부 완화)

- 사유: Chrome은 ICE 후보 수집에서 루프백을 제외 → 127.0.0.1 단독 바인딩으로는 같은 머신 브라우저조차 WebRTC 불성립(실측 "ICE closed", S3 스모크는 SDP 교환만 확인해 못 잡음)
- 완화 근거: 8555는 미디어 전용(세션별 ICE 자격증명+DTLS 필수), 시그널링(1984)은 계속 127.0.0.1 잠금 → 이 포트만으로 영상 추출 불가
- 배포 권장: 방화벽으로 8555를 관제 PC 고정 IP에만 개방 — 상세 docs/edge_network_hardening.md §1·§1-1

## 5. 파일 카메라 vs 실카메라 — 이번에야 드러난 차이

1. **자격증명·계정 상태**: 파일 소스엔 없음. 실카메라는 리셋 시 계정 초기화 → DESCRIBE 401. 진단 표준절차: cv2 직접 1프레임 테스트로 실패 단계 특정
2. **버퍼 누적**: 파일은 `is_stream=False`라 `VIGENT_CAPTURE_MODE`가 무의미 — 스트림 캡처 경로(thread·grab-드레인)는 실 RTSP에서 처음 검증됨. read() 단독은 고해상 디코드가 추론과 CPU 경합 시 큐가 자라 지연이 무한 성장(실측 +0.09s/s)
3. **카메라 내부 지연**: 파일엔 0, 실카메라 ~1.4s — 표시 정합(박스 vs 영상) 문제의 뿌리
4. **WebRTC ICE**: 파일 카메라 시절 S3 리허설은 프로토콜 레벨만 통과 — 실브라우저 ICE는 바인딩 이슈로 실패했었음
5. **트래커 파편화**: 실보행(빠른 이동+작은 PPE 박스)은 파일 테스트 영상보다 매칭을 심하게 깨뜨림 — 유령 박스는 실카메라에서야 재현

## 6. 파일럿 전 수정 필요 항목 (백로그 후보)

- **PPE 표시 캐던스**: focus 중에도 풀세트(PPE)는 base 2fps — PPE 박스는 구조적으로 최대 ~500ms 추가 지연. 관제용 프로파일에서 풀세트 fps 상향 검토(비용 재측정 필요)
- **트래커 파편화 근본 개선**: PPE id 교체 심함(계측: 20초 221트랙) — track.algo=bytetrack(person 한정 기존 옵션)의 PPE 확장 또는 매칭 게이트 속도 확장 A/B
- **카메라 지연 저감 실험**: §3 후속 후보
- **focus_fps 기본값**: 5→8 채택 여부 — 실측 달성 7.33회/초, 서버 CPU 평균 437→464%(24논리코어, 기계 전체 +1.1%p). 채택 시 config/tuning.yaml `hub.focus_fps: 8`
- **fps_live 명명**: 목표 fps인데 "live"로 읽힘 — 달성률(검출 갱신률) 별도 노출 검토
- 30분 연속 측정·재연결 내성 테스트(전원 30초 차단)는 본 검증에서 미수행 — T-E2E 원계획 항목 3·4로 잔존

## 7. 재현 절차(측정 스크립트)

- 검출 배치 캡처: scratchpad `capture_dets.py`(40ms 폴링, ts 단위 JSONL) → 유령 지표(동시 다중·동결 잔류) 산출
- 표시 스택 재생 시뮬: scratchpad `sim_boxtracker.py`(BoxTracker 수식 재현, cg 클램프 A/B)
- 시계 촬영: scratchpad `clock.html`(밀리초 시계 전체화면) → `/cameras/{cid}/snapshot` 연사 → 이미지 속 시각과 수신 시각 차
- 트래커 내부 계측: `VIGENT_TRACK_DEBUG=1` 기동 → `data/track_debug.jsonl`(fresh·트랙 상태 프레임별)
