## 2. 지연 예산표 (실측)

| 구간 | p50 | 비고 |
|---|---|---|
| 카메라 인코딩→RTSP 도달 | **~1.35s** | 시계 촬영(§3). 영상·박스 공통 |
| 워커 캡처 큐(수정 전) | 성장형 +0.09s/s | grab-드레인 후 성장 0 |

| PPE 캐던스(수정 전) | 평균 +250ms | 고속화 후 배치율(~4.4회/초)로 해소 |
| 표시 스택 이동시작 관성(수정 전) | 283ms (p95 885) | 클램프 80ms 후 p50 0ms |
| 렌더 | ~8ms | 60fps rAF |

**중요한 구분 — 판정은 정합, 표시가 문제였다**: 안전 판정(PPE 미착용·침입 등)은 "분석한 그 프레임" 기준으로 계산되므로 프레임이 몇 초 과거든 **판정 자체는 옳다**(늦게 울릴 뿐). 오늘 잡은 문제들은 전부 **실시간 뷰(영상↔박스 정렬)의 표시 계층** 문제였고, 판정 캐던스·로직은 전 과정에서 불변으로 유지했다(규칙6). 카메라 1.4s는 "경보가 실제 상황보다 ~1.5+α초 늦게 울린다"로 남는다 — §3.

## 3. 카메라 자체 지연 ~1.4s — 판정 근거와 함의

- 우리 캡처 경로(OpenCV/FFmpeg): 시계 촬영 1.35~1.47s(grab-드레인·FFmpeg nobuffer 후에도 불변)
- go2rtc 경로(자체 Go RTSP 클라이언트, FFmpeg 무관)→WebRTC 브라우저: 사용자 동시 비교 ~1.4s
- **서로 다른 두 클라이언트가 같은 값 → 공통 구간인 카메라 내부(인코더·GOP 버퍼)로 확정**
- 함의: ①클라이언트 튜닝으로 더 못 줄인다 ②파일럿 안내에 "경보 시점은 실제보다 ~1.5+α초 후" 명시 ③즉각 반응 요구 기능(프레스 방호 등)엔 저지연 카메라 필수 — docs/camera_requirements.md 조항 신설 ④후속 실험 후보: stream2·GOP/해상도 하향·타 기종 — P3 백로그
- 측정법 표준화: "시계 촬영법"(밀리초 시계 화면을 카메라로 촬영 → 스냅샷 속 시각과 수신 시각 차, 전부 같은 PC 시계 기준) — 설치 실사 절차로 camera_requirements.md 에 수록

## 5. go2rtc 8555 전체 바인딩 — 보안 트레이드오프 (S2 일부 완화)

- 사유: Chrome은 ICE 후보에서 루프백 제외 → 127.0.0.1 단독으로는 같은 머신 브라우저조차 WebRTC 불성립(S3 스모크는 SDP 교환만 확인해 못 잡음)
- 완화 근거: 8555는 미디어 전용(세션별 ICE 자격증명+DTLS 필수), 시그널링(1984)은 계속 127.0.0.1 → 이 포트만으로 영상 추출 불가
- 배포 권장: 방화벽으로 8555를 관제 PC 고정 IP만 개방 — docs/edge_network_hardening.md §1·§1-1

## 6. 파일 카메라 vs 실카메라 — 이번에야 드러난 차이

1. **자격증명·계정 상태**: 파일 소스엔 없음. 리셋 시 카메라 계정 초기화 → DESCRIBE 401
2. **버퍼 누적**: 파일은 `is_stream=False`라 캡처 스레드 경로가 아예 안 탐 — thread 모드·grab-드레인은 실 RTSP에서 처음 검증. read() 단독은 디코드가 추론과 경합 시 지연 무한 성장
3. **카메라 내부 지연 ~1.4s**: 파일엔 0 — 표시 정합 문제의 뿌리
4. **WebRTC ICE**: S3 리허설(프로토콜 레벨)은 통과했지만 실브라우저 ICE는 바인딩 이슈로 실패
5. **트래커 파편화·유령**: 실보행(빠른 이동+작은 PPE 박스)에서야 재현
6. **동시 세션 한도**: 강제 종료 잔류 세션+재시도 폭주가 한도를 고갈(연대기 9) — 파일엔 없는 실카메라 고유 실패 모드

## 7. 미해결·설계 한계 / 백로그

- **카메라 자체 지연 ~1.4s**: 코드로 축소 불가 — 카메라 설정/기종 실험은 백로그
- **트랙 id 파편화**: PPE 20초 221트랙(계측) — 유령은 표시 경계에서 차단했으나 파편화 자체는 남음. ByteTrack(track.algo, 현재 person 한정 opt-in)의 PPE 확장·매칭 게이트 속도 확장 재조정은 백로그
- **go2rtc 재시도 백오프**: EOF 폭주(연대기 9) 재발 방지 설정/버전 검토 백로그
- **카메라 세션 슬롯 경합(연대기 9·12 공통 뿌리)**: 소비자용 카메라의 동시 RTSP 한도(추정 2)를
  go2rtc·워커가 나눠 쓰는 구조가 취약 — ①워커를 stream2(저해상, 검출 입력은 어차피 640 축소)로
  분리해 stream1(go2rtc/표시)과 슬롯·디코드 경합 동시 해소 ②go2rtc 좀비 세션 감시(유휴
  producer 의 ESTABLISHED 잔류 감지 시 재시작) ③hang 워치독과 캡처 백오프의 상호 간섭 정리
  (스트림 끊김 중엔 워치독 재기동 억제) — 3건 모두 백로그
- **focus_fps 기본값**: 5→8 실측(달성 7.33회/초, CPU +1.1%p/기계) — 채택 시 tuning.yaml `hub.focus_fps: 8`
- **자동 선택 시 WebRTC 미시작**: 타일 클릭 시에만 WebRTC 체인 시작(스냅샷으로 열림) — 개선 후보
- `fps_live` 명명(목표값인데 live 로 읽힘) — 달성률 별도 노출 검토

  조용히 죽는다 — 운영자는 이상을 알아챌 수 없다

### 최종 판정

실카메라 E2E 검증 — **연결·인증·검출·이벤트·표시·30분 안정성 통과. 단, 재연결 경합 P0
1건 발견으로 "완료" 선언은 보류**: 카메라 전원/네트워크 순단 후 go2rtc(표시)가 검출 워커를
세션 기아로 몰 수 있다. 파일럿 전 필수 수정(아래 P0). 이 건 해소 후 잔여는 엣지박스
실기종 실측뿐.

① 워커를 stream2 로 분리(+디코드 부하 절감 부수효과) ② 워커 기아 감지 시 go2rtc 세션
양보(재시작/일시 해제) 로직 ③ /health 에 "영상은 살았는데 검출이 죽음" 상태를 명시 노출
