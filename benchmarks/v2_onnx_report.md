# [V2] ONNX 동일 가중치 — GPU 없이 성립하는가 (2026-08-19 재측정)

> 목적: **가중치는 그대로 두고 실행기만** ONNX Runtime 으로 바꿔, GPU 없는 박스에서
> 카메라가 성립하는지를 **수치로** 판정한다. 가중치 교체·경량 모델 도입은 범위 밖이다.
>
> 원자료·스크립트: `benchmarks/e1_bottleneck/v2_*` · MANIFEST: `vigent-core/weights/MANIFEST.md`

> ### 측정 위생 (§7)
> 2026-08-18 1차 측정은 도중에 같은 PC 에서 게임(`TslGame.exe`, CPU 543%)이 실행돼 **폐기**했다.
> 이번엔 별도 프로세스 감시자(`meas_watchdog.py`)를 띄워 **측정과 동시에** 외부 고부하를
> 기록하고, 구간별로 대조했다. 결과는 §7.

## 0. 결론 3줄

1. **동일성은 확인됐다** — ppe **불일치율 0.00%**, fire_smoke **4.35%**(허용 내). forklift 는 **부결**.
2. ★**ONNX-CPU 는 지연이 2.2~2.3배 빠르지만 CPU 를 1.7~2.2배 더 쓴다.** 병목이 CPU 처리량인
   이 시스템에서는 **채택하면 손해**다 — "1.85배 빠르다"는 맞지만 **대수를 늘리지는 않는다**.
3. ★**GPU-less 는 성립한다** — **torch-CPU** 로, **i7-10700급(환산 7.06코어)** 이면
   **현행 기능 그대로**(3슬롯·2fps) GPU 없이 카메라 1대가 돌아간다(필요 **6.33 환산코어**).

### 2-1. 첫 시도의 조용한 실패 (기록)

첫 export 는 파일은 만들어졌으나 어댑터가 로드를 거부하고 **조용히 torch 로 폴백**했다.
원인은 `export()` 에 **`notes=` 를 안 넘겨 ONNX 메타데이터에 `class_names` 가 빠진 것**
([`rfdetr_adapter.py:82`](../vigent-core/detectors/rfdetr_adapter.py#L82)가 이를 요구).

★**위험한 이유**: 폴백이 조용해서(규칙6 설계상 의도된 동작) **"ONNX 를 켰다"고 믿는데 실제로는
torch 로 돌 수 있다.** 그래서 측정 스크립트가 매번 **실제 모델 클래스를 찍어 확인**한다(§3-1).

## 3. ★동일성 검증 — 채택 조건

`tests/test_rfdetr_onnx_parity.py` 의 판정 기준을 그대로 재사용하되, 단일 데모 이미지가 아니라
**실제 현장 프레임 24장**으로 돌렸다.

**기준**: 같은 라벨끼리 IoU ≥ 0.90 매칭 · 매칭분 bbox 최대오차 < **0.02** · 점수 오차 < **0.05**
· 프레임당 미매칭 ≤ **2**

| 슬롯 | 운용 임계 | torch / onnx 검출 | 매칭 | **불일치율** | **최대 bbox 오차** | **최대 점수차** | **판정** |
|---|---|---|---|---|---|---|---|
| **ppe** | 0.35 | 135 / 135 | 135 | **0.00%** | **0.0005** | **0.011** | ✅ **PASS** |
| **fire_smoke** | 0.30 | 11 / 12 | 11 | **4.35%** | **0.0019** | **0.002** | ✅ **PASS** |
| **forklift** | 0.002 | 33 / 31 | 25 | **21.88%** | **0.0491** | 0.001 | ❌ **부결** |

- ppe 는 **사실상 완전 동일**하다(135건 전부 매칭, 좌표 오차 0.0005).
- fire_smoke 의 불일치 1건은 **ONNX 쪽에만 뜬 검출 1개**다. 매칭분의 좌표·점수 오차는
  극히 작고(0.0019 / 0.002), 프레임당 미매칭이 기준(2개)을 넘은 프레임은 **없다**.

### 3-1. 배선 확인 (조용한 폴백으로 인한 무의미 측정 차단)

```
[onnx-cpu] person: RFDETRNano(torch) · ppe: _OnnxRfdetrModel · fire_smoke: _OnnxRfdetrModel · forklift: _OnnxRfdetrModel
[torch]    person: RFDETRNano       · ppe: RFDETRNano       · fire_smoke: RFDETRNano       · forklift: RFDETRNano
```

★**person 은 `onnx-cpu` 에서도 torch 다.** `rfdetr_adapter.py:147` 이
`Path(weights).with_suffix(".onnx")` 로 경로를 만드는데 person 슬롯은 `vision.yaml` 에
`rfdetr_weights.person` 항목이 없어(COCO 사전학습) **onnx 경로가 아예 생성되지 않는다.**
배선 변경은 하지 않았다 — 아래 모든 ONNX 수치의 전제다.

**이 전제가 좋은 대조군이 된다**: 1슬롯(person 단독)은 두 백엔드가 같은 코드로 돌므로
수치가 일치해야 한다 → 실측 **2.30 vs 2.29 코어**(§4-2). 측정 재현성이 확인된다.

### 3-2. forklift 부결 — 원인은 "모른다"

운용 임계 **0.002** 에서 최대 bbox 오차 0.0491 로 허용치(0.02)를 넘겼다.
진단으로 정상 임계(0.30)에서 재검했으나 **torch·onnx 모두 0건**이라 아무것도 알 수 없었다
— F-7 과소학습으로 이 모델의 최대 confidence 가 ~0.005 라 정상 임계에서는 검출이 없다.

**정직한 결론**: conf 0.002 라는 병적인 운용점에서 미세한 수치 차이가 검출을 대량으로
뒤집었을 **가능성**이 크지만, **모델이 너무 퇴화해 ONNX 변환 자체가 정상인지 확인할 방법이
없다**(규칙7 — 모른다). 억지 채택하지 않는다. forklift 는 **기본 비활성**이라 파일럿을 막지 않는다.

### 3-3. FP16 — ❌ **부결 확정 (미측정)**

| 항목 | 내용 |
|---|---|
| 경로 | RF-DETR `export()` 의 `quantization` 인자는 **`format="onnx"` 에서 무시**된다(TFLite 전용). fp16 ONNX 를 만들려면 `onnxconverter_common` **설치가 필요** |
| **결정** | **설치하지 않는다. 측정하지 않는다.** |
| 사유 ① | ONNX Runtime **CPU** EP 는 fp16 을 내부에서 fp32 로 환원하는 것으로 알려져 있어 **CPU 박스에서 이득이 없을 것으로 추정**(미검증 — 그래서 측정 대신 부결) |
| 사유 ② | GPU 쪽은 VRAM 이 **1.4GB**(V1 §3)뿐이라 fp16 으로 메모리를 줄일 **필요 자체가 없다** |

## 4. CPU 단독 실측 — 슬롯 구성 × fps × 실행기

`VIGENT_DETECT_DEVICE=cpu` 강제(GPU 있어도 안 씀), 카메라 1대 기준, 구간 40초.

### 4-1. 검출 지연 (1회 호출, p50)

| 구성 | ONNX(person만 torch) | torch 전부 | ONNX 이득 |
|---|---|---|---|
| 4슬롯 | **319.0ms** | 563.9ms | −43% |
| 3슬롯(현행) | **261.5ms** | 418.2ms | −37% |
| 2슬롯 | **202.8ms** | 286.0ms | −29% |
| 1슬롯(둘 다 torch) | 137.0ms | 139.2ms | ±1.6%(대조군) |

**슬롯당 한계 지연**: ONNX **60.7ms** vs torch **141.6ms** → ★**ONNX 가 2.33배 빠르다**
(2·3·4슬롯 구간에서 각각 2.23 / 2.24 / 2.33배 — 일관).

> ### "1.85배" 가정이 실측으로 대체됐다
> `benchmarks/onnx_cpu_bench.md` 의 **1.85배**(ppe 단일 슬롯 지연)는 **방향이 맞았고**,
> 이번 실측은 오히려 더 큰 **2.2~2.3배**를 보인다. **지연 관점에서 ONNX 는 확실히 빠르다.**

### 4-2. ★그러나 CPU 소모는 정반대다 — 카메라당 검출 코어

| 구성 | fps | **ONNX 코어** | **torch 코어** | 어느 쪽이 이득 |
|---|---|---|---|---|
| 4슬롯 | 2.0 | 8.73 | **3.95** | torch **2.21배** 효율 |
| 4슬롯 | 1.5 | 6.58 | **3.79** | torch 1.74배 |
| 4슬롯 | 1.0 | 4.39 | **2.80** | torch 1.57배 |
| **3슬롯(현행)** | **2.0** | 6.51 | **3.78** | torch **1.72배** |
| 3슬롯 | 1.5 | 4.91 | **3.35** | torch 1.47배 |
| 3슬롯 | 1.0 | 3.19 | **2.23** | torch 1.43배 |
| 2슬롯 | 2.0 | 4.24 | **3.40** | torch 1.25배 |
| 2슬롯 | 1.5 | 3.11 | **2.53** | torch 1.23배 |
| 2슬롯 | 1.0 | 2.10 | **1.70** | torch 1.24배 |
| 1슬롯 | 2.0 | 2.30 | 2.29 | **동일**(둘 다 torch — 대조군 ✅) |
| 1슬롯 | 1.5 | 1.72 | 1.70 | 동일 |
| 1슬롯 | 1.0 | 1.14 | 1.14 | **완전 동일** |

**왜 이런가**: ONNX Runtime CPU EP 가 훨씬 공격적으로 멀티스레딩한다. 3슬롯·2fps 기준
호출당 CPU 는 ONNX **3.26 코어초** vs torch **1.89 코어초** — 벽시계는 짧지만(261 vs 418ms)
**총 CPU 는 1.7배 더 쓴다.**

> ### 결정에 미치는 영향
> 이전 판단(`ops_capacity_sizing.md`)은 **지연** 기준이었다. 그러나 E1 에서 병목이
> **CPU 처리량**으로 확정됐으므로 대수를 결정하는 것은 지연이 아니라 **CPU 초**다.
> 그 기준에서 **ONNX-CPU 는 현재 설정 그대로는 채택하면 손해**다.
>
> ### ⚠ 단, 이 결론은 **뒤집힐 가능성이 크다**
> [V1 §5-2](v1_slot_config_report.md) 에서 **같은 패턴이 pose 에서 실증됐다**:
> ORT 세션에 `SessionOptions` 를 주지 않으면 스레드풀이 **스핀(busy-wait)** 하며
> CPU 를 태운다 — pose 는 세션 옵션만 바꿔 **CPU 0.82→0.09코어(−89%)** 가 됐다.
>
> 그리고 검출 ONNX 경로도 **똑같이 `SessionOptions` 없이** 세션을 만든다
> ([`rfdetr_adapter.py:70`](../vigent-core/detectors/rfdetr_adapter.py#L70)).
> "지연은 2.2~2.3배 빠른데 CPU 는 1.7~2.2배 더 쓴다"는 조합은 **스핀의 전형적 서명**이다.
> → **스핀을 끄고 재측정하면 ONNX 가 오히려 유리해질 수 있다. 측정하지 않았다(백로그).**

### 5-1. 판정

> ## ✅ **GPU-less 는 성립한다** (카메라 1대 기준)
>
> | CPU 급 | 환산코어 | GPU 없이 가능한 최대 구성 |
> |---|---|---|
> | **i7-10700급** | 7.06 | ✅ **현행 기능 그대로**(3슬롯·2fps, 필요 6.33) — 4슬롯도 가능(6.57) |
> | **i5-10400급** | 5.29 | 🔸 **fps 를 1.0 으로** 낮추면 3슬롯(4.11). 2fps 는 1슬롯까지(4.20) |
> | **i5-8500급** | 3.12 | 🔸 **person 단독·1fps** 만(2.56) |
> | **N100급** | 1.61 | ❌ **어떤 조합으로도 불가**(최소 요구 2.56) |

### 5-2. ★그러나 GPU 를 넣는 편이 압도적으로 싸다

GPU 경로의 같은 조건(3슬롯·2fps)은 카메라당 **2.03코어**(V3 실측) = 필요 **2.90 환산코어**다.
**GPU-less 는 6.33** 이므로 **2.2배의 CPU** 가 필요하다.

> **GPU 는 "성능 장치"가 아니라 "CPU 절약 장치"다.**
> GTX 1650급(중고 10~18만원)을 넣으면 CPU 를 **두 단계** 낮출 수 있다 —
> i7-10700급이 필요하던 것이 **i5-8500급으로** 내려간다(2.90 < 3.12).
> CPU 급을 올리는 비용이 GPU 값보다 크면 **GPU 를 넣는 것이 정답**이다(V4 §가격).

## 7. 측정 위생 — 감시 결과 (규칙7)

`meas_watchdog.py` 를 별도 프로세스로 띄워 5초 간격 237샘플을 수집하고, 측정 구간 30개와
대조했다. **게임 등 대형 부하는 없었다.** 다만 Windows 자체 프로세스가 산발적으로 잡혔다:

| 구간 | 감지된 외부 부하 | 지속 |
|---|---|---|
| onnx-cpu/p/2.0fps | `svchost.exe` 108~127% | 6샘플(≈30초) |
| torch/pp/1.0fps · torch/p/2.0fps | `svchost.exe` 107~126% | 각 4~5샘플 |
| V3 2.0fps N=4 | `MsMpEng.exe`(Defender) 132~208% | 6샘플(≈30초) |
| onnx-cpu/ppf/1.5fps·1.0fps | `taskhostw.exe` 85% · `MsMpEng.exe` 89% | 각 1샘플 |

**판정: 결과를 왜곡하지 않았다고 본다.** 근거는 **내부 일관성**이다.

- 24스레드 중 측정이 쓴 것은 2~9코어이고 코어 평균은 21~48% — **포화와 거리가 멀다**.
- fps 비례성이 유지된다: torch/2슬롯 코어 ÷ fps = 1.70 / 1.69 / 1.70 (2.0/1.5/1.0fps).
- 대조군 일치: 1슬롯에서 ONNX 2.30 vs torch 2.29 코어(같은 코드 경로).
- 교차 검증: V3 2fps 의 카메라당 1.38코어가 **V1 의 1.37코어**(다른 날, 게임 이전 측정)와 일치.

★그럼에도 **감지 사실 자체를 숨기지 않는다.** 원자료(`meas_watchdog.jsonl`)를 함께 커밋하니
누구든 재대조할 수 있다.
