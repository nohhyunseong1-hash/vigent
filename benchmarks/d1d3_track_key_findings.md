# [D1+D3] 트랙 단위 키 전환 — 재생 검증 결과 (2026-08-24)

> **지시**: "쿨다운과 백오프 억제 키에 트랙 ID를 넣어 사람 단위로 바꾼다. 단 **ID 스위치가
> 억제를 우회해 폭주하지 않는지 반드시 검토** — 실측 오탐 데이터로 재생 검증 포함."
>
> **결론 먼저**: 결정대로(쿨다운·백오프 **둘 다** 트랙 키) 구현하면 **추적 품질이 나쁠 때
> 알림이 66배**로 폭주한다. 다만 그 66배는 **운영에 쓰지 않는 트래커(iou)** 데이터에서 나온
> 값이다. 운영 트래커(bytetrack)에서는 짧은 표본에서 **1~3배**였고, **장시간 표본은 없다**.

---

## 0. 먼저 — 문제가 PILOT_DECISIONS 에 적은 것보다 크다

[docs/PILOT_DECISIONS.md](../docs/PILOT_DECISIONS.md) D1 에 "13초 뒤 B가 들어오면 쿨다운에
막힌다"고 적었는데, 코드를 더 읽어보니 **그보다 심각**하다.

[worker.py:190-209](../vigent-core/worker.py#L190) 의 구역 판정은 이렇다:

```python
raw_inside = False
for d in detections:            # 사람을 하나 찾으면 곧바로 break
    if _point_in_poly(...): raw_inside = True; break
...
now_in = debouncer.update(cid, raw_inside)      # ★키가 '카메라'다
if now_in and not was:                          # 확정 '전이'에서만 발화
```

`raw_inside` 는 **카메라 단위 집계 불리언**이고 디바운서 키도 **카메라**다. 따라서:

> **A가 구역 안에 서 있는 동안 B가 들어오면 상태가 안 바뀌므로 아예 발화하지 않는다.**
> 15초 쿨다운의 문제가 아니라, **A가 나갈 때까지 무기한** 가려진다.

D1 의 근거는 더 강해졌다. 다만 해법의 부작용도 함께 커진다.

## 1. 재생 검증 — 같은 데이터를 두 방식으로

**데이터**: `data/track_debug.jsonl` — **실카메라 8.7분**, person 트랙 기록(프레임별 tid·bbox).
구역은 실제 사람 동선(x 0.20~0.40 · 하단)에 맞춰 설정했다.
★**이 기록은 `iou` 트래커로 남긴 것**이다(tid 최대 347 — bytetrack 이면 1천만 이상).

| 방식 | 발화 | 폰 알림 |
|---|---|---|
| **A) 현행** — 카메라 디바운스 · 규칙 쿨다운 | 3 | **1** |
| **B) 결정대로** — 쿨다운·백오프 **둘 다** 트랙 키 | 67 | **66** |
| **C) 완화1** — 쿨다운만 트랙, **백오프는 카메라** | 67 | **1** |
| **D) 완화2** — C + 트랙 `hits≥3` 필터 | 63 | 1 |
| **E) 완화3** — C + 트랙 `hits≥5` 필터 | 59 | 1 |

**왜 B가 폭주하는가**: 최대 2명이 있던 8.7분 동안 person 트랙 ID가 **68개** 생겼다.
새 ID = 새 디바운스 상태 + 새 쿨다운 + **새 백오프 상태**다. 즉 alert_gate 의
적응형 백오프(300초→3600초)가 **통째로 무력화**된다 — 폭주를 막으라고 만든 장치인데
키에 트랙을 넣는 순간 매번 초기 상태에서 시작한다.

**단명 트랙 필터(D·E)는 효과가 작다** — 63·59로 거의 안 줄었다. ID 스위치가 "짧게 나타났다
사라지는 유령"이 아니라 **같은 사람이 계속 새 번호를 받는** 형태이기 때문이다.

## 2. ★자기정정 — 66배는 운영 트래커의 수치가 아니다

위 데이터는 `iou` 트래커 기록인데, **운영 설정은 이미 `bytetrack`** 이다
(`config/tuning.yaml` → `track.algo: bytetrack`, 코드에서 실제 적용 확인).

같은 영상(45초)에 두 트래커를 돌린 실측:

| 트래커 | person 고유 ID |
|---|---|
| iou | **25개** |
| bytetrack (운영) | **8개** |

**3배 차이**다. 그래서 66배를 그대로 인용하면 과장이다.

**bytetrack 로 돌린 짧은 표본**(영상 7개, 10~45초, `benchmarks/d1d3_track_key_replay.py`):

| 영상 | 고유 tid | A 알림 | B 알림 | 배수 |
|---|---|---|---|---|
| footage 190652986 | 8 | 1 | 3 | 3.0배 |
| accident 000438282 | 8 | 1 | 2 | 2.0배 |
| accident 000442974 | 3 | 1 | 2 | 2.0배 |
| accident 000552920 | 5 | 1 | 1 | 1.0배 |
| accident 000601541 | 1 | 1 | 1 | 1.0배 |
| accident 000611749 | 4 | 1 | 2 | 2.0배 |
| accident 000632301 | 6 | 1 | 3 | 3.0배 |

**중앙값 2배.** 파국은 아니다.

## 3. ★모르는 것 (규칙7)

- **장시간(수 시간) bytetrack 표본이 없다.** 위 표본은 전부 10~45초다. 백오프는 300초부터
  작동하므로 **이 표본들은 백오프 무력화를 측정조차 하지 못했다.**
- 8.7분짜리 유일한 장시간 표본은 iou 기록이라 운영과 다르다.
- 학원 현장의 추적 난이도(조명·가림·지게차 뒤 통과)는 **아직 모른다.**

즉 **"운영 트래커로 몇 시간 돌렸을 때 폭주하는가"는 측정되지 않았다.** 66배는 상한,
2배는 하한으로 보는 것이 정직하다.

## 4. 제안

| | 범위 | 근거 |
|---|---|---|
| **방문 전** | **하지 않는다** | 장시간 bytetrack 측정이 없다. 하필 **폭주 방지 장치가 무력화되는** 변경이라, 시연 중 폭주하면 되돌릴 시간이 없다 |
| **방문 중** | `track_debug` 를 **bytetrack 로 켜서 현장 데이터 수집** | 학원 실제 난이도에서 ID 스위치율을 잰다 — 그 수치가 결정 근거다 |
| **방문 후** | 측정값 기준으로 B 또는 C 선택 | 분당 신규 ID 가 낮으면 B(결정대로), 높으면 C(백오프는 카메라 유지) |

**C를 미리 권하는 이유**: C는 **기록은 사람 단위로 남기고**(미검출 해소 — 67건 전부 기록)
**알림만 카메라 단위 백오프로 묶는다**(폭주 방지 유지). 두 목적이 충돌할 때
"놓치면 사고"는 기록으로 막고 "꺼버리는 오탐"은 알림으로 막는 절충이다.
다만 이러면 **두 번째 사람의 폰 알림은 여전히 늦을 수 있어**, 결정 취지의 절반만 달성한다.

★**결정권자 판단이 필요한 지점**: B(취지 100% · 폭주 위험)와 C(취지 50% · 안전) 중 어디로 갈지.
현재 측정으로는 **어느 쪽도 확정 근거가 부족**하므로, 현장 데이터를 먼저 받는 것을 권한다.
