# [W1·W2] 경보 통보 배선 + 폭주 방지 + 근접 디바운스 (2026-08-20)

> 배경: [M1](m1_alert_latency.md) 에서 **카메라 검출 경로에 알림 전송 배선이 없다**는 것이,
> [M3](m3_alert_rate_2026-08-20.md) 에서 **정지한 오검출 1개가 24시간에 무동작 경보 221건을
> 낳는다**는 것이 각각 실측으로 확인됐다. 배선만 하면 켜는 순간 경보 폭탄이 되므로
> **배선과 억제를 한 커밋으로** 처리한다.
>
> 신규: `vigent-core/alert_gate.py`(순수 정책) · `vigent-core/alert_notify.py`(비동기 전송)
> 테스트: `tests/test_alert_wiring.py` **29건**

---

## 1. W1 — 워커 → 알림 전송 배선

### 1-1. 무엇을 바꿨나 (최소 변경)

| 위치 | 변경 |
|---|---|
| `worker.py` `_process_frame` | 기존 `data_engine.log_event(...)` **바로 다음**에 `alert_notify.submit(...)` 1회 추가 |
| `main.py` 예열 배선 | `alert_notify.set_sender(dispatcher.dispatch)` + `alert_notify.start()` |
| 신규 `alert_notify.py` | 큐 + 전용 스레드(비동기 전송) |
| 신규 `alert_gate.py` | 통보 여부 정책(폭주 방지) |

기존 판정·기록·증거 경로는 **한 줄도 바꾸지 않았다.**

### 1-2. ★비동기여야 하는 이유 (규칙6: 저하 금지)

`dispatcher._dispatch_now()` 는 텔레그램·이메일·웹훅을 **동기 호출**하고 타임아웃이 6~8초다.
이것을 워커 루프에서 직접 부르면 **채널 하나가 느려질 때 검출이 수 초간 멈춘다** —
안전 기능이 알림 때문에 죽는 최악의 구조다.

그래서 워커는 **큐에 넣기만** 하고 전용 스레드가 전송한다. 테스트로 고정했다:

| 검증 | 결과 |
|---|---|
| 전송기가 2초 걸려도 `submit()` 소요 | **< 0.25초** (테스트 임계) — 검출 캐던스 무영향 |
| 전송기가 예외를 던져도 | `submit()` 정상 반환 · **전송 스레드 생존** · 다음 경보 정상 접수 |
| 게이트 자체가 고장나도 | `submit()` 이 예외를 삼키고 `reason="exception"` 반환 |
| 통보가 폭발해도 | 프레임 처리 루프 유지(워커 상태 정상) |

### 1-3. 기존 내구 큐 경로를 그대로 탄다

전송 스레드가 부르는 것은 `dispatcher.dispatch()` 이고, 그 안에서 [B5] **선기록(write-ahead)
→ 즉시 전송 → 성공/실패 표시**가 이뤄진다. 실패하면 재시도 스레드가 지수 백오프로 이어받고,
최대 시도를 넘기면 데드레터로 간다. **경보는 유실되지 않는다.**

### 1-4. 순서 계약 — 기록이 먼저다

`log_event()` → `alert_notify.submit()` 순서를 테스트로 고정했다.
전송이 실패해도 **증거·이벤트는 반드시 남는다.**

## 2. W1 — 경보 폭주 방지 (★설계 중 결함을 실측이 잡아냈다)

### 2-1. 처음 설계는 틀렸다

처음엔 **고정 쿨다운 300초 + 시간당 상한 10건**으로 설계했다. [M3] 실측 데이터로 재현해 보니
**아무것도 막지 못했다**:

- 무동작 오경보 221건/24시간 = **평균 391초 간격**
- 391초 > 300초 → 쿨다운을 **그대로 통과**
- 시간당 9.2건 < 10건 → 상한에도 **안 걸림**
- **결과: 221건이 전부 통보된다** — 배선하는 순간 경보 폭탄

이 사실은 테스트(`test_m3_scenario_221_events_become_bounded`)가 실패하면서 드러났다.
실측 데이터를 테스트에 넣지 않았다면 그대로 배포됐을 설계다.

### 2-2. 고친 정책 — 적응형 백오프

| # | 정책 | 기본값 |
|---|---|---|
| 1 | 반복 억제 쿨다운(시작값) | 300초 |
| 2 | ★**적응형 백오프** — 통보할 때마다 쿨다운 ×2 | 배수 2.0 · 상한 3,600초 |
| 3 | 조용해지면 백오프 리셋 | 1,800초 무발화 시 |
| 4 | 시간당 상한(최종 방어선) | 6건 / 카메라·규칙 |
| 5 | **등급 상승 예외**(high→critical) | 쿨다운 무시(상한은 유지) |
| 6 | **억제 요약** — 억제 건수를 다음 통보에 실음 | — |

백오프가 상한에 도달하면 같은 원인은 **시간당 1건**으로 수렴한다.
완전 침묵이 아니다 — **카메라가 계속 이상하다는 사실 자체는 알아야 하기 때문**이다.

### 2-3. 실측 데이터로 검증한 효과

[M3] 의 실제 발생 패턴을 그대로 재생해 측정했다.

| 시나리오 | 발화 | 통보 | 억제율 |
|---|---:|---:|---:|
| 무동작 오경보(24h, 391초 간격) — **고정 쿨다운(구 설계)** | 221 | **221** | **0.0%** |
| 무동작 오경보(24h) — **백오프(채택)** | 221 | **24** | **89.1%** |
| 화재/연기 오경보(24h, 74건) — 백오프 | 74 | 20 | 73.0% |
| ★**정상 현장 실제 경보**(하루 4건, 수 시간 간격) | 4 | **4** | **0.0%** |

> ### ★마지막 줄이 이 설계의 핵심이다
> 억제를 세게 걸면 오경보는 줄지만 **진짜 위험을 놓친다** — 그러면 안전 제품이 아니다.
> 수 시간 간격으로 오는 실제 경보는 **하나도 억제되지 않는다**는 것을 테스트로 고정했다
> (`test_real_site_alerts_are_not_suppressed`).

### 2-4. ★기록은 절대 억제하지 않는다

게이트는 **통보만** 거른다. 증거 프레임과 이벤트 로그는 기존 경로 그대로 **전부** 남는다.

- 사후 조사에 필요하고,
- [M3] §4 의 파일럿 오탐률 측정이 **이벤트 전건**을 분모로 쓰기 때문이다.

"안 보낸 것"과 "없던 일"은 다르다.

## 3. W2 — 근접(협착) 디바운스

### 3-1. 왜 필요한가

침입(zone_intrusion)은 [B6] 에서 1.0초 시간 디바운스를 넣었는데 **근접은 빠져 있었다** —
검출된 그 프레임에 즉시 발화하므로 **단일 프레임 오검출이 곧 경보**다. [M2] 에서 정지 물체가
person 으로 conf 0.36~0.67 에 잡히는 것이 실측된 이상, 이 경로도 막아야 한다.

### 3-2. ★시간상수를 침입보다 짧게 둔 근거

**침입과 같은 1.0초를 쓰면 안 된다.** 근접은 *이동체 사이의 거리*라 상황 전개가 훨씬 빠르다.

| 계산 | 값 |
|---|---|
| 위험반경(`proximity.radius_m`) | **3.0 m** |
| 지게차 구내 서행 속도(일반적 기준) | 10 km/h = **2.78 m/s** |
| **반경 3m 를 통과하는 시간** | **약 1.08초** |

즉 **1.0초를 기다리면 경고가 성립하기 전에 상황이 끝난다.** 보행 속도(1.4 m/s)로 접근해도
2.1초뿐이라 여유가 크지 않다.

**채택값 `enter_s: 0.4초`** — 검출 주기 0.5초([M1] 실측)에서 **연속 2회 검출**을 요구한다.
이는 단일 프레임 오검출만 걸러내는 **최소한의 디바운스**이며, 추가 지연은 약 0.5초다.

| | 침입(zone) | **근접(proximity)** |
|---|---|---|
| 진입 확정 `enter_s` | 1.0초 | **0.4초** |
| 해제 확정 `exit_s` | 1.0초 | **1.0초** |
| 필요한 연속 검출(주기 0.5초) | 3회 | **2회** |

★**해제(1.0초)를 진입(0.4초)보다 길게 둔 비대칭**은 의도다 — 경계에서 깜빡일 때 경보가
성급히 풀리면 안 되므로 **안전 쪽으로 치우쳐** 둔다.

### 3-3. 지연 영향 ([M1] 표 갱신)

| 경보 | W2 이전 | **W2 이후(예상)** |
|---|---|---|
| 근접 — 최선 | 0.20초 | **0.70초** |
| 근접 — 중앙 | 0.45초 | **0.95초** |
| 근접 — 최악(이론) | 0.76초 | **1.26초** |

⚠**이 표는 계산값이다**(추가 0.5초 = 연속 2회 검출 요구분). 재측정하지 않았다 —
서비스 재시작 후 `m1_alert_latency.py` 재실행이 필요하다(§5).

### 3-4. 발화 방식도 침입과 통일했다

**확정 진입 전이에서만 1회 발화**한다(체류 중 재발화 없음) — `zone_intrusion` 과 같은 방식이다.
이전에는 매 프레임 발화하고 15초 쿨다운이 걸렀다.

⚠**동작 변화 고지(규칙6)**: 근접이 지속되는 동안의 **반복 기록이 사라진다.** 체류 타임라인을
증거로 남기던 부분이라 정보가 줄어드는 방향이다. 침입과의 일관성·폭주 억제를 우선해 채택했고,
**롤백 경로**(`proximity.enter_s: 0`)로 구 동작을 즉시 복원할 수 있다.

## 4. 롤백 경로 (모두 설정 한 줄)

| 되돌릴 대상 | 설정 | 결과 |
|---|---|---|
| 통보 배선 전체 | `alerts.notify: false` (또는 `VIGENT_ALERT_NOTIFY=0`) | 구 동작 — 기록·증거만, 알림 없음 |
| 백오프만 끄기 | `alerts.backoff_factor: 1.0` | 고정 쿨다운으로 복귀 |
| 억제 완화 | `alerts.notify_cooldown_s` · `max_per_hour` 조정 | — |
| 근접 디바운스 | `proximity.enter_s: 0` | 구 동작 — 매 프레임 즉시 발화 |

### ★학원 방문 전 반드시 할 것

1. **서비스 재시작** — 코드는 재시작해야 반영된다. 재시작 후 로그에
   `경보 통보 스레드 시작` 이 뜨는지 확인.
2. **알림 채널 설정**(텔레그램 토큰 또는 웹훅 URL) — 채널이 없으면 배선해도 갈 곳이 없다.
   설정 후 실제 도달을 1회 확인.
3. `m1_alert_latency.py` 재실행 — 근접 지연 실측값 갱신.
