# [M1] 엔드투엔드 경보 지연 실측 (2026-08-20)

> 목적: "위험 발생 → 경보 도달"까지 총 몇 초인가. 안전 제품의 핵심 지표인데 미측정이었다.
>
> 도구: `benchmarks/m1_alert_latency.py` · 원자료: `benchmarks/m1_alert_latency_result.json`
> 재현: `python benchmarks/m1_alert_latency.py --samples 60`
>
> 측정 조건: 실서비스(NSSM) 가동 중 · 실카메라 1대 · 3슬롯 2fps · GPU 있음.
> **라이브 단계는 `/health` 읽기만** 해서 실카메라를 건드리지 않았고, 기록·전송 단계는
> **임시 폴더·임시 DB로 격리**해 운영 데이터(`data/evidence`·`alert_queue.db`)를 오염시키지 않았다.

## 0. 결론 — 먼저 알아야 할 것 두 가지

> ### 🔴 ① 카메라 검출 경로에는 **경보 전송 단계가 배선돼 있지 않다.**
>
> 워커는 위험을 판정하면 `data_engine.log_event()` 로 **증거 저장과 이벤트 기록만** 한다.
> `dispatcher.dispatch()`(텔레그램·이메일·웹훅) 호출부는 저장소 전체에서 **API·브라우저
> 경로에만** 있다(`routers/zone.py`·`routers/safety_core.py`·`agents/dispatcher.py` 내부).
> **`vigent-core/worker.py` 에는 dispatch 호출이 0건**이다.
>
> 즉 지금 카메라가 스스로 감지한 위험은 **아무에게도 통보되지 않는다** — 화면과 디스크에만 남는다.
> 24시간 소크에서 `alerts.sent` 가 끝까지 **0** 이었던 것이 이 사실과 정합한다.
>
> **→ 아래 §2 의 총 지연은 "위험 발생 → 증거·기록 완료"까지다.** 전송 구간은 §3 에서
> 따로 쟀고, 두 구간을 잇는 배선은 **없다**. 이것은 파일럿 전 필수 조치다(§6).

> ### 🟠 ② 근접 경보(proximity)에는 디바운스가 없다.
>
> 위험구역 침입은 [B6] 에서 시간 디바운스(1.0초)를 넣었지만, `proximity_hazard` 는
> **검출된 그 프레임에 즉시 발화**한다(`worker.py:173-176`). 지연은 짧지만
> **단일 프레임 오검출이 곧 경보**다 — B6 이전의 침입 경보와 같은 상태다.

## 2. 총 지연 — 위험구역 침입 (zone_intrusion)

**현재 배선 기준: "위험 발생 → 증거·기록 완료"까지.**

| 구간 | 최선 | 중앙(대표값) | 최악(실측) |
|---|---|---|---|
| 판정 확정(캡처 위상 + 디바운스 포함) | 1,000.0ms | 1,247.5ms | 1,497.5ms |
| 증거 인코딩 | 70.4 | 70.4 | 94.2 |
| 로그·디스크 기록 | 4.8 | 4.8 | 6.6 |
| **합계(기록까지)** | **≈1.08초** | **≈1.32초** | **≈1.60초** |
| *(참고) 전송을 배선했을 때 +* | +13.4 | +13.4 | +15.8 |
| ***가정 총계(전송 포함)*** | ***≈1.09초*** | ***≈1.34초*** | ***≈1.61초*** |

> ★**S1(프레임 신선도 300~600ms)은 위 합계에 더하지 않았다.** S3 스윕이 "위험 발생 →
> 확정" 을 재는데, 그 기준시각이 **검출 완료 시각**이라 캡처·추론 대기가 이미 안에 들어 있다.
> 다만 서버가 가진 프레임 자체가 최대 600ms 낡을 수 있으므로, **실제 물리적 위험 발생
> 시점 기준으로는 위 값에 최대 0.6초가 더 붙을 수 있다**(중복 계산을 피하려 별도 표기).
>
> ★**카메라 내부 지연(노출·인코딩·RTSP 전송)은 측정하지 않았다** — 서버 도착 이후만 쟀다.
> 눈-화면 전체 지연 측정 절차는 `docs/glass_to_glass_measurement.md` 에 있으나 사람이 필요해 미실시.

### 안전 관점 해석

침입 확정에 **1.0~1.5초**가 걸리는 것은 **의도된 설계**다 — 단일 프레임 오검출을 막는
디바운스(`zone.enter_s: 1.0`)가 지연의 **약 75%**를 차지한다. 이 값은 트레이드오프의
손잡이이며 `config/tuning.yaml` 에서 조정 가능하다.

| enter_s | 총 지연(중앙, 추정) | 대가 |
|---|---|---|
| 0.5초 | ≈0.82초 | 단일 프레임 오검출 통과 위험↑ |
| **1.0초(현행)** | **≈1.32초** | 균형 |
| 2.0초 | ≈2.32초 | 오경보↓, 짧은 침입 놓칠 위험↑ |

## 3. 총 지연 — 근접 경보 (proximity_hazard)

디바운스가 **없어서** 판정 구간이 0이다.

| 구간 | 최선 | 중앙 | 최악(실측) |
|---|---|---|---|
| 캡처 위상(다음 검출 사이클 대기) | 0ms | 250ms | 500ms |
| 검출(추론) | 126.5 | 126.5 | 141.4 |
| 판정 | **0**(즉시) | 0 | 0 |
| 증거 인코딩 + 기록 | 75.2 | 75.2 | 100.8 |
| **합계(기록까지)** | **≈0.20초** | **≈0.45초** | **≈0.74초** |
| *(참고) 전송 배선 시* | +13.4 | +13.4 | +15.8 |

**이론 최악** = 검출주기(0.5) + 추론 p95(0.141) + 기록 p95(0.101) + 전송 p95(0.016)
= **0.758초**. 실측 합계와 일치한다.

★**빠른 것이 무조건 좋은 게 아니다.** 근접 경보가 침입 경보보다 3배 빠른 이유는 성능이
아니라 **안전장치(디바운스)가 없기 때문**이다. 학원 실측에서 근접 판정은 운전자 제외 적용
후에도 38.1% 프레임에서 발화했는데, 디바운스가 없으면 그중 단발성 오검출이 그대로 경보가 된다.

## 4. 실채널 전송 시간 — ★텔레그램 실측 완료 (2026-08-21)

§1 의 S5' 13.4ms 는 **localhost mock 웹훅** 기준이었다. 실채널을 붙여 재보니
**100배 이상 느리다.**

| 채널 | 상태 | 실측 |
|---|---|---|
| 웹훅(mock, localhost) | ✅ | p50 **13.4ms** · delivered 12/12 |
| **텔레그램(실채널)** | ✅ **실측** | **p50 1,415.8ms** · 평균 1,414.5 · p95 1,475.3 · 범위 1,349~1,475 · **도달 10/10** |
| 이메일(SMTP) | ⛔ 미측정 | 계정 미설정 |
| 실 웹훅(외부망) | ⛔ 미측정 | 인터넷 왕복·상대 서버 응답에 좌우 |

> 측정: `POST /alerts/test` 10회(실제 배포 경로 — dispatcher → 텔레그램 API), 1.2초 간격.
> 원자료 `benchmarks/m1_telegram_result.json`. 전부 `telegram_status: 200`.

### ★이 1.4초가 검출을 늦추지는 않는다

[W1] 배선이 **비동기**라 워커는 큐에 넣고 즉시 다음 프레임으로 간다 — 텔레그램이 1.4초를
쓰든 10초를 쓰든 **검출 캐던스는 영향받지 않는다**(테스트로 고정: 2초 지연 전송기에서도
`submit()` < 0.25초). 1.4초는 **"위험 발생 → 담당자 폰 도착"** 에만 더해진다.

### 갱신된 총 지연 — 폰 도착까지

| 경보 종류 | 증거·기록 완료 | **+ 텔레그램 도착** |
|---|---|---|
| 위험구역 침입(중앙) | 1.32초 | **약 2.74초** |
| 위험구역 침입(최악 실측) | 1.60초 | 약 3.08초 |
| 근접(협착) — W2 이전 | 0.45초 | 약 1.87초 |

⚠근접은 [W2] 디바운스 도입으로 값이 바뀐다 — 재시작 후 재측정 필요(§6).

**전송 실패 시 거동은 배선돼 있다**(측정 아님, 코드 확인): 선기록 후전송 →
실패 시 지수 백오프 재시도(1·2·4…최대 60초, 최대 10회) → 초과 시 데드레터.
즉 **최악의 경보 도달 시간은 재시도 정책이 지배**하며, 순단 시 수 분까지 늘어날 수 있다.

## 5. 한계 (규칙7)

| 항목 | 내용 |
|---|---|
| **전송 배선 없음** | 카메라 경로의 총 지연에 전송이 포함되지 않는다. §2 의 "전송 포함" 행은 **가정치**다 |
| 카메라 내부 지연 | 노출·인코딩·RTSP 전송 미측정. 서버 도착 이후만 쟀다 |

| 단일 카메라·저부하 | 카메라가 늘면 추론·락 대기가 커진다(8대에서 실카 p95 255ms — `capacity_report.md`). **다중 카메라 지연은 미측정** |
| 판정 구간은 가상시계 | 상태기계는 실제 코드지만 시각을 주입해 구동했다. 실시간 구동 시 스케줄링 지터는 반영 안 됨 |
| 기록 구간 | 임시 폴더(로컬 SSD) 기준. 현장 저장장치가 느리면 커진다 |
| 1회 측정 | 반복 측정으로 분산을 보지 않았다(라이브 폴링 n=60, 나머지 n=12) |
