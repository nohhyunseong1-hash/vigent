## B2 가 P0 지문을 실제로 잡았다

2회차 t=110.8~116.8 구간이 교과서적이다:

```
t=110.8  HTTP503  cam=stale_detect  frame=1.6   detect=52.3
t=112.8  HTTP503  cam=stale_detect  frame=3.7   detect=54.3
t=116.8  HTTP503  cam=stale_detect  frame=3.6   detect=58.3
t=118.9  HTTP200  cam=ok            frame=0.2   detect=0.0
```

**프레임은 살아 돌아왔는데(frame 1.6~3.7) 검출만 죽어 있는** 상태가 6초간 이어졌고,
`/health` 가 그 동안 정확히 `stale_detect` + HTTP 503 을 반환했다. 이것이 P0 의 지문이며,
B2 이전에는 이 구간이 **200 OK 로 보였다**.

3회차는 같은 상태가 **49.6초** 지속됐다 — 수정 전이라면 영구화됐을 구간이다.

## 회차별 편차(6.0 / 8.1 / 49.6초)에 대해

3회차가 유독 오래 걸린 이유는 **측정으로 확정하지 못했다**(규칙7). 관측된 사실만 적으면:

- 3회차 기록에 `stale_frame` ↔ `stale_detect` 전환이 반복된다(t=149.2 stale_frame →
  t=158.6 stale_detect → t=200.1 stale_frame → t=204.1 stale_detect). 카메라가 프레임을
  주다 말다 하는 **불안정한 부팅 구간**이 길었다는 뜻이다.
- 같은 구간에서 `hangs` 카운터가 17→20 으로 증가했다 — 워커가 hang 판정·재시작을 3회 반복했다.
- 기아 2차 방어(1단계 60초)는 **발동하지 않았다**(로그에 발동 기록 없음). 즉 3회 모두
  **1차 방어(백오프 상한 5초)만으로 복구**됐고, 2차 방어는 이번 시험에서 검증되지 않았다.

★따라서 이 시험이 검증한 것은 **1차 방어**다. 2차 방어(슬롯 회수·워커 재시작·프로세스 승격)는
단위 테스트(`tests/test_starvation_guard.py` 9종)로만 검증됐고 **실환경 발동 실적이 없다**.

## 부수 관측

- 서버 무응답(HTTP 0) 샘플이 회차당 1~2회 있었다(t=51.1, t=13.5, t=172.6). 기록기 타임아웃
  8초를 넘긴 경우로, 예열·재시작과 겹친 구간이다. **원인 미확인** — 운영 영향은 확인되지 않았다.
- 카메라 IP 는 3회 모두 `192.168.0.4` 를 유지했다. 단 **이전 전원차단에서는 IP 가 바뀐 적이
  있다**(.4 → .5 → .4). 현장에서는 카메라에 **고정 IP(DHCP 예약)** 를 주는 것이 필수다 —
  IP 가 바뀌면 이 자동복구가 성립하지 않는다(등록 주소로 계속 접속 시도).

## 4회차 — 원 사고 조건 재현 (2026-08-17 추가)

1~3회차는 확대뷰가 닫힌 상태였다. 원 사고(2026-08-13, 7분 검출 사망)는 **확대뷰가 열려
카메라 슬롯 여유가 0** 인 상태였으므로, 그 조건을 그대로 재현해 4회차를 수행했다.

**조건 재현**: go2rtc 소비자를 코드로 붙여(`scratchpad/b3_r4_spotlight.py`) 유지하고
— 끊기면 즉시 재연결하도록 해 "확대뷰가 계속 열려 있는" 상태를 강제 — 전원을 차단했다.
차단 직전 카메라 세션 **2/2 소진** 확인.

**슬롯 경쟁이 실제로 일어났다**(세션 수 추이):
```
t= 61.0  sess=0   ← 전원 차단, 양쪽 다 끊김
t=113.8  sess=1   ← 카메라 복귀, 한쪽이 먼저 슬롯 확보
t=115.8  sess=2   ← 나머지 한쪽도 확보(한도 소진)
t=117.8  frame 19.1→1.9  ← 워커가 프레임을 다시 받기 시작
t=126.0  cam=ok  detect 0.3  ← 검출 복구
```

**결과: 프레임 복귀 후 8.2초 만에 검출 복구 — PASS.** 수정 전 같은 조건에서는 워커가
영구히 밀려 7분간 검출이 죽었고 go2rtc 를 수동 종료해야 했다. 백오프 상한 축소(30→5초)가
슬롯 경쟁에서 워커를 되살린다는 것이 **원 사고 조건에서 직접 확인**됐다.
