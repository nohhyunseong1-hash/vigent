# [B3] 재연결 세션 선점 기아 — 원인 분석 (2026-08-16)

> 지시: "원인 모르고 고치지 마라." 아래는 **추측이 아니라 이 머신에서 실제로 측정한 값**이다.
> 측정 대상: Tapo 실카메라(192.168.0.4, stream1) · go2rtc v1.9.14 · 워커 thread 캡처 모드.

## 1. 측정한 사실

| # | 측정 | 결과 | 방법 |
|---|---|---|---|
| M1 | **카메라 동시 RTSP 세션 한도** | **정확히 2** | 같은 URL 로 세션을 1개씩 늘려 열며 첫 프레임 성공 여부 확인. 1·2번 성공, **3번은 open 자체가 실패(0.3s)** |
| M2 | go2rtc 온디맨드 여부 | **온디맨드 맞음** | 스트림 등록 직후 소비자 0 → 카메라 세션 **0** |
| M3 | go2rtc 세션 해제 속도 | **2초 이내** | 소비자 연결 시 세션 1 → 소비자 종료 후 2·5·10·20·30초 전부 **세션 0** |
| M4 | 워커 세션 점유 | 실행 중 **상시 1** | worker._StreamCapture 가 카메라에 직접 접속 |
| M5 | 워커 재연결 백오프 | 1→2→4→8→16→**30초 상한** | `_RECONNECT_MAX=30`(worker.py:42), 지수 증가 |

## 2. 원인 (M1~M5 로부터)

**여유 슬롯이 0이다.**

```
카메라 한도 2
  ├─ 워커        1  (상시 점유 — 검출이 살아 있는 한)
  └─ go2rtc      1  (확대뷰가 열려 있을 때만)
                ───
                 2  = 한도 소진, 여유 0
```

확대뷰를 연 상태는 **정상 운영 상태**인데, 그때 이미 한도가 꽉 찬다. 여유가 0이면 카메라가
슬롯을 하나라도 늦게 내주는 순간(부팅 중, 이전 세션 정리 지연) **둘 중 하나는 반드시 실패**한다.

여기에 **재시도 공격성의 비대칭**이 겹친다:
- 워커: 지수 백오프로 **최대 30초씩 쉰다**(M5). 쉬는 동안 슬롯을 잡으러 가지 않는다.
- go2rtc: 실패 시 초당 여러 번 재시도(2026-08-12 로그 실측: EOF 경고가 **초당 ~10회**).

→ 카메라가 슬롯을 여는 순간 **거의 항상 go2rtc 가 먼저 잡는다.** 워커는 백오프 중이라 늦고,
다음 시도 때는 이미 슬롯이 없어 또 실패하고, 백오프는 더 길어진다. **한 번 밀리면 영구히 밀린다.**

이것이 2026-08-13 실측에서 **7분간 검출 사망**(워커 재시작 45회)으로 나타난 기전이다.
그때 go2rtc 를 종료해 슬롯을 비우자 워커가 **10초 만에 복구**된 것도 이 설명과 일치한다.

## 3. 왜 "영상은 살고 검출만 죽는" 형태가 되나

슬롯 경쟁에서 이긴 쪽이 go2rtc(=화면 영상)이기 때문이다. 운영자 화면은 정상으로 보이고,
안전 검출만 사라진다. **최악의 고장 모드**다 — 아무도 이상을 못 느낀다.
(B2 에서 `/health` 가 `stale_detect` 로 이 상태를 잡도록 만든 이유가 이것이다. 실제로 오늘
IP 변경 사고에서 `/health` 가 503 + `stale_detect` 로 정확히 잡아냈다.)

## 4. 기각한 가설

| 가설 | 기각 근거 |
|---|---|
| "go2rtc 가 좀비 세션을 붙들고 안 놓는다" | M3 — 소비자 종료 2초 내 세션 0. 정상 경로에서 좀비 없음 |
| "워커 재연결 코드가 고장났다" | 2026-08-13 실측: 슬롯을 비워주자 **10초 만에 자동 복구**. 코드는 정상 |
| "카메라가 죽어서 아무도 못 붙는다" | 같은 시점에 go2rtc 는 정상 접속 중이었다 |

★단, 2026-08-13 에 관측된 **go2rtc 가 세션 2개를 점유한 상태**는 M2·M3 와 어긋난다.
런타임 설정에 스트림이 2개(`tapo`·`test`) 등록돼 있어 둘 다 소비되면 2세션이 될 수 있으나,
당시 `tapo` 가 실제로 소비 중이었는지는 **기록이 없어 확인 불가**(미확인).
이 미확인 항목이 있어도 §2 의 결론(여유 0 + 비대칭 재시도)은 M1·M4·M5 만으로 성립한다.

## 5. 수정 방향과 선택 이유

**하지 않기로 한 것**: 워커의 재시도를 go2rtc 보다 더 공격적으로 만드는 것 —
경쟁을 격화시킬 뿐 근본을 못 고치고, 카메라에 부하만 준다.

**채택**:
1. **백오프 상한을 낮춘다**(30초 → 5초). 워커가 30초씩 쉬면 슬롯이 열려도 못 잡는다.
   상한을 낮추면 "한 번 밀리면 영구히 밀리는" 구조가 깨진다.
2. **기아를 감지해 슬롯을 되찾는다**(2차 방어). `stale_detect` 가 N초 지속되면 해당 카메라의
   go2rtc 스트림을 내려 슬롯을 비우고 워커가 붙게 한다 — **안전 검출 > 라이브 영상** 우선순위.
   M회 실패하면 프로세스 워치독으로 승격.
3. **세션 세대(generation)**로 재연결 경계를 명시해, 옛 세션 프레임이 새 세션에 섞이지 않게 한다.
4. STABILITY.md 의 2차 워치독 변수 3종은 **실제 코드에서 소비되게** 한다(문서만 있는 설정 제거).
