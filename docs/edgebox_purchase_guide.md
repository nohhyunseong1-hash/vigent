## 1. 결론

| 순위 | 항목 | 이유 |
|---|---|---|
| **1** | **CPU** | 병목이 여기다. 카메라당 **2.1 환산코어**(§2) 소모 |
| 2 | RAM 16GB · SSD 256GB | 넉넉하면 그만. 병목 아님 |
| **3(최소만)** | **GPU — VRAM 6GB CUDA 카드면 충분** | 카메라 8대에서도 **GPU util 최대 42%**, 상주 VRAM **3.2GB** |

### 1-1. 가장 중요한 두 줄

> **① GPU 에 돈을 쓰면 낭비다. 같은 예산이면 GPU 를 최저로 내리고 CPU 에 몰아라.**
> **② "CPU 디코드가 병목"은 사실이 아니다 — 픽셀을 1/9 로 줄여도 CPU 는 5% 밖에 안 준다.**

E1 실측: 포화 시점에 **CPU 는 79~99%, GPU 는 16~42%** 였다. 8번째 카메라를 붙이면 그
카메라가 받는 CPU 가 앞선 카메라들의 **절반(208%→109%)** 으로 떨어지고, 그 부족분을
**지연 악화**(실카메라 p95 139→159ms)로 값을 치른다. CPU 가 다 떨어졌다는 뜻이다.

→ **NVDEC(하드웨어 디코더)·고해상도 대응에 돈을 쓰지 말 것.** 해결할 문제가 아니다.

### 1-2. 예산에 대한 정직한 답

| 예산 | 가능한 것 | 근거 |
|---|---|---|
| **30~50만원(중고)** | **파일럿 1~2대** | §4 환산표 — i7-10700급(8C/16T)이 **2대** |

## 2. ★산정 기준 — "코어 수"가 아니라 "이 PC 코어 환산"

카메라당 2.1 코어는 **개발기 코어 기준**이다. 코어 수만 세면 안 된다 — 구형 CPU 는 코어가
같아도 느리다. 그래서 모든 사양을 **환산 코어(9900X-코어 환산)** 로 표기한다.

### 2-1. 기준 CPU

| 항목 | 값 |
|---|---|
| 기준 CPU | **AMD Ryzen 9 9900X** (12코어 / **24 논리스레드**, 4.4GHz) |
| PassMark **싱글스레드** | **4,672** |
| PassMark **CPU Mark**(멀티) | **54,322** |

> 출처: [PassMark — Ryzen 9 9900X](https://www.cpubenchmark.net/cpu.php?cpu=AMD+Ryzen+9+9900X&id=6171) (2026-08-18 조회).
> ★이 점수는 표본이 쌓이며 조금씩 바뀐다. 조회 시점 값으로 다시 계산할 것.

### 2-2. 환산 공식

후보 CPU 의 **환산 코어 수**를 두 가지로 구하고 **작은 쪽(보수적)** 을 택한다.

```
환산코어 A = (후보 논리스레드 수) × (후보 PassMark 싱글스레드 ÷ 4,672)
환산코어 B = 24 × (후보 PassMark CPU Mark ÷ 54,322)

채택 환산코어 = min(A, B)        ← ★반드시 작은 쪽
```

**왜 둘을 비교하나**: A 는 코어당 성능만 보고 SMT(하이퍼스레딩)를 실제 코어처럼 세어
**과대평가**하기 쉽다. B 는 멀티스레드 총량을 보지만 벤치 구성이 우리 작업과 다르다.
둘 중 작은 값을 쓰면 **어느 쪽 오차에도 안전한 방향**으로 기운다.

### 2-3. 대수 산정

```
한계 N  =  환산코어 × 0.70 ÷ 2.1        (= 환산코어 ÷ 3.0)
권장 N  =  한계 N × 0.75                 (야간·재연결 폭주 여유)

거꾸로:  필요 환산코어(최소) = 원하는 대수 × 3.0
         필요 환산코어(권장) = 원하는 대수 × 4.0
```

**검산**: 기준 CPU 는 환산 24.0 → 한계 8.0대. C5 **실측 한계 7대**, E1 에서 **8대째에 포화
신호**. 공식이 실측보다 약간 낙관적이므로 **구매 판단에는 보수적으로 쓴다.**

## 3. 시나리오별 사양표

### 3-A. 파일럿 (카메라 1~2대)

| 항목 | **최소** | **권장** | 근거 |
|---|---|---|---|
| **CPU(환산코어)** | **6.0** (2대 × 3.0) | **8.0** (2대 × 4.0) | §2-3 |
| GPU | NVIDIA CUDA **VRAM 6GB** | VRAM 8GB | 상주 실측 **3.2GB** + 여유(§5) |
| RAM | 16GB | 32GB | 소크 실측 RSS ≈ 3.2GB + OS·torch |
| 저장 | SSD 256GB | NVMe 500GB | 실사용 실측 **≈5.2GB**(§6) |
| OS | **Windows 10/11** | 동일 | §7 |

> 카메라 **1대만** 필요하면 환산코어 최소 **3.0** / 권장 **4.0**.

### 3-B. 소형 현장 (카메라 4~5대)

| 항목 | **최소** | **권장** | 근거 |
|---|---|---|---|
| **CPU(환산코어)** | **15.0** (5대 × 3.0) | **20.0** (5대 × 4.0) | §2-3 |
| | 4대면 최소 **12.0** / 권장 **16.0** | | |
| GPU / RAM / 저장 / OS | 3-A 와 **동일** | | **대수와 무관** — GPU util 은 8대에서도 42% 이하 |

> ### 🔴 이 구간은 30~50만원 예산 밖이다
> 환산코어 15~20 은 **PassMark CPU Mark 약 27,000~45,000** 에 해당한다(§2-2 B식 역산).
> 이 예산대의 중고 사무용 CPU 는 §4 표에서 보듯 **Mark 9,500~16,000** 수준이다.
> **예산을 올리거나, 대수를 줄이거나, §3-C 를 검토해야 한다.**

### 3-C. 예산 안에서 대수를 늘리는 유일한 실측 기반 수단

**카메라당 fps 를 2 → 1 로 낮추면 소요가 절반**이 된다(C-1 실측 + E1 환산이 일치).
같은 박스로 대수가 **2배**가 되고, 필요 환산코어는 **대수 × 1.5(최소)** 로 떨어진다.

⚠ **그러나 규칙6(기능 저하 금지) 대상이라 여기서 결정하지 않는다.** 검출 주기가
0.5초 → 1.0초가 되면 **존 침입 디바운스(`zone.enter_s` = 1.0초)와 충돌**해 침입을 놓칠
수 있다. 채택하려면 **별도 승인 + 침입 검출률 재측정**이 선행돼야 한다.

## 5. GPU 하한 — 실측 근거

| 지표 | 실측값 | 출처 | 함의 |
|---|---|---|---|
| 상주 VRAM | **3,205~3,350 MiB** | C5·E1 전 구간 | **VRAM 6GB 면 충분**(2배 여유), 8GB 권장 |
| VRAM 증가폭(1→8대) | 3,205 → 3,239 MiB (**+1%**) | E1 §4 | **대수를 늘려도 VRAM 은 거의 안 는다** |
| GPU util | **최대 42%**(대개 20~30%) | C5·E1 | **GPU 연산은 남아돈다** |
| 8대 시점 GPU util | **16~21%** | E1 §2-1 | 카메라가 늘수록 오히려 **내려간다** |

→ **결론: GPU 성능은 대수에 영향이 없다. VRAM 6GB CUDA 카드면 되고, 그 이상은 낭비다.**
단 **최신 torch(cu130) 지원 아키텍처**여야 한다(§9 체크리스트).

## 6. RAM·저장 — 병목이 아니다 (실측)

| 항목 | 실측 |
|---|---|
| 프로세스 RSS(24h 소크) | **≈3.2 GB** → RAM 16GB 최소 |
| Python site-packages(torch cu130 포함) | **4.09 GB** |
| 저장소(코드 + runs) | **0.66 GB** |
| 모델 가중치 3개(각 115MB) | **0.35 GB** |
| 증거 30일 보관(5대, 중 시나리오) | **95.6 MB** ([ops_disk_sizing.md](ops_disk_sizing.md)) |
| **합계(Windows 제외)** | **≈5.2 GB** |

→ **256GB SSD 로 충분하고 남는다.** 저장 용량에 예산을 더 쓸 이유가 없다.

## 7. Windows 필수 · Linux/ARM 제외 사유

현재 배포 경로는 Windows 에 묶여 있다. **이식 가능하지만 재작업이 필요하고 검증되지 않았다.**

| 의존 | 위치 | Linux 시 |
|---|---|---|
| 서비스 등록(재부팅 자동 기동) = **NSSM** | `deploy/windows/install_service.ps1` | systemd 유닛 **재작성 필요** |
| 저장 암호화 검사 = **`cipher /c`** | `vigent-core/privacy.py:175` | LUKS/eCryptfs 로 **재구현 필요** |
| 볼륨 암호화 검사 = **`Get-BitLockerVolume`** | `vigent-core/privacy.py:199` | 동일 |
| 배포·상태 점검 스크립트 | `deploy/windows/*.ps1` | 전부 **재작성 필요** |
| 설치 절차서 | [md/DEPLOYMENT.md](../md/DEPLOYMENT.md) (PowerShell 기준) | **재작성 필요** |

**ARM(Jetson·라즈베리파이 등) 추가 제외 사유**: 위 4가지가 전부 깨지는 데다,
**ARM 용 torch·RF-DETR 조합을 우리는 검증한 적이 없다.** 성능 이전에 **동작 자체가 미확인**이다.

→ **Windows 라이선스가 포함된 중고 PC** 를 사는 편이 총비용에서 유리하다.

## 8. ❌ 사지 말아야 할 것

| 사지 말 것 | 이유(실측 근거) |
|---|---|
| **비싼 GPU** | 8대에서도 GPU util 최대 42%. 대수가 늘지 않는다 — 순수 낭비(§5) |
| **NVDEC·하드웨어 디코딩을 내세운 제품** | 픽셀을 1/9 로 줄여도 CPU 는 −5.5%. 디코드는 문제가 아니다 |
| **VRAM 만 큰 카드** | VRAM 은 1대→8대에서 **+1%** 밖에 안 는다. 6GB 면 끝 |
| **NVIDIA 아닌 GPU**(Intel Arc·AMD·iGPU) | 서빙이 **torch cu130 CUDA** 경로다. 타 백엔드 **미측정·미검증** |
| **Jetson·ARM 엣지박스** | §7 — Windows 의존 4가지가 깨지고 ARM torch/RF-DETR **미검증** |
| **N100급 4코어 미니PC** | 환산 **1.61코어** → **1대도 못 돌린다**(§4) |
| **아주 오래된 GPU**(Kepler·Maxwell 등) | 최신 torch(cu130)가 지원을 끊었을 수 있다 — §9 에서 확인 |

## 9. 중고 구매 체크리스트

### 9-1. 구매 **전** — 후보 거르기 (책상에서)

- [ ] PassMark 에서 후보 CPU 의 **ST 점수**와 **CPU Mark** 를 조회
- [ ] §2-2 로 **환산코어** 계산 → §2-3 으로 **한계 N** 산출 → 목표 대수와 비교
- [ ] GPU 가 **NVIDIA CUDA** 이고 **VRAM ≥ 6GB**
- [ ] 그 GPU 가 **현재 torch(cu130) 지원 대상**인지 확인 (구형 아키텍처 지원 중단 주의)
- [ ] RAM ≥ 16GB (증설 슬롯 여유 확인)
- [ ] SSD ≥ 256GB
- [ ] **Windows 정품 라이선스 포함** 여부
- [ ] 전원 용량이 GPU 를 감당하는지 · 설치 공간·발열·소음
- [ ] ★**반품·교환 가능 조건** ← 9-4 에서 떨어질 수 있으므로 **필수**

### 9-2. 수령 **직후** — 30분 안에 (설치 전)

물건이 광고와 같은지, 고장은 없는지 먼저 본다. 여기서 틀리면 **바로 반품**한다.

- [ ] `Get-ComputerInfo` — OS 판/버전, Windows **정품 활성화** 상태
- [ ] `wmic cpu get name,NumberOfCores,NumberOfLogicalProcessors` — **광고한 CPU 가 맞는지**
- [ ] `nvidia-smi` — **GPU 모델·VRAM 총량·드라이버 버전** 이 광고와 일치하는지
- [ ] `wmic memorychip get capacity,speed` — RAM 용량·슬롯
- [ ] 저장장치 SMART 상태(중고 SSD 수명) — `wmic diskdrive get model,status,size`
- [ ] 30분 부하 후 온도·소음·강제 종료 여부 (중고는 **쿨링 열화**가 흔하다)

## 10. 이전 "30만원대 가능" 결정 대조 — ❌ **무효**

### 10-1. 그 결정의 실제 내용

`docs/ops_capacity_sizing.md`(C-1, 2026-08-11):

- §3 표: *"CPU 전용 미니PC 25만원 → **약 8대**(추정/미검증)"*
- §3.1: **그 8대를 스스로 보류**했다 — *"§3의 «CPU 전용 미니PC(25만원) → 약 8대»는 이
  재검증으로 보류한다"*
- §3.1 최종: *"**중간급(40~60만원대, 중고 사무용 i5) 경로를 기본으로 확정한다**
  … N100급은 카메라 1~2대의 초소형 현장에 한해 조건부 후보"*

### 10-2. 전제 2개가 모두 깨졌다

| 전제 | 당시 | 현재 | 영향 |
|---|---|---|---|
| **카메라당 1fps** | 모든 실측이 1fps | 운영 기본 **2fps**(`worker.fullset_fps: 2`, C5·E1 모두 2fps) | **소요 2배 → 대수 절반** |
| **ONNX fp32 CPU 백엔드로 1.85배 이득** | "적용하면" 기준으로 환산 | **적용되지 않았다** — 검출 경로는 torch(`.pth`). `onnx` 는 얼굴 익명화(YuNet)에만 쓰인다(`privacy.py:65`) | **가정한 이득이 실재하지 않음** |

> C-1 §3.1 자신이 *"아직 실제 서빙 코드에는 반영하지 않았다"* 고 적어뒀고, 그 상태가 오늘까지 그대로다.

**추가된 제약**: RF-DETR 4슬롯 필수화·YOLO 폴백 차단(가벼운 폴백으로 도망갈 길 없음),
그리고 E1 로 병목이 **CPU 추론 연산**으로 확정(= CPU 사양이 곧 대수).

### 10-3. 항목별 판정 — 이번엔 숫자로 대조했다

| 이전 주장 | 현재 실측 환산(§4) | 판정 |
|---|---|---|
| "N100급(25만원) → 약 8대" | 환산 **1.61코어 → 0.5대** | ❌ **무효**(C-1 §3.1 이 이미 보류) |
| "N100급 → 1~2대 조건부 후보" | 환산 **1.61코어 → 0.5대** | ❌ **무효 — 1대도 불가** |
| "중고 사무용 i5(40~60만원) → 2~4대 여유" | i5-8500 **1.0대** / i5-10400 **1.8대** | ❌ **무효 — 1~2대가 상한** |
| "중간급 경로를 기본으로 확정" | 이 예산으로는 **파일럿 전용** | 🔸 **조건부** — 파일럿 박스로서는 유효, **소형 현장(4~5대)에는 무효** |

### 10-4. 왜 틀렸나 — ★측정값은 틀리지 않았다

C-1 §2(b)는 **같은 개발기**에서 **1fps 로 "16대까지 미포화"** 를 실측했다. E1 의 2.1코어를
1fps 로 환산하면 1.05코어/대 → 24×0.70÷1.05 = **16.0대**. **두 독립 측정이 정확히 일치한다.**

무효가 된 것은 측정이 아니라 **①운영 조건(fps)이 바뀌었고 ②가정했던 최적화(ONNX)가
적용되지 않았기 때문**이다. C-1 문서 자체에는 무효 배너를 달아뒀다.

### 10-5. 현재 유효한 결론

> **30~50만원 = 파일럿 1~2대.** 소형 현장 4~5대는 이 예산에서 **보증 불가**이며,
> 예산 상향(환산코어 15~20 = CPU Mark 27,000~45,000) 또는 §3-C(fps 하향, 별도 승인 필요)가
> 필요하다.

## 11. 측정하지 않은 것 (규칙7)

| 항목 | 상태 |
|---|---|
| **§4 표의 CPU 들** | **VIGENT 를 돌려본 적 없다.** 공개 벤치 점수로 계산한 **추정**이다 |
| **PassMark 환산의 타당성** | 우리 작업(torch 다중 스레드 추론)과 PassMark 벤치 구성은 다르다. **환산 오차를 측정하지 않았다** — §9-4 에서 예측 대 실측을 기록해 나가야 정확해진다 |
| 메모리 대역폭·PCIe 세대의 영향 | **미측정**. 환산식에 반영돼 있지 않다 |
| 구체적 기종·가격·매물 | **조사하지 않았다** — 이 문서는 요구 조건과 거르는 방법만 정의한다 |
| 1fps 운전 시 침입 검출률 | **미측정** — §3-C 채택 전 필수 |
| ONNX 서빙 전환 시 실제 이득 | 개발기 단일 슬롯 1.85배 추정치뿐. 4슬롯·서비스 통합 시 이득은 **미측정** |
| Linux 이식 비용·성능 | **미검증**(§7) |
| **실서비스 디코드 절대값** | E1 에서 `decode_ms` 계측을 추가했으나 **다음 재시작 전까지 값이 나오지 않아 미확인**이다.[^decode] |

[^decode]: **판정에는 영향이 없다.** H1(디코드 병목) 기각은 ①실서비스 저해상 대조군
(픽셀 1/9 → 카메라당 CPU −5.5%)과 ②별도 프로세스 디코드 실측(0.4~1.2ms) 두 갈래로
이미 성립한다. `decode_ms` 는 실서비스에서 절대값을 한 번 더 확인하는 **확인 사살**이며,
다음 재시작 시 수집해 [E1 리포트](../benchmarks/e1_bottleneck_report.md) §9 에 채운다.
