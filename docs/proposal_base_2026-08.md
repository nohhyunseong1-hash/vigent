## 1. 한 장 요약

**VIGENT 는 산업안전 CCTV 영상을 실시간으로 분석해 위험을 감지하는 소프트웨어다.**
기존 CCTV(RTSP)에 연결해 ①사람 검출·추적 ②보호구 착용 여부 ③화재·연기 ④중장비 근접·
위험구역 침입을 판정하고, 위험 시 증거 프레임을 남기고 경보를 보낸다.

| 항목 | 내용 |
|---|---|
| **현재 단계** | 파일럿 직전 — 기반 검증 + **라이브 종단 실증 완료**, 산업현장 설치 검증 대기 |
| **검증 방식** | 자체 감사로 차단 항목을 먼저 식별하고, 항목마다 **합격 기준을 측정 전에 선언**한 뒤 실측으로 닫았다 |
| **개발 기간** | 2026-06-19 ~ 2026-08-20 (약 2개월, 커밋 644건) |
| **코드 규모** | 애플리케이션 18,077줄 / 테스트 4,366줄 (테스트 348건) |
| **실환경 가동 실적** | 실카메라 **24시간 연속 무중단** 가동 (자동복구 실패 0, 미전송 경보 0) |

**핵심 주장 3가지와 그 근거:**

1. **무인 24시간 운영이 실측으로 확인됐다** — 실카메라 24시간 소크에서 unhealthy 0회,
   자동복구 실패 0건, 메모리 누수 징후 없음.
2. **장애가 나도 사람 없이 돌아온다** — 전원차단 3회·강제 종료·재부팅 3종을 모두 실측했고
   전부 무개입 복구됐다.
3. **한계를 숨기지 않고 수치화했다** — 카메라 수용 한계 7대, 안전모 미착용 검출 재현율
   36.1% 등 불리한 숫자도 그대로 공개한다. 무엇이 안 되는지 아는 것이 파일럿 설계의 전제다.

**경보 지연**(안전 제품의 핵심 지표): 위험 발생 → 증거·기록 완료까지 **위험구역 침입 1.32초 /
근접 경보 0.45초**(중앙값 실측, §2-6).

> ### ✅ 라이브 종단 실증 완료 (2026-08-21)
>
> 사람이 실카메라 앞에서 위험구역을 걸어 통과 → **담당자 폰에 텔레그램 알림 도착**까지
> 실제로 확인했다(§2-7). 감지 0.94~0.98 · 판정 1초 · **폰 도착 2.72초**.
> 시연으로 그대로 보여줄 수 있다.

> ### 자체 측정으로 결함을 찾고 같은 날 닫았다 (2026-08-20)
>
> 경보 지연을 재는 과정에서 **카메라가 감지한 위험이 통보되지 않는다**는 것을 발견했다
> (워커가 기록까지만 하고 알림 전송 호출이 없었다). 24시간 소크의 전송 경보 0건이 그 증거였다.
> **같은 날 배선을 완료**했고, 배선만 하면 오경보가 폭주하므로 **경보 폭주 방지를 한 묶음으로**
> 설계했다 — 실측 데이터로 재현한 결과 오경보는 **221건 → 24건(89% 억제)**, 반면 수 시간
> 간격의 **실제 경보는 4건 중 4건 전부 통보**된다(§2-8).

**아직 안 된 것(§4에서 상세):** 실제 산업현장 상주 설치 검증, 야간 재현율, 오탐률 집계,
다중 카메라 장시간 운영, 2인 이상 실카메라 추적, 알림 채널 실채널 도달 확인.

## 2. 검증 실적 표

### 2-1. 24시간 실카메라 연속 가동

| 검증 항목 | 방법 | 실측 결과 |
|---|---|---|
| 연속 가동 시간 | 실카메라(RTSP) 1대, 60초 간격 1,437샘플, 결측 0 | **24시간 무중단** · 동일 프로세스 유지(PID 대조) |
| 상태 이상 | `/health` 전수 기록 | unhealthy **0회** · degraded 누적 **0분** |
| 자동복구 실패 | 워커·캡처 카운터 추적 | **0건** |
| 미전송 경보 | 경보 큐 pending/dead 추적 | **0건** |
| 메모리 안정성 | RSS 기울기(구간 분리 후 최악 구간) | **+11.4 MB/h** (기준 ≤30) · 최근 10시간 **−4.87 MB/h** — 누수 징후 없음 |
| 자원 경쟁 내성 | 외부 GPU 부하 90분과 경쟁 | 상태 이상 샘플 **0건**(89샘플 전부 정상) |

**한계(그대로 적는다)**: 카메라 **1대**·정적 장면·저부하 조건이다. 사람이 계속 오가는
현장의 24시간은 미검증이다. 또 24초짜리 짧은 중단이 1회 있었고(RTSP 끊김 → 워치독 정상
작동 → 재시작), 60초 샘플링 사이에 들어가 지표로는 잡히지 않았다 — 로그 대조로만 드러났다.
"완전 무중단"이 아니라 **"임계 미만의 중단이 1회 있었다"** 가 정확한 서술이다.

> 근거: `audit/soak_realcam_2026-08-17_report.md` (2026-08-17~18) · 원자료 JSONL 커밋됨

### 2-2. 검출 정확도

**(가) 보호구(PPE) — 현장 평가셋 109장, 영상 단위 dev/test 분할**

> 🔴 **정정 (2026-08-25) — 아래 '사람' 수치는 현 운영 구성의 성능이 아니다**
>
> 이 표는 **2026-08-10** 측정이고, **2026-08-13 에 추적기가 IoU → ByteTrack 으로 교체**됐다
> (`track.algo: bytetrack`). 그런데 **기준선을 다시 재지 않았다.** 2026-08-25 재측정 결과:
>
> | 사람(person) | dev 재현율 | test 재현율 |
> |---|---|---|
> | 표 아래 값(IoU 시절, 2026-08-10) | 68.2% | 77.3% |
> | **현 운영(ByteTrack) 재측정** | **38.2%** [31,46] | **59.1%** [44,72] |
> | 〃 정밀도 | 84.5% | **100.0%** |
>
> ByteTrack 은 재현율을 크게 낮추는 대신 정밀도를 올린다(**교환**이다). 특히 dev 에서
> **원거리(화면 높이 10% 미만) 재현율이 0%** 였다. 근거·재현: `benchmarks/x5_recall_knobs.py`,
> `benchmarks/x5_recall_knobs_interim.md`.
>
> ★**대외 인용 시**: 사람 재현율은 **38~59%(구성·표본에 따라)** 로 말해야 한다.
> 77% 를 말하고 실제가 38% 면 사후에 신뢰가 무너진다. PPE·안전모 수치는 이 교체의
> 영향을 받지 않는다(추적 필터가 person 에만 걸린다 — 실측 확인).

| 지표 | dev(74장) | **test(35장, 1회 채점)** |
|---|---|---|
| 사람 정밀도 / 재현율 ⚠**아래 정정 참조** | 84.9% / 68.2% | **77.3% / 77.3%** |
| PPE 정밀도 / 재현율 | 93.6% / 64.8% | **95.9% / 61.0%** |
| 안전모 미착용 재현율 | [25.9%, 100.0%] | [55.2%, 80.0%] |

**정직하게 읽는 법**: 정밀도(헛경보 적음)는 90% 대로 쓸 만하고, **재현율(놓침)이 61~68%로
낮다.** 그중 **안전모 미착용이 가장 약한 클래스**다 — 109장 전체 측정에서 **36.1%(30/83)**,
동결 기준선에서는 dev [25.9%, 100.0%] / test [55.2%, 80.0%] 구간이다.

★구간으로 낸 이유와 원인: 놓친 GT의 상당수가 **사람이 봐도 착용 여부를 판별할 수 없는**
프레임이었다(육안 검수 확인). **카메라가 정수리를 수직으로 내려다보는 설치 각도**라
안전모 챙이 이미지에 아예 안 담기는 물리적 한계이며, 학습으로 고칠 수 없다.
→ 이것이 §5 "카메라 설치 요건"이 제품의 일부인 이유다.

※ dev·test 의 판별불가 판정 방법이 서로 달라(test 1회 채점 원칙 유지 위해) 두 구간은
엄밀히 같은 정의가 아니다 — 방향만 참고한다.

**순환 오염을 스스로 제거한 지표**: 정답지가 자체 모델 초안에서 출발했으므로, 정답 박스를
"모델이 원래 찾던 것"과 "사람이 새로 추가한 것"으로 갈라 따로 쟀다.
→ 사람이 추가한 자리 재현율 **사람 37.8% / PPE 20.1%**. 이것이 순환에 오염되지 않은
유일한 성능 지표이며, 우리는 이 낮은 숫자를 공개한다.

**측정 불가로 선언한 것**: `Safety-Vest`(양성 표본 2건)는 **조끼 성능을 주장할 수 없다.**
`mAP@50:95` 는 구조적 결함(사람이 손대지 않은 박스가 IoU=1.0)이 확인돼 **인용 금지**로 못박았다.

### 2-3. 카메라 수용량

| 항목 | 실측값 | 근거 |
|---|---|---|
| **한계 대수** | **7대** (8대에서 불합격) | 단계별 3분 부하시험, 합격 기준 사전 선언 |
| **권장 대수** | **5대** (한계의 75%) | 야간·재연결 폭주 여유 |
| 8대 실패 양상 | 지연 p95 116ms → **309ms(2.7배)**, degraded 발생 | — |
| 카메라당 CPU | **1.55 논리코어** @2fps (개선 전 2.10) | 실서비스 짝지은 비교 |
| GPU 소요 | VRAM **1,397 MiB** · util 최대 42% | — |

★**병목을 실험으로 특정했다.** 가설 4개를 각각 데이터로 판정했다:
- **CPU 디코드 → 기각**: 픽셀을 1/9로 줄여도 CPU는 5.5%만 감소(디코드 절대값 0.4~1.2ms)
- **GIL 병목 → 기각**: 포화 시 15.4~16.0 코어가 24코어에 널리 분산 — 단일 코어 포화 아님
- **락 직렬화 → 부차적**: 락만으로 포화하려면 10.7대 필요 — CPU가 먼저 막는다
- **결론: 추론 파이프라인의 CPU 연산** → 따라서 **GPU를 올려도 대수가 안 늘어난다**

이 진단으로 실제 개선을 만들었다: 추론 런타임의 스핀 대기(busy-wait)를 제거해
**카메라당 CPU −26%**(2.10→1.55), 실카메라 검출 p95 **162.9 → 85.8ms**.

**한계**: 부하 카메라는 파일 소스라 RTSP 디코드·재연결 부하가 실카메라보다 가볍다 —
**실카메라 7대는 더 나쁠 수 있다.** 1회 측정이며 분산은 보지 않았다.

> 근거: `benchmarks/capacity_report.md` · `benchmarks/e1_bottleneck_report.md`

### 2-4. 장애 복구

| 시나리오 | 방법 | 실측 결과 |
|---|---|---|
| **카메라 전원차단** | 실카메라 전원 3회 차단 + 확대뷰 점유 1회 | **4/4 무개입 복구** — 6.0초 / 8.1초 / 49.6초 / 8.2초 |
| **프로세스 강제 종료** | 관리자 권한 `taskkill /F` | **10.0초 재기동**(설정 지연 5초 포함, 순수 오버헤드 ~1.5초) → 28.8초 후 정상 → 33.8초 후 카메라 복귀 |
| **PC 재부팅** | 실제 재부팅, 로그인하지 않은 상태 | **무인 자동 기동 성공** — 부팅 +284초(지연 시작 설계) · 카메라 자동 복귀 · 경보 유실 0 |
| **경보 전송 실패** | 내구 큐 + 데드레터 | 24시간 소크 중 미전송 **0건** |

**개선 전과 비교**: 전원차단 복구는 수정 전에는 **7분간 검출이 죽고 수동 개입이 필요**했다.
지금은 최장 49.6초에 자동 복구된다.

**한계**: 전원차단 3회 중 2차 방어(기아 감시)는 **발동하지 않았다** — 1차 방어만으로
복구돼서 **2차 방어는 이 시험에서 검증되지 않았다.**

| **자동 파기** | ✅ 구현 + **자동 실행(2026-08-21~)** | 그룹별 보존기간 분리(증거 30일 / 감사·위험성평가 3년). 서버가 24시간 주기로 스스로 스윕한다. 안전장치: 첫 주기는 목록만 남기고 지우지 않음 · 삭제 경로 화이트리스트 · 실행 여부를 `/health` 의 `retention_sweep` 으로 확인 |
| **영상 외부 전송** | ✅ 기본 차단 | 클라우드 분석은 **명시적 opt-in 2조건**(전용 스위치 + API 키)이 모두 있을 때만. 실증: 키만 있고 스위치 없을 때 외부 호스트 조회 **0건** |
| **저장 암호화** | ⛔ **미적용 — 요건으로 이관** | 개발 PC(Windows Home)는 EFS·BitLocker 관리 기능이 없어 **적용 불가 확정**. → **현장 장비 OS 는 Pro 이상 필수**라는 조달 요건으로 문서화. 상태 API가 `false` 를 정직하게 노출 |

> ### ★정정(2026-08-21) — "자동 파기"는 이 날짜 이전까지 사실이 아니었다
>
> 파기 로직(`retention.sweep()`)은 구현돼 있었지만 **그것을 주기적으로 부르는 주체가
> 어디에도 없었다** — 서버에 스레드가 없었고, 배포 스크립트에 작업 스케줄러 등록도
> 없었다. 실제로는 사람이 손으로 스크립트를 돌려야 했고, 설치 후 아무도 등록하지
> 않으면 **영원히 한 번도 안 지워진다.** 설치 전 안전 리뷰(F6)에서 발견했다.
>
> **2026-08-21 부터 사실이 됐다** — 서버가 24시간 주기로 스스로 스윕하는 스레드를
> 넣었고(`retention_scheduler.py`), 돌고 있는지를 `/health` 의 `retention_sweep`
> (`thread_alive`·`next_run_in_s`)으로 확인할 수 있다. 이 날짜 이전에 작성된
> 자료에서 "자동 파기"를 인용할 때는 이 정정을 함께 봐야 한다.

★**저장 암호화를 "완료"로 적지 않은 이유**: 실행했고 실패했기 때문이다. 전 파일이
"지원되지 않는 요청"으로 0개 암호화됐다. 이것을 실패가 아니라 **조달 요건 발견**으로
기록하고, 개발 PC의 미암호화 잔여 위험도 그대로 등재했다.

> 근거: `vigent-core/privacy.py` · `docs/disk_retention_policy.md` · `audit/human_tests_2026-08-20.md`

> 재시도(최대 10회·60초)가 걸려 **최악의 도달 시간은 수 분까지 늘어날 수 있다**(코드 확인, 미측정).
> ★mock 13.4ms → 실채널 1,416ms 로 **100배 차이**가 났다 — mock 수치를 제품 성능으로
> 인용하면 안 된다는 사례라 두 값을 나란히 남긴다.
>
> **③ 근접 경보 지연은 디바운스 도입으로 늘어났다** — 0.45초 → **0.81초(2026-08-21 실측)**.
> 단일 프레임 오검출을 막는 대가이며 의도한 트레이드오프다(§2-8).

원인은 저조도가 아니라 **화각**이었다(화면 밝기 123/255로 어둡지 않음) —

★**첫 설계는 틀렸고, 실측 데이터를 넣은 테스트가 그것을 잡았다.** 고정 쿨다운 300초는

## 3. 개발 과정의 신뢰성 — 검증이 실제로 결함을 잡아냈다

우리의 방식은 **"만들고 나서 자체 감사로 차단 항목을 먼저 목록화한 뒤, 항목마다 합격
기준을 측정 전에 선언하고 하나씩 실측으로 닫는 것"** 이다.

2026-08-16 자체 감사에서 **설치차단 8건 / 파일럿차단 7건**을 식별했고, 4일 만에
**설치차단 8/8 완료 · 파일럿차단 5/7 완료**(잔여 2건은 사람·조달 대기)로 닫았다.

아래는 **검증이 없었다면 현장에서 터졌을** 결함들이다.

### 사례 1 — 지게차 운전자가 상시 오경보를 만들 뻔했다 (현장 투입 전 발견)

교육기관 실습장은 지게차에 사람이 **상시 탑승**한다. 실영상 320프레임을 분석하니 탑승
운전자가 person 으로 **89.6% 프레임에서 검출**됐고, 운전자–지게차 거리가 0이라
**근접 경보가 94.4% 프레임에서 울렸다** — 사실상 상시 오발화다.

- 조치: 사람 박스가 장비 박스에 일정 비율 이상 포함되면 **그 장비와의 쌍만** 제외
- 결과: 근접 경보 발화 **94.4% → 38.1%**(잔여는 실제 보행자 접근)
- ★안전 설계: **하차하면 즉시 다시 센다**(프레임 단위 판정, 이월 상태 없음) — 하차 직후가
  협착 최고 위험 순간이므로 제외가 과하면 안 된다. 이 계약을 테스트 14건으로 고정했다.

### 사례 2 — "정상"으로 보이던 고장 (감시 지표 자체의 결함)

영상은 살아 있는데 **검출만 죽는** 고장이 있었고, 상태 API가 이때 **200 OK를 반환**했다.
즉 감시로는 영원히 정상으로 보였다. 상태 API에 검출 생존 정보를 넣은 뒤 전원차단 시험을
하니, 프레임이 돌아왔는데 검출만 죽어 있는 6초 구간을 정확히 이상 상태로 잡아냈다.
3회차에서는 같은 상태가 **49.6초** 지속됐다 — 수정 전이라면 영구화됐을 구간이다.

### 사례 3 — 측정이 통과했는데, 실은 아무 부하도 없었다

카메라 수용량 1차 측정에서 9대까지 전부 합격이 나왔다. **부하가 실제로 0대였다** —
등록 API에 활성화 플래그를 빠뜨려 워커가 기동하지 않았던 것이다. 발견 경위는
"카메라를 8대 늘렸는데 GPU 사용률이 안 오르는 게 부자연스럽다"였다. 무효 처리하고,
①워커가 실제로 떴는지 확인 후 진행 ②판정을 전체 평균이 아닌 **실카메라 단독 지표**로
변경해 재측정했다. **이 무효 이력을 리포트에 남긴 이유**는, 같은 실수가 재발하면
"측정했는데 부하가 없었다"는 결과가 그럴듯한 합격으로 보이기 때문이다.

### 사례 4 — 원격 점검이 3일간 막혀 있던 잠복 결함

재부팅 시험 중 휴대폰으로 상태 페이지에 접속하니 흰 화면이 떴다. 원인은 브라우저가 아니라
**서버가 403을 반환**한 것이었고, 서비스 등록 방식과 앱의 접속 허용 설정이 어긋나
**등록 시점부터 3일간 줄곧 있던 결함**이었다. 재부팅과 무관했다. 설치 스크립트를 고쳐
재검증했고, 휴대폰에서 정상 표시를 확인했다. ★이 사례에서 **"사전 점검을 통과했다"고
보고했던 내 확인이 불충분했다는 사실**(인증 면제만 보고 접속 허용 설정을 안 봤다)도
감사 문서에 그대로 남겼다.

### 사례 5 — 학습이 처음부터 발산했는데 그대로 배포됐다

지게차 전용 모델이 모든 대상에 대해 신뢰도 0.002~0.005를 뱉는 현상이 있었다. 회수한 학습
로그를 분석하니 **1 epoch 부터 분류 손실이 NaN** 이었고, 그 상태로 49 epoch 을 완주해
**망가진 체크포인트가 저장·배포**된 것이었다. 정상 대조군(다른 모델)은 같은 파이프라인에서
수렴했다. → 재학습 계획에 **NaN 감시 필수**를 반영했다. 원인 가설(클래스 수 설정)은
**미확정**으로 적었다 — 재현 실험 전에는 단정하지 않는다.

### 사례 6 — 메모리 급감을 오판했고, 정정 이력을 남겼다

24시간 소크 중 메모리가 두 번 계단식으로 떨어졌다. 처음에 "테스트 서버 기동 때문"이라고
보고했는데 **틀렸다.** ①그 서버는 소크 시작 전에 종료돼 시각이 안 겹쳤고 ②워커 카운터가
리셋되지 않아 프로세스 교체가 아니었다. 실제 원인은 외부 GPU 부하로 인한 OS의 메모리
회수였다. **오판 사실과 정정 근거를 감사 문서에 함께 남겼다.**

> 이 6개 사례의 공통점은 **자체 검증이 잡아냈다**는 것이고, 하나같이 **현장에서 발견됐다면
> 신뢰를 잃었을** 종류다. 우리는 리포트에 유리한 숫자만 남기지 않고, 무효 측정·오판·실패한
> 실험(기각된 개선 시도 4종 포함)을 함께 커밋한다.

## 5. 기술 스택과 하드웨어 요건

### 5-1. 기술 스택

| 계층 | 구성 |
|---|---|
| 언어·프레임워크 | Python 3.11 · FastAPI |
| 검출 | RF-DETR 4슬롯(사람 / 보호구 / 화재·연기 / 중장비), 입력 384px |
| 추적 | ByteTrack |
| 영상 | OpenCV · RTSP 직결 |
| 서버 형태 | Windows 서비스(단일 프로세스, 카메라별 스레드) |
| 설계 원칙 | **가산식 + 폴백** — 모델이 없거나 실패해도 규칙 기반으로 자동 폴백, 기능이 죽지 않는다 |
| 테마 확장 | 신규 업종 = 설정 파일 + 프론트 1개. 코어 로직 미수정 |

### 5-2. 하드웨어 요건 (실측 기반)

★**우리가 실제로 돌려본 하드웨어는 개발기 1대뿐이다.** 다른 CPU 값은 공개 벤치마크
기반 **환산 추정**이며, 도입 전 재측정이 필요하다(규칙7).

산정식: `필요 성능 = 대수 × 카메라당 1.55코어 ÷ 0.70(여유율)`

| 시나리오 | CPU(개발기 코어 환산) | GPU | RAM | 저장 |
|---|---|---|---|---|
| **파일럿 1대** | **2.21** (최소) / 2.95 (권장) | CUDA **VRAM 4GB** | 16GB | SSD 256GB |
| **파일럿 2대** | 4.43 / 5.90 | 동일 | 16~32GB | 동일 |
| 소형 현장 4대 | 8.9 / 11.8 | 동일 | 동일 | 동일 |
| 소형 현장 5대 | 11.1 / 14.8 | 동일 | 동일 | 동일 |

**GPU를 넣는 것이 경제적으로 유리하다(실측 근거):** 실제 VRAM 사용은 **1.4GB**뿐이라
저가 GPU로 충분하다. GPU 없이 1대를 돌리려면 상위 CPU가 필요한데, 저가 GPU 값이 CPU
두 단계 가격차보다 싸다. GPU 사용률은 최대 42%라 **상위 GPU로 바꿔도 대수는 안 늘어난다.**

**도입 비용 수준(2026-08 시세 조사 기준, 중고 포함 — 추정):**

| 구성 | 카메라 | 예상 총액 |
|---|---|---|
| 중고 사무용 본체 + 저가 GPU | **1~2대** | **약 56~64만원** |
| 소형 현장(4~5대) | 4~5대 | 🔴 **위 예산 밖** — 조사한 중고 CPU 중 요건을 만족하는 것이 없다 |

★**"30만원대 엣지박스로 8대" 라는 초기 가정은 실측으로 무효 처리했다.** 저가 미니PC급은
환산 성능이 부족해 GPU를 넣어도 1대가 안 된다. 이 정정을 문서에 남긴 것도 검증 결과다.

> 근거: `docs/edgebox_purchase_guide.md` · `benchmarks/capacity_report.md`

### 5-3. 카메라 설치 요건 (제품의 일부)

실측에서 **화면 내 사람 박스 높이가 10% 아래로 떨어지면 신뢰도가 급락**한다(원거리
0.45~0.61, 역광 출입구 0.35 — 추적 활성 임계 0.70 미만). 또 정수리를 수직으로 내려다보는
각도에서는 안전모 판별이 **물리적으로 불가능**하다.
→ 따라서 **카메라 화각·거리·역광 회피가 성능 조건**이며, 설치 전 조사 체크리스트를
제품 산출물로 제공한다.

## 6. 안전·법규 경계 (반드시 함께 고지)

- **VIGENT 는 인증 안전기능을 대체하지 않는다.** 비전 AI 는 확률적이므로, 프레스·전단기
  비상정지의 1차 책임은 인증 하드웨어(광전자식 방호장치, 안전 PLC)에 있다.
  VIGENT 는 **보조·감시 계층으로 신호만 제공**한다.
- CCTV 촬영에는 개인정보 원칙(익명화·고지·동의)이 적용된다. 노사협의·고지 절차는
  배포 시 별도 확인이 필요하다.
- 현재 보존기간 설정은 **법률 전문가 확인 전 잠정값**이다.

## 7. 심사위원이 물을 만한 날카로운 질문 13개와 우리의 답

> 약점을 숨기지 않는 것이 목적이다. 아래 답변은 전부 근거 문서를 즉시 제시할 수 있다.

**Q1. 재현율 61~68% 면 3명 중 1명을 놓친다는 뜻 아닌가? 안전 제품으로 쓸 수 있나?**
맞습니다. 그것이 정확한 해석이고 저희도 그렇게 적었습니다. 두 가지로 답합니다.
①VIGENT 는 인증 안전장치의 대체재가 아니라 **감시 보조 계층**입니다 — 사람이 못 보는
시간대를 덮는 것이 역할이고, 놓침이 있어도 현재의 "아무도 안 보는 상태"보다 낫습니다.
②정밀도는 90~96%라 **헛경보가 적습니다.** 안전 시스템에서 헛경보가 많으면 사람이 무시하기
시작해 시스템 전체가 죽는데, 저희는 그 반대 방향에 있습니다. 재현율 개선이 로드맵 1순위입니다.

**Q2. 안전모 미착용 재현율 36%는 사실상 못 쓰는 수준 아닌가?**
그 클래스만 보면 그렇습니다. 다만 원인을 규명했고, **학습으로 고칠 수 없는 부분이 상당수**
입니다 — 카메라가 정수리를 수직으로 내려다보면 안전모 챙이 이미지에 안 담깁니다. 육안
검수에서도 사람이 판별 못 하는 GT가 다수였습니다. 그래서 저희는 **카메라 설치 요건을 제품에
포함**시켰습니다. 각도가 확보된 조건에서의 재현율은 별도 측정이 필요하며, 아직 안 했습니다.

**Q3. 24시간 소크가 카메라 1대·정적 장면이면 실제 현장 검증이라 할 수 있나?**
할 수 없습니다. 그래서 문서에 한계로 명시했습니다. 이 시험이 증명하는 것은 **"장시간 무인
가동에서 메모리 누수·프로세스 사망·경보 유실이 없다"** 는 인프라 안정성이지, 현장 부하
성능이 아닙니다. 현장 부하는 카메라 수용량 시험(§2-3)이 별도로 다루며, **실카메라 다중
장시간은 미검증**입니다.

**Q4. 지게차 99.1% 재현율은 과장 아닌가?**
그 숫자만 떼면 과장이 됩니다. 그래서 저희가 **먼저 반증을 찾았습니다.** 다른 도메인(창고형
전동 리치트럭) 공개 데이터로 교차 검증하니 **21.4%로 무너졌습니다.** 그 결과를 그대로
공개하고, 99.1% 에 **"카운터밸런스 지게차 한정"** 이라는 꼬리표를 영구히 붙였습니다.
도메인이 바뀌면 재측정이 필요하다는 것이 저희 입장입니다.

**Q5. 테스트 348건이 많아 보이지만, 실제로 의미 있는 걸 검증하나?**
테스트는 기능 커밋에 동봉하는 방식으로 늘렸습니다. 예를 들어 운전자 제외 기능에는 14건을
붙였는데, 그중 핵심은 **"하차하면 즉시 다시 센다"** 는 안전 계약입니다 — 제외 로직이 과하게
작동해 하차 직후(협착 최고 위험) 사람을 무시하면 안 되기 때문입니다. 즉 테스트가 **안전
요구사항을 코드로 고정**하는 역할을 합니다. 다만 테스트는 단위·통합 수준이고, **현장
E2E 는 실측 리포트가 담당**합니다.

**Q6. 카메라 7대 한계면 큰 현장에는 못 쓰는 것 아닌가?**
1대 기준으로는 그렇습니다. 다만 저희는 **병목을 실험으로 특정**했습니다 — GPU가 아니라
추론 파이프라인의 CPU 연산입니다. 그래서 ①GPU를 올려도 소용없고 ②CPU 성능에 비례해
확장되며 ③실제로 스핀 대기 제거만으로 **카메라당 CPU 26%를 회수**했습니다. 대규모 현장은
장비 분산(박스 여러 대)이 현재의 정답이고, 단일 박스 대수 확대는 최적화 여지가 남아 있습니다.

**Q7. 소프트웨어만 있고 하드웨어 비용 산정이 없는 것 아닌가?**
산정했고, 그 과정에서 **저희 초기 가정이 틀렸다는 것도 실측으로 확인**했습니다. 처음엔
"30만원대 엣지박스로 8대"라고 봤는데, 환산 성능을 재보니 **1대도 안 됩니다.** 무효 처리하고
현재는 파일럿 1~2대에 **56~64만원** 수준으로 다시 냈습니다. 4~5대 구간은 아직 예산 밖이라고
정직하게 적어뒀습니다. 다만 저희가 실제로 돌려본 하드웨어는 **1대뿐**이며, 나머지는
공개 벤치 환산 추정입니다.

**Q8. 개인정보 보호를 말하면서 저장 암호화가 미적용인 이유는?**
적용을 시도했고 **실패했습니다.** 개발 PC의 OS 에디션이 암호화 기능을 지원하지 않아 전
파일이 거부됐습니다. 저희는 이것을 실패가 아니라 **조달 요건 발견**으로 기록했습니다 —
현장 장비 OS 는 상위 에디션이 필수라는 요건이 나왔고, 문서 3곳을 고쳤습니다. 그리고
상태 API가 **암호화 안 됨(false)을 정직하게 노출**합니다. 숨기지 않는 것이 저희 방식입니다.

**Q9. 결국 실제 산업현장에 설치해서 운영해본 적은 없는 것 아닌가?**
없습니다. 그것이 현재 가장 큰 공백이고 문서에 그렇게 적었습니다. 다만 준비 상태는
구체적입니다 — 설치 예정 현장(프레스 공장)과 테스트 현장(중장비 교육기관) 영상을 각각
파이프라인에 태워 **사전 검증을 마쳤고**, 현장별 오탐 원인(금속판 배경의 연기 오탐 등)과
카메라 설치 요건을 미리 도출했습니다. 방문 절차서·조사 체크리스트도 작성돼 있습니다.
**파일럿은 검증할 게 남아서가 아니라, 남은 검증이 현장에서만 가능하기 때문에 필요합니다.**

**Q10. 위험을 감지하면 몇 초 만에 알 수 있나?**
증거·기록 완료까지 **위험구역 침입 1.32초, 근접 경보 0.45초**(중앙값 실측)입니다. 구간별로
분해해 쟀고 원자료가 있습니다. 침입 경보의 지연 중 **약 75%는 의도한 안전장치**입니다 —
단일 프레임 오검출을 막는 1.0초 디바운스이며, 설정으로 0.5초까지 줄일 수 있지만 오경보가
늘어납니다. 다만 **정직하게 덧붙일 것이 있습니다**: 현재 카메라가 감지한 위험은 **알림으로
전송되지 않습니다.** 증거 저장과 기록까지만 되고 통보 호출이 배선돼 있지 않습니다. 전송
계층 자체(내구 큐·재시도·데드레터)는 구현·측정돼 있어서 남은 건 두 구간을 잇는 작업이고,
파일럿 로드맵 1순위로 올려뒀습니다. 저희가 자체 측정 중에 발견해 스스로 공개하는 항목입니다.

**Q11. 헛경보는 얼마나 나나?**
**수치를 드릴 수 없습니다.** 24시간 무인 가동에서 위험 이벤트 361건이 기록됐고 표본 6건을
육안 검사하니 6건 모두 헛경보였지만, 전수 분류를 하지 않았고 무엇보다 **그 장면이 작업
현장이 아닙니다**(사무실 책상). 그 숫자를 제품 사양처럼 쓰면 과장입니다. 대신 **원인은
규명했습니다** — 정지한 검은 물체가 사람으로 오검출되고(야간 재측정에서 86.4%), 정지한
오탐 박스는 자동으로 "무동작=쓰러짐 의심" 경보가 되어 **오탐 하나가 경보를 계속 낳습니다.**
원인은 어둠이 아니라 **화각**이었습니다. 파일럿 오탐률 측정 설계(분모·분자·기간·층화)는
이미 확정해 문서에 넣어뒀습니다.

**Q13. 실제로 동작하는 걸 보여줄 수 있나?**
있습니다. **지금 이 자리에서 시연 가능합니다.** 카메라 앞 바닥에 위험구역을 마우스로 그리고,
그 안으로 걸어 들어가면 **약 2.7초 뒤 담당자 휴대폰에 알림이 도착**합니다. 2026-08-21 에
전 경로를 실측했습니다 — 검출 신뢰도 0.94~0.98, 구역 진입 1초 뒤 판정 확정, 증거 프레임
저장(얼굴 자동 모자이크), 텔레그램 도착까지 확인했고 기록이 남아 있습니다(§2-7).
경계를 스치듯 지나가면 **울리지 않는 것도** 함께 보여드릴 수 있습니다 — 단일 프레임
오검출을 막는 디바운스가 의도대로 동작한다는 증거입니다.
다만 정직하게 덧붙이면, 이 실증은 **실내 주거 공간**에서 한 것이고 산업현장 조건
(조명·거리·인원·설비)과 다인 동시 진입은 아직 검증되지 않았습니다.

**Q12. 2개월 만든 것치고 검증 실적이 과한데, 정말 다 측정한 건가?**
저장소에 **원자료가 커밋돼 있습니다** — 소크 JSONL 1,437샘플, 수용량 측정 JSON, 평가셋
109장과 정답지, 학습 로그 CSV까지 전부 추적 가능합니다. 재현 명령도 각 리포트 머리에
적혀 있습니다. 더 강한 증거는 **불리한 기록이 그대로 남아 있다**는 점입니다 — 무효가 된
측정, 저희가 틀렸던 판단과 정정 근거, 효과 없어 기각된 개선 시도 4종이 삭제되지 않고
커밋돼 있습니다. 유리한 것만 남겼다면 그것들이 없었을 겁니다.
