## 0. 추가 진단 — 놓친 것들의 정체 (실측, 2026-08-08)

**질문**: 놓친 객체들은 "임계를 넘지 못한 것"인가, "모델이 아예 못 본 것"인가?
conf=0.10 초안(`labels_draft/`, 1,574건)에 그 객체가 있었는지로 갈랐다.

| | 놓침(FN) | 그중 conf 0.10 초안에 있었던 것 | 해석 |
|---|---|---|---|
| person | 87건 | **48건 (55.2%)** | 절반은 **임계 문제** |
| PPE | 119건 | **9건 (7.6%)** | 대부분 **모델이 아예 못 봄** |

클래스별로 보면 결론이 더 뚜렷하다:

| 놓친 클래스 | 건수 | 초안에 있던 것 |
|---|---|---|
| NO-Safety-Vest | 54 | 4 |
| **NO-Hardhat** | **53** | **0** |
| Hardhat | 10 | 5 |
| Mask | 2 | 0 |

**`NO-Hardhat`은 53건을 놓쳤는데 그중 conf 0.10 초안에 있던 건 0건이다.**
임계를 아무리 낮춰도 안 잡힌다 — **모델이 이 도메인의 안전모 미착용을 볼 능력이 없다.**

### 객체 크기별 재현율 (박스 면적 / 화면 면적)

| 크기 | person | PPE |
|---|---|---|
| 대(>5%) | 73/94 = 77.7% | 32/33 = **97.0%** |
| 중(1~5%) | 31/87 = 35.6% | 58/94 = 61.7% |
| 소(<1%) | 10/20 = 50.0% | 115/197 = 58.4% |

**PPE 정답의 61%(197/324)가 화면의 1% 미만인 아주 작은 객체**이고, 거기서 재현율이 58%로 떨어진다.
크게 보이면 97% 잡는다 — **모델의 문제라기보다 "너무 작게 들어간다"는 입력 해상도 문제**일 수 있다
(가설 — 검증 필요).

## 1. 우선순위별 실행 계획

### ~~★1순위 — person 임계 스윕~~ → **완료(2026-08-08). 가설 기각 — 채택하지 않음**

**실측 결과**(`benchmarks/person_conf_sweep.md`): 임계를 0.20까지 내려도 회수는 31건(예상 48건의 65%)
뿐인데 오탐은 14→103건(7.4배)으로 늘어 정밀도가 89.1%→58.5%로 무너진다. 어느 지점에서도
**정답 1건 회수 = 오탐 1.6~2.9건**. F1 최댓값(0.30, 70.1%)조차 현재값(0.40, 69.3%) 대비 +0.8%p뿐이다.
→ **운용값 0.40 유지 권고.** person 재현율 개선은 아래 2~6순위(해상도·2단계·데이터)에서 찾아야 한다.

### ★2순위 — PPE 소형 객체 대응 (효과 클 가능성, 검증 필요)

**근거**: PPE는 큰 객체 97% / 작은 객체 58%. 정답의 61%가 작은 객체.

두 가지 접근을 A/B로 잰다:

**(a) 입력 해상도 상향** — 현재 `detect.imgsz: 960`. 1280·1536에서 재현율·지연을 측정.
비용: 지연 증가(현재 CPU 148ms → 얼마나 늘지는 재봐야 안다).

**(b) 사람 박스 크롭 후 2단계 PPE 추론** — person 검출 결과로 상반신을 크롭해 그 안에서만
PPE를 추론한다. 작은 객체를 확대해서 넣는 효과. 구조 변경이 필요하지만 소형 객체 문제의
정공법이다. **단, person 재현율(56.7%)이 상한이 된다** — 사람을 놓치면 그 사람의 PPE도 못 본다.
그래서 **1순위(person 임계) 이후에 검토하는 것이 순서상 맞다.**

**주의**: (a)는 `vision.yaml`/`tuning.yaml` 수정만으로 되돌릴 수 있다. (b)는 코어 로직 변경이라
"절대 저하 없음 = 가산식 + 폴백" 원칙에 맞게 **기존 경로를 남긴 채 옵션으로** 붙여야 한다.

### ★3순위 — NO-Hardhat 학습 데이터 보강 (유일한 근본 해법, 비쌈)

**근거**: 놓친 53건 중 conf 0.10 초안에 있던 것 **0건**. 임계·해상도로 해결되지 않는다.
현재 PPE 모델(`ppe_rfdetr_v1.pth`)은 Roboflow 공개셋 *Construction Site Safety v27*로 학습됐다
(`vigent-core/weights/MANIFEST.md`) — **국내 사고영상 도메인과 차이가 있을 가능성이 높다**(추정).

**할 일**:
1. 이 9개 영상에서 프레임을 더 뽑아 라벨링(현재 109장 → 최소 수백 장). 파이프라인은 이미
   구축돼 있다(CVAT + `generate_pilot20_dataset.py` + `cvat_setup_pilot.py`).
2. `NO-Hardhat` 표본을 의도적으로 많이 포함시킨다(현재 정답 83건).
3. 파인튜닝 후 **같은 평가셋으로 재측정**해 개선을 확인한다.

**주의**: 학습에 쓴 프레임은 평가셋에서 제외해야 한다(현재 109장은 평가 전용으로 남길 것).

### 4순위 — GPU 사용 여부 확인 (지연 여유 확보, 확인 필요)

현재 **148ms/프레임(CPU 전용)**. 2순위 (a)로 해상도를 올리면 더 느려진다.
이 PC의 PATH에 NVIDIA 관련 경로가 보이므로 GPU가 있을 가능성이 있으나 **확인하지 않았다.**

**할 일**: `nvidia-smi`로 GPU 유무·VRAM 확인 → 있으면 CUDA 빌드 torch로 전환 검토.
효과가 크면 해상도 상향의 지연 비용을 상쇄할 수 있다.

### 5순위 — 정답지 신뢰도 보강 (모든 수치의 상한)

- **교차검증**: 현재 정답지는 1인 1회 검수. 일부(예: 20장)를 다른 날 다시 보고 일치율을 재면
  "이 정답지의 오차"를 처음으로 수치화할 수 있다. 이후 모든 성능 수치의 신뢰구간이 여기서 나온다.
- **Safety-Vest 표본 확보**: 109장에 양성 2건뿐. **조끼 관련 성능 주장은 현재 불가능하다.**
  조끼 착용 장면이 있는 영상을 별도로 확보하지 않으면 이 클래스는 계속 측정 불가.
- **`000633827` 영상 재검토**: 오탐이 몰린 영상(12프레임에서 삭제 19·추가 2). 정답지 오류인지
  실제 모델 특성인지 확인.

### 6순위 — 측정 인프라 정리

- **초안 생성과 측정의 설정 불일치 해소**: 초안은 `imgsz=640·conf=0.10`, 측정은 `imgsz=960`.
  `generate_pilot20_dataset.py`의 하드코딩 640을 `tuning.yaml`에서 읽도록 통일.
- **`field_eval_*` mAP@50:95 사용 금지 명시** — 순환으로 부풀려진 값(`field_eval_results.md` §2).
  결과 JSON에 경고 필드를 넣거나 문서에 고정 표기.
- **회귀 추적**: 위 변경들을 적용할 때마다 같은 평가셋으로 재측정해 표를 누적한다.

## 2. 하지 말아야 할 것 (근거 있는 반대)
