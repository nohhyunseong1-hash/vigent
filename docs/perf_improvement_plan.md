## ★원칙 — dev/test 분리 (2026-08-10, [P-0] 확정, 위반 금지)

**109장을 dev(74장)/test(35장)로 고정 분할했다(`data/field_eval/dev_test_split.json`, 영상 단위
분할·사용자 승인 완료 — 근거·비교표는 `benchmarks/dev_test_split.md`). 이후 원칙:**

1. **모든 A/B 실험·튜닝(P-1 이후 전부)은 dev로만 채점한다.**
2. **test는 전 실험이 끝난 뒤 단 1회만 연다.** 중간에 test로 채점하거나 test를 보고 설정을 고치면
   그 순간부터 test는 오염되고, **지금까지의 라벨링 노력 전체가 무의미**해진다(다시 살 수 없는
   자원 — 재검수하면 test가 아니게 됨).
3. **`dev_test_split.json`은 재생성·변경 금지.** 분할을 바꾸려면 새 사용자 승인이 필요하고, 그때도
   기존 파일은 보존한 채 새 파일로 남긴다.
4. **⚠️ 기존에 보고된 수치(정밀도 89.1%/91.1%, 재현율 56.7%/63.3%, `field_eval_results.md`)는
   109장 전체 기준(dev/test 분리 전)이다 — test를 오염시키므로 이후 "확정 성능"으로 재인용하지
   않는다.** 참고용(분리 전 전체 기준)으로만 취급한다. 확정 성능은 전 실험 종료 후 test 35장으로
   단 1회 재측정한 값만 쓴다.

## 0. 추가 진단 — 놓친 것들의 정체 (실측, 2026-08-08)

**질문**: 놓친 객체들은 "임계를 넘지 못한 것"인가, "모델이 아예 못 본 것"인가?
conf=0.10 초안(`labels_draft/`, 1,574건)에 그 객체가 있었는지로 갈랐다.

| | 놓침(FN) | 그중 conf 0.10 초안에 있었던 것 | 해석 |
|---|---|---|---|
| person | 87건 | **48건 (55.2%)** | 절반은 **임계 문제** |
| PPE | 119건 | **9건 (7.6%)** | 대부분 **모델이 아예 못 봄** |

클래스별로 보면 결론이 더 뚜렷하다:

| 놓친 클래스 | 건수 | 초안에 있던 것 |
|---|---|---|
| NO-Safety-Vest | 54 | 4 |
| **NO-Hardhat** | **53** | **0** |
| Hardhat | 10 | 5 |
| Mask | 2 | 0 |

**`NO-Hardhat`은 53건을 놓쳤는데 그중 conf 0.10 초안에 있던 건 0건이다.**
임계를 아무리 낮춰도 안 잡힌다 — **모델이 이 도메인의 안전모 미착용을 볼 능력이 없다.**

### 객체 크기별 재현율 (박스 면적 / 화면 면적)

| 크기 | person | PPE |
|---|---|---|
| 대(>5%) | 73/94 = 77.7% | 32/33 = **97.0%** |
| 중(1~5%) | 31/87 = 35.6% | 58/94 = 61.7% |
| 소(<1%) | 10/20 = 50.0% | 115/197 = 58.4% |

**PPE 정답의 61%(197/324)가 화면의 1% 미만인 아주 작은 객체**이고, 거기서 재현율이 58%로 떨어진다.
크게 보이면 97% 잡는다 — **모델의 문제라기보다 "너무 작게 들어간다"는 입력 해상도 문제**일 수 있다
(가설 — 검증 필요).

### 완료 이력 — person 임계 스윕 → **가설 기각(2026-08-08), 채택하지 않음**

**실측 결과**(`benchmarks/person_conf_sweep.md`, 109장 전체 기준 — P-0 이전 측정): 임계를 0.20까지
내려도 회수는 31건(예상 48건의 65%)뿐인데 오탐은 14→103건(7.4배)으로 늘어 정밀도가 89.1%→58.5%로
무너진다. 어느 지점에서도 **정답 1건 회수 = 오탐 1.6~2.9건**. F1 최댓값(0.30, 70.1%)조차 현재값
(0.40, 69.3%) 대비 +0.8%p뿐이다. → **운용값 0.40 유지 권고.** person 재현율 개선은 아래
P-2(이중 신호 앙상블)·P-3(해상도·2단계·데이터)에서 찾는다.

<details><summary>착수 당시 계획(기록 보존)</summary>

**근거**: 놓친 person 87건 중 48건(55.2%)이 conf 0.10 초안에 존재. 현재 운용 임계는 **0.40**

### [P-1] GPU 확인 — 대기 (2분)

현재 **148ms/프레임(CPU 전용)**. P-3의 해상도 상향은 더 느려진다.
이 PC의 PATH에 NVIDIA 관련 경로가 보이므로 GPU가 있을 가능성이 있으나 **확인하지 않았다.**

**할 일**: `nvidia-smi`로 GPU 유무·VRAM 확인, torch가 실제로 CUDA를 잡는지 확인 →
있으면 CUDA 빌드 torch 전환 검토. 없으면 이후 실험(해상도 상향·2단계 크롭)이 CPU로도 실시간
요구사항(현재 148ms/프레임)을 만족하는지 함께 판단.

### ★[P-2] person 이중 신호 앙상블 — 대기 (신규, 2순위로 격상)

**근거**: `benchmarks/pilot_conf_threshold_report.md`([L] 조사)에서 PPE 모델 자체의 `Person` 클래스가
person 검출기가 놓친 사람을 잡는 사례를 "사람없음" 17장 중 6장에서 확인했다 — 두 신호(person 슬롯 ·
ppe 슬롯의 Person 클래스)는 현재 합쳐지지 않는다. person 재현율(56.7%, 전체 기준)은 PPE 판정
자체의 병목이다(사람을 못 보면 그 사람의 PPE 판정 대상 자체가 안 생김). 이 실험은 **학습 불필요·
코드 소량·dev로 즉시 채점 가능**해서 P-1 GPU 확인 다음으로 우선순위를 올린다.

**할 일(순서대로, dev 74장만 사용)**:
1. 두 신호가 dev에서 각각 무엇을 잡고 무엇을 놓치는지 **겹침/차집합부터 측정**한다. 겹침이 거의
   전부면 앙상블 이득이 없다는 뜻 — 그러면 여기서 중단하고 결과만 보고한다.
2. 이득이 있어 보이면 합치는 방식(OR + NMS/중복제거, 클래스 신뢰도 가중 등)을 제안하고 dev에서
   재현율·정밀도 변화를 측정한다.
3. **정밀도 하락이 재현율 상승보다 크면 기각한다**(규칙6, person 임계 스윕과 같은 판단 기준).
4. **지연 영향도 함께 측정**한다 — PPE 모델을 항상 돌려야 한다면(현재도 돌리지만, person 판정에
   쓰려면 두 모델 결과를 매 프레임 합치는 비용이 새로 생김) 비용이 붙는다.

### [P-3] 이후 순서 — 전부 dev로만 진행

**3-1. PPE 소형 객체 대응(해상도 A/B)**: PPE는 큰 객체 97% / 작은 객체 58%(전체 기준, §0),
정답의 61%가 작은 객체. `detect.imgsz` 960→1280·1536에서 재현율·지연 측정(비용: 지연 증가,
P-1 GPU 결과에 따라 감당 가능 여부가 갈림). `vision.yaml`/`tuning.yaml` 수정만으로 되돌릴 수 있다.

**3-2. 사람 크롭 2단계 PPE**: person 검출 결과로 상반신을 크롭해 그 안에서만 PPE를 추론 — 소형
객체를 확대해서 넣는 효과. **person 재현율이 상한이 된다**(사람을 놓치면 그 사람의 PPE도 못 봄) —
그래서 P-2(person 이중 신호 앙상블)로 person 재현율을 먼저 올린 뒤에 검토하는 게 순서상 맞다.
코어 로직 변경이라 "절대 저하 없음 = 가산식 + 폴백" 원칙대로 **기존 경로를 남긴 채 옵션으로** 붙인다.

**3-3. 정답지 교차검증**: 현재 정답지는 1인 1회 검수. dev 또는 test 일부를 다른 날 다시 보고
일치율을 재면 "이 정답지의 오차"를 처음으로 수치화할 수 있다 — 이후 모든 성능 수치의 신뢰구간이
여기서 나온다. **test로 교차검증할 경우 그 자체가 test를 "열어보는" 행위가 아님에 주의**(라벨
재검수는 채점이 아니라 정답지 품질 확인이므로 원칙 위반이 아니다 — 단, 이때 얻은 정답 수정본이
있으면 test 확정 성능 측정 전에 반영해야 함).

**3-4. NO-Hardhat 학습 데이터 보강(유일한 근본 해법, 비쌈)**: 놓친 53건 중 conf 0.10 초안에
있던 것 0건 — 임계·해상도로 해결 안 됨. 현재 PPE 모델은 Roboflow 공개셋 *Construction Site
Safety v27*로 학습돼(`vigent-core/weights/MANIFEST.md`) 국내 사고영상 도메인과 차이가 있을
가능성이 높다(추정). 이 9개 영상에서 프레임을 더 뽑아 라벨링하고 파인튜닝 후 **test로 단 1회
재측정**. **학습에 쓴 프레임은 dev/test 어디에도 안 겹치게 완전히 새로 뽑아야 한다.**

**3-5. 측정 인프라 정리**: 초안 생성(`imgsz=640`)과 측정(`imgsz=960`) 설정 불일치 해소
(`generate_pilot20_dataset.py`의 하드코딩 640을 `tuning.yaml`에서 읽도록 통일) · `field_eval_*`
mAP@50:95 사용 금지 명시(순환 오염, `field_eval_results.md` §2) · 회귀 추적 표 누적.
