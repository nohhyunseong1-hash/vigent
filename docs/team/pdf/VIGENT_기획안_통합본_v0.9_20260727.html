00. 시작하기 전에 (3분 요약)

이 문서는 팀원 전원(대표 포함)이 가장 먼저 읽는 문서입니다. 바이브코딩·팀 프로젝트가 처음이어도 괜찮습니다.

VIGENT가 뭘 만드는 회사인가 (5줄)

  1. VIGENT는 공장·건설현장의 CCTV 영상을 AI가 보고 위험을 잡아내는 산업안전 플랫폼입니다.
  2. 카메라가 "위험구역에 사람이 들어왔다 / 보호구를 안 썼다 / 불·연기가 났다"를 자동으로 감지해 경보합니다. (이것을 비전(Vision, L1)이라 부릅니다.)
  3. 감지 결과로 위험성평가서 같은 안전 서류를 AI가 자동 작성합니다. (이것을 에이전트(Agent, L2)라 부릅니다.)
  4. 즉 "보는 눈(비전) + 판단하는 머리(에이전트)"가 한 시스템으로 붙어 있습니다.
  5. VIGENT는 보조 감시 도구입니다 — 법으로 정해진 안전장치(방호장치 등)를 대체하지 않고, 추가로 지켜보는 신호를 줍니다.

지금 어디까지 왔나 (3줄)

  • 비전·에이전트 코드와 자체 테스트(82개 통과)는 갖춰졌고, 동시부하 크래시(F-14) 같은 큰 안정성 문제는 해결했습니다.
  • 하지만 실제 현장 CCTV로 정확도를 잰 적이 거의 없습니다(실영상 검증 1건). 공개 데이터셋 수치만 있습니다.
  • 감지 클래스는 3클래스 가동(person·PPE·fire/smoke) + forklift(지게차)는 재학습 대기입니다.

앞으로 뭘 할 건가 (3줄)

  • 비전(L1): 현장 영상으로 정확도(오탐·미탐)를 재고, 부족한 클래스(안전모 미착용 등)를 재학습해 KISA 인증 기준(F1 ≥ 0.90)을 향합니다.
  • 에이전트(L2): AI가 만든 안전서류의 품질을 계측하고, 잘못된 법령 인용(환각)을 막고, 비전 감지와 자동 연동합니다.
  • 두 트랙이 만나 파일럿(시범 설치) → 유상 납품으로 갑니다. 상세 단계는 10·20 문서에 있습니다.

좋은 지시문 4원칙

  1. 목적 먼저 — "무엇을 왜" 한 줄로.

60. 협업 규칙 — Git

깃(git)이 뭔가 (비유)

  • 게임 세이브 파일과 같습니다. 작업을 "저장(커밋)"하면 언제든 그 지점으로 돌아갈 수 있습니다.
  • 여러 명이 각자 세이브를 만들고 나중에 합치는(merge) 도구입니다. 문서 버전관리(v1, v2 …)를 자동으로 해준다고 보면 됩니다.

반드시 지킬 5가지 규칙 (제일 중요)

  1. 작업 전 git pull — 남이 올린 최신을 먼저 받는다.
  2. 내 작업은 내 브랜치에서 — main에 직접 작업하지 않는다.
  3. 작업 단위로 커밋 — 한 번에 하나. 메시지에 무엇을 했는지 쓴다.
  4. .env·가중치·현장영상은 절대 올리지 않는다.
  5. 막히면 멈추고 공유 — 특히 충돌(conflict)은 혼자 해결하려 하지 말 것.

하루 작업 흐름 (명령어 + 한 줄 해설)

git pull                          # 최신 내용 받기
git checkout -b feat/내작업이름     # 내 작업 공간(브랜치) 만들기
# ... 작업 ...
git status                        # 뭐가 바뀌었는지 보기
git add -A                        # 바뀐 것 전부 담기
git commit -m "feat: 무엇을 했는지" # 저장(커밋)하기
git push -u origin feat/내작업이름  # 내 브랜치를 서버에 올리기

브랜치 이름 규칙

  • 형식: 종류/짧은설명 — 예: feat/f1-측정, fix/포트충돌, docs/온보딩보완

커밋 메시지 규칙 (종류 + 한글 설명)

  • feat: 새 기능 / fix: 버그 수정 / docs: 문서 / test: 테스트 / refactor: 구조 개선
  • 예시 5개:
    • feat: 클래스별 F1 산출 스크립트 추가 (V-02)
    • fix: 가중치 부재 시 fail-fast 전환 (F-8)
    • docs: 신규 팀원 온보딩 문서 추가
    • test: rig_monitor 상태전이 테스트 보강
    • refactor: 이벤트→체크리스트 연동 구조 정리 (A-01)

절대 치면 안 되는 명령어와 이유

명령어 왜 위험한가
git push --force 남의 작업을 덮어써 삭제할 수 있음
git reset --hard 저장 안 한 내 작업이 되돌릴 수 없이 사라짐
rm -rf 폴더·파일을 복구 불가하게 삭제
main에 직접 push 리뷰 없이 전원에게 영향, 사고 시 추적 어려움

  3. 화면(충돌 메시지)을 Claude Code에 그대로 붙여넣고 "충돌이 났어. 어떻게 해결하는지 알려줘"라고 물어봅니다.
