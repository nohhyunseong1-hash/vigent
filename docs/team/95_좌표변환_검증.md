## A단계 — 서버 쪽 좌표 변환 (제품 경로 우선)

### 1. 크기 변환 경로 추적 (영상 → 박스 좌표)

| 순서 | 무엇 | 위치 |
|---|---|---|
| ① 원본 크기 | 입력 이미지 h,w 그대로 읽음(줄이지 않음) | `detectors/rfdetr_adapter.py:47` `h,w = image_bgr.shape[:2]` |
| ② 모델 입력 | **원본 PIL을 그대로** `model.predict`에 전달 → **리사이즈는 RF-DETR 내부에서** 수행 | `rfdetr_adapter.py:48~49` |
| ③ 비율 유지? | 우리 코드는 리사이즈 안 함 → **종횡비 처리는 RF-DETR 라이브러리 내부** 소관 | (라이브러리) |
| ④ 여백 보정 | 우리 코드엔 letterbox/padding 없음(원본 그대로) → 보정도 라이브러리 내부 | — |
| ⑤ 원본 좌표 복원 | 반환 박스는 원본 픽셀 → **원본 w,h로 정규화(0~1)** | `rfdetr_adapter.py:60~61` → `detectors/base.py:finalize_box` `x1/w, y1/h` |
| ⑥ 픽셀 되돌림 | 정규화 0~1 × 입력 이미지 W,H → 픽셀 | `routers/detect.py:51~57` |

- **우리 코드의 좌표 수학은 왕복 정합(원본 w,h로 정규화 → 같은 W,H로 복원)이라 구조상 정확.** 유일한 변수는 **②의 RF-DETR 내부 리사이즈**.

### 2. 타일링(zone_tile) 좌표 — 정상

- `zone_tile.py:41` 위험구역 픽셀 bbox(프레임 경계로 클램프) → `:45` 크롭 → `:46` **upscale 2배**(검출 해상도용) → `:48` detect_fn → `:51~57` 되돌림.
- **되돌림 수학 정확**: `px1 = zx0 + bx1*zw`(크롭 정규화 × 크롭 픽셀폭 + 오프셋) → `/W`(원본 정규화). **upscale은 정규화에서 상쇄**되어 좌표에 영향 없음.
- 경계 걸친 사람: 크롭에 **잘림**(zone 한정 의도). 좌표 매핑 자체는 정상, foot(하단중앙)로 zone 소속 판정(`foot_in_zone`).
- → **타일링 좌표 어긋남 없음.**

### 3. 실측 — 정답을 아는 합성으로 오차 측정 (`scratchpad/coord_baseline.py`)

방법: 실제 사람 프레임(test_walk f24, 960×540)을 여러 해상도/비율로 **레터박스(비율유지 패딩)**해 넣고, 계산된 위치 vs `guard.detect` 반환 위치의 중심 오차를 픽셀로 측정.

| 입력 해상도 | 비율 | 가로 오차(px) | 세로 오차(px) | 판정 |
|---|---|---|---|---|
| 1920×1080 | 16:9 | 0.3 | 0.6 | 정상 |
| 1280×720 | 16:9 | 0.1 | 0.7 | 정상 |
| 640×480 | 4:3 | 0.0 | 4.2 | 정상 |
| **720×1280** | **9:16 세로** | 0.0 | **93.4** | **★오차 큼** |
| 640×640 | 1:1 정사각 | 6.0 | 9.3 | 경계선 |

- **판정 기준**: 중심 오차 **< 프레임 크기의 2%** = 정상(검출 자체의 미세 지터). **2% 이상이고 비율에 따라 커지면** 좌표 변환 문제.
- 같은 비율(16:9) 3종 오차 = 검출 지터 바닥(<1px). 이걸 기준으로 나머지 판단.

### 4. 오차 원인 (코드로)

- **가로는 항상 정상(0~6px), 세로만 문제.** 세로 오차가 **비율이 극단(세로형)일수록 커짐**(16:9 0.6 → 4:3 4.2 → 1:1 9.3 → 9:16 **93.4**).
- **일정하게 밀리는 게 아니라 비율 의존**(landscape에서 멀어질수록↑) → **RF-DETR 내부 리사이즈가 극단 종횡비에서 세로를 정확히 되돌리지 못함**(②). 우리 코드(finalize_box·router·zone_tile)는 정확.
- 타일링과 무관(타일 안 켜도 발생). 특정 해상도가 아니라 **비율(aspect)** 문제 — **세로형(9:16)에서 심각, 정사각(1:1) 경계선, 가로형(16:9·4:3) 정상.**

## B단계 — 브라우저 쪽 (서버 표준비율 정상 확인 후)

### 1. 재계산 방어(realtime_core.js:2450~2459)가 막는 것 / 못 막는 것

- **막는 것**: 매 렌더마다 **현재** `videoWidth/videoHeight·canvas.width/height`를 읽어(2453), 캡처 시점 값과 다르면 **scX/scY를 그 자리에서 재계산**(2456~2458). → 캡처~렌더 사이의 **창 리사이즈·카메라 전환**을 잡아 캐시 race를 무력화.
- **못 막는 것(좁음)**: ① 재계산 이후~그리기 사이의 **초미세 race**(한 렌더 내부). ② 카메라 전환 순간 `videoWidth=0`이면 재계산을 건너뜀(`nowVW>0` 가드) → 그 1프레임은 캐시값 사용(단 telemetry 기록·다음 렌더에 교정). ③ CSS object-fit 가정이 다르면 mediaRect가 어긋날 수 있음(현재 contain 전제).

### 2. 좌표 어긋남 기록(telemetry) — 실제 확인

- `_coordMismatchTelemetry`(2435)가 불일치 시 **`/recognition/log`에 `rule:coord_mismatch`로 기록**(2441) → `data/recognition/events_*.jsonl`에 쌓임(800ms throttle).
- **실측(32개 로그·610 이벤트)**: **`coord_mismatch` = 0회.** 기록 경로는 정상(같은 방식의 `coord_event` = 9회 존재) → **좌표 어긋남이 기록상 한 번도 발생하지 않음.**
- 확인 명령: `grep -h '"coord_mismatch"' data/recognition/events_*.jsonl | wc -l` → 0

### 3. 브라우저 수동 확인 절차 (초보자용)

1. 브라우저에서 라이브뷰를 연다(예: `http://127.0.0.1:8010/safety-pro`), 카메라를 켠다.
2. 사람이 화면에 나와 **박스가 그려진 상태**를 만든다.
3. **DevTools 콘솔**을 연다(F12 → Console).
4. 박스가 보이는 동안 **브라우저 창 크기를 천천히 바꾼다**(모서리 드래그) / 또는 전체화면 토글.
   - **정상**: 박스가 사람에게 계속 붙어 있고, 리사이즈 후에도 정렬 유지.
   - **문제**: 박스가 사람에서 **벗어나 엉뚱한 곳**으로 가고 **회복 안 됨**.
5. 콘솔에 **`[coord-mismatch]`** 경고가 뜨는지 본다(뜨면 그 순간 불일치 감지·자동 교정 시도).
6. **카메라 전환**(다른 카메라/전후면)도 해보고 박스가 다시 정렬되는지 본다.
7. 서버 기록 확인: `grep coord_mismatch data/recognition/events_*.jsonl` — 새 항목이 생겼는지.

## 최종 판정

- **서버 좌표 변환**:
  - **가로형(16:9·4:3) = 문제 없음** (오차 <5px, 1% 미만 = 검출 지터 수준). **실측 근거.**
  - **세로형(9:16) = 문제 있음** (세로 93px 오차). 정사각(1:1)은 경계선(9px). 원인은 **RF-DETR 내부 리사이즈**(우리 코드 아님).
- **브라우저 좌표 변환**: **문제 없음** (재계산 방어 존재 + `coord_mismatch` 실측 **0회**).
- **제품(worker.py) 영향**:
  - 표준 CCTV(16:9·4:3)를 쓰면 **영향 없음**.
  - **세로형(포트레이트) 카메라**를 쓰면 세로 좌표 어긋남 → zone_intrusion 발 위치 판정 등에 영향 가능. 라이브 브라우저는 640 다운스케일(대개 16:9/4:3) → 영향 미미.
- **고칠 필요**:
  - 표준 비율만 쓸 계획이면 **불필요**.
  - 세로형/정사각 카메라 지원이 필요하면, **`detectors/rfdetr_adapter.py:48~49`**(predict 호출)에서 **명시적 letterbox(정사각 패딩) 후 unletterbox 보정**을 추가하는 방안. (이 문서에서는 **수정하지 않음** — 제안만.)

> **없는 문제를 만들지 않음**: 브라우저·타일링·가로형 서버는 실측상 정상. 문제는 **세로형 서버 좌표 하나**로 국한.

# 추가 검증 — 패딩이 해결책인가? + 이전 수치 정정 (2026-07-27)

## ⚠️ 정정: 이전 "세로형 93px"는 트래커 오염값
- 앞 A단계 측정은 `guard.detect`를 썼는데, 이 함수는 **지속 트래커(`self._tracks`)+EMA**로 **이전 호출에 영향받는 비순수 함수**다(전역 트래커 이슈). 호출 순서에 따라 세로형 오차가 93px↔27.8px로 흔들렸다.
- **트래커 없는 어댑터(`RfdetrDetector.detect`)로 재측정**(순수·결정적, 같은 입력 2회 동일 `0.35095` 확인) → **세로형 실제 오차 = 27.8px**(93px 아님). 문제는 실재하나 값은 정정.

## 패딩(정사각 letterbox) 효과 — 실측 (`scratchpad/coord_pure_test.py`)

| 입력 | 비율 | A: 패딩 없음(현재) | B: 정사각 패딩 후 | 판정 |
|---|---|---|---|---|
| 1920×1080 | 16:9 | 0.8px | 4.9px | 둘 다 정상 |
| 1280×720 | 16:9 | 0.8px | 3.4px | 둘 다 정상 |
| 640×480 | 4:3 | 0.2px | 2.2px | 둘 다 정상 |
| **720×1280** | **9:16 세로** | **27.8px** | **1.7px** | **✅ 패딩이 해결** |
| 640×640 | 1:1 | 2.2px | 2.2px | 불변 |

- **결론: 패딩이 해결책이 맞다.** 세로형 27.8px → 1.7px. 가로형은 패딩 후에도 정상(≤5px, 미세 증가는 패딩 리사이즈 1단계 추가 탓, 허용 범위).
- 원인 재확인: RF-DETR 내부 리사이즈가 극단 종횡비에서 세로를 왜곡 → **입력을 미리 정사각으로 패딩하면 종횡비 1:1이라 왜곡 없음** → un-pad로 원좌표 복원.

## 제안하는 수정 (미적용 — 승인 대기)
