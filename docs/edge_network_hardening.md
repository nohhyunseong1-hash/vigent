# 엣지박스 네트워크 구성 권장안 (초안) — [S2] 보안 점검 Phase 2

> 전제: VIGENT가 고객사 **내부망**에 엣지박스(온프레미스 서버)로 설치되는 배포 형태.
> "내부망이니 안전하다"고 가정하지 않는다 — 내부망도 신뢰 경계 밖으로 취급한다(제로트러스트
> 원칙). 이 문서는 초안이며, 실제 배포 전 검토·승인이 필요하다.

## 핵심 발견 — VIGENT 자체와 go2rtc는 서로 다른 보안 경계다

VIGENT 앱(FastAPI, 포트 8010)은 `VIGENT_API_TOKEN`으로 보호되고, 외부 바인딩(`0.0.0.0`) +
무토큰 조합은 기동 자체를 거부하도록 이미 잘 설계돼 있다(`main.py`). **그러나 go2rtc
서브프로세스(카메라 스트림 중계용, `config/go2rtc.yaml`)는 이 보호를 전혀 받지 않는다** —
`api.listen: ":1984"`·`webrtc.listen: ":8555"`는 Go 관례상 **전 인터페이스에 바인딩**되고,
go2rtc 자체엔 인증 메커니즘이 없다(설정 파일에 인증 섹션 없음, 확인). 즉 VIGENT의 토큰이
설정돼 있어도 **내부망의 아무 기기나 포트 1984/8555로 직접 접근해 스트림을 등록·조회·삭제할
수 있다** — VIGENT 인증 모델을 완전히 우회하는 별도 공격면이다. (P0, 상세는 보안 점검
본 리포트 참고)

## 권장 네트워크 구성

### 1. 필수 — go2rtc 포트를 localhost로 제한

`config/go2rtc.yaml`의 바인딩을 명시적으로 `127.0.0.1`로 좁힐 것(VIGENT가 같은 호스트에서만
go2rtc API를 호출하므로 외부에 열 필요가 없다):

```yaml
api:
  listen: "127.0.0.1:1984"
webrtc:
  listen: "127.0.0.1:8555"
```

★단, WebRTC는 브라우저(대시보드)가 P2P로 미디어를 주고받아야 해서 UDP 후보 광고 방식에
따라 완전한 localhost 제한이 실사용(외부 브라우저 접속) 시나리오와 충돌할 수 있다 — 대시보드를
같은 호스트에서만 여는 구성(예: 관리 PC가 엣지박스에 SSH 터널 또는 VPN으로 접속)이면
문제없지만, 사무실 여러 PC에서 직접 접속해야 한다면 방화벽 규칙(아래 3)으로 대체 검토.

### 2. 필수 — VIGENT 앱 포트(8010)도 내부망 전체에 열지 않는다

`VIGENT_HOST=0.0.0.0`로 열더라도, 그 자체가 "누구나 접근 가능"을 뜻하지 않게 아래 3과
결합할 것. 가능하면 애초에 `127.0.0.1` 유지 + 리버스 프록시(TLS 종단, `docs/TLS_DEPLOYMENT.md`
참고)로 접근을 통제하는 편이 낫다.

### 3. 방화벽 — 화이트리스트 방식 접근 제한

엣지박스의 OS 방화벽(iptables/firewalld/Windows 방화벽)에서:
- 8010(VIGENT API), 1984·8555(go2rtc)는 **관리 대상 IP 대역만 인바운드 허용**(예: 사무실
  내부 관제 PC 몇 대의 고정 IP, 또는 VPN 서브넷).
- 임의의 내부망 브로드캐스트/전체 대역 접근은 차단.
- 아웃바운드는 필요한 만큼만(웹훅 목적지 화이트리스트 호스트, LLM API 호출용 외부 도메인 등).

### 4. VIGENT_API_TOKEN 상시 활성화

엣지박스 배포는 "로컬 개발"이 아니므로, `VIGENT_REQUIRE_TOKEN=1`(이미 구현된 기존 옵트인
플래그, `main.py`)을 **배포 스크립트/Dockerfile의 기본값**으로 채택할 것을 제안한다(코드
강제 변경이 아니라 배포 설정 값 — 별도 승인 필요, 본 리포트 P0 항목 참고).

### 5. camera_secrets.json 등 비밀 파일 접근 통제

`data/`(camera_secrets.json·`.env` 등)는 OS 파일권한으로 서비스 계정만 읽기 가능하게
제한(예: `chmod 600`, 실행 계정 외 접근 차단). 엣지박스가 물리적으로 접근 가능한 환경이면
디스크 암호화(BitLocker/LUKS)도 고려.

## 확인이 필요한 것(이 문서만으로는 결정 불가)

- go2rtc가 실제로 요청 URL을 로그에 남기는지(자격증명 포함 쿼리스트링) — 이 데스크탑엔
  go2rtc 바이너리가 없어 미검증. 배포 환경에서 `data/go2rtc.log` 실제 내용을 확인할 것.
- WebRTC UDP 포트(8555)를 localhost로 제한했을 때 실제 브라우저 접속 시나리오가 깨지는지
  실측 필요(이 문서의 §1 경고 참고).
- 고객사 내부망의 기존 방화벽/VLAN 정책과의 통합 방식은 현장별로 다르므로 별도 협의 필요.
