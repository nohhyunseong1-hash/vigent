## 핵심 발견 — VIGENT 자체와 go2rtc는 서로 다른 보안 경계다

VIGENT 앱(FastAPI, 포트 8010)은 `VIGENT_API_TOKEN`으로 보호되고, 외부 바인딩(`0.0.0.0`) +
무토큰 조합은 기동 자체를 거부하도록 이미 잘 설계돼 있다(`main.py`). **그러나 go2rtc
서브프로세스(카메라 스트림 중계용, `config/go2rtc.yaml`)는 이 보호를 전혀 받지 않는다** —
`api.listen: ":1984"`·`webrtc.listen: ":8555"`는 Go 관례상 **전 인터페이스에 바인딩**되고,
go2rtc 자체엔 인증 메커니즘이 없다(설정 파일에 인증 섹션 없음, 확인). 즉 VIGENT의 토큰이
설정돼 있어도 **내부망의 아무 기기나 포트 1984/8555로 직접 접근해 스트림을 등록·조회·삭제할
수 있다** — VIGENT 인증 모델을 완전히 우회하는 별도 공격면이다. (P0, 상세는 보안 점검
본 리포트 참고)

## 권장 네트워크 구성

### 1. ✅ 완료 — go2rtc 포트를 localhost로 제한(기본값)

`config/go2rtc.yaml`의 바인딩을 `127.0.0.1`로 좁혔다(VIGENT가 같은 호스트에서만 go2rtc
API를 호출하므로 기본값으로는 외부에 열 필요가 없다):

```yaml
api:
  listen: "127.0.0.1:1984"
webrtc:
  listen: "127.0.0.1:8555"
```

같은 머신(엣지박스 자체 화면 또는 SSH/VPN 터널로 접속)에서 여는 대시보드는 이 기본값
그대로 확대뷰(WebRTC)가 동작한다(127.0.0.1 ICE 후보로 성립 — 스모크 확인 완료).

#### 1-2. ✅ 완료 — go2rtc RTSP 재배포 리스너(8554) 완전 비활성화

go2rtc는 카메라 스트림을 RTSP로도 재배포하는 별도 기능이 있는데(자체 릴레이, 소스와
무관하게 `rtsp://<go2rtc>:8554/<stream>`으로 재접속 가능), **VIGENT는 이 기능을 전혀
쓰지 않는다** — 코드 전체에서 `rtsp://...8554` 형태로 go2rtc에 재접속하는 곳이 없다(grep
확인). 그런데 `config/go2rtc.yaml`에 `rtsp:` 섹션이 없으면 go2rtc가 자체 기본값(`:8554`,
전 인터페이스 바인딩, 무인증)을 그대로 적용한다 — api/webrtc는 S2에서 이미 잠갔는데 이
포트만 놓쳐 있었다(S3 리허설에서 `netstat`로 `0.0.0.0:8554 LISTENING` 확인).

안 쓰는 기능이라 바인딩을 좁히는 대신 **완전히 비활성화**했다:

```yaml
rtsp:
  listen: ""
```

go2rtc 문서상 `listen: ""`는 해당 리스너를 아예 켜지 않는다는 뜻이다. 이 desktop에서
go2rtc를 이 설정으로 단독 기동해 `netstat`으로 8554가 더 이상 뜨지 않음을 확인했다(api
1984·webrtc 8555는 기존대로 127.0.0.1에 정상 바인딩).

#### 1-1. 원격 관제 PC에서 확대뷰가 필요한 배포 절차

사무실 여러 PC가 엣지박스에 직접(터널 없이) 접속해 확대뷰를 써야 하는 배포는, **기본값을
그대로 두지 말고** 아래 절차로 명시적으로 열어야 한다 — "전체 개방"이 아니라 "특정 PC만
개방"이 목표다:

1. `config/go2rtc.yaml`의 `webrtc.listen`을 `"127.0.0.1:8555"`에서 `":8555"`(전
   인터페이스) 또는 엣지박스의 LAN IP로 되돌린다. `api.listen`(1984)은 **그대로
   127.0.0.1 유지**(VIGENT만 호출하면 되고, 관제 PC가 직접 호출할 이유가 없다 — 확대뷰에
   필요한 건 8555 미디어 포트뿐).
2. `candidates`의 `${GO2RTC_LAN_IP}:8555` 항목이 이제 실제로 도달 가능해진다(기존 자동
   감지 메커니즘 그대로 사용, 코드 변경 불필요).
3. OS 방화벽에서 UDP 8555 포트를 **관제 PC의 고정 IP(들)만** 인바운드 허용 — 예(Linux
   `firewalld`):
   ```
   firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="<관제PC IP>/32" port port="8555" protocol="udp" accept'
   firewall-cmd --reload
   ```
   Windows 방화벽은 "고급 보안이 포함된 Windows Defender 방화벽"에서 인바운드 규칙을
   프로토콜 UDP·포트 8555·원격 IP 주소를 관제 PC로 한정해 생성.
4. 1984(go2rtc 관리 API)는 이 절차에서도 계속 127.0.0.1 유지 — 관제 PC가 스트림을
   등록/삭제할 필요는 없고 VIGENT를 통해서만 하면 되므로, 열 이유가 없다.
5. 배포 후 관제 PC에서 `/safety-hub` 확대뷰가 실제로 뜨는지 확인하고, 다른(화이트리스트
   밖) PC에서는 UDP 8555 연결이 타임아웃되는지 확인할 것(방화벽 규칙 검증).

### 2. 필수 — VIGENT 앱 포트(8010)도 내부망 전체에 열지 않는다

`VIGENT_HOST=0.0.0.0`로 열더라도, 그 자체가 "누구나 접근 가능"을 뜻하지 않게 아래 3과
결합할 것. 가능하면 애초에 `127.0.0.1` 유지 + 리버스 프록시(TLS 종단, `docs/TLS_DEPLOYMENT.md`
참고)로 접근을 통제하는 편이 낫다.

### 3. 방화벽 — 화이트리스트 방식 접근 제한

엣지박스의 OS 방화벽(iptables/firewalld/Windows 방화벽)에서:
- 8010(VIGENT API), 1984·8555(go2rtc)는 **관리 대상 IP 대역만 인바운드 허용**(예: 사무실
  내부 관제 PC 몇 대의 고정 IP, 또는 VPN 서브넷).
- 임의의 내부망 브로드캐스트/전체 대역 접근은 차단.
- 아웃바운드는 필요한 만큼만(웹훅 목적지 화이트리스트 호스트, LLM API 호출용 외부 도메인 등).

### 4. ✅ 완료 — VIGENT_API_TOKEN 상시 활성화(엣지박스 배포 프로파일)

`Dockerfile`(엣지박스 배포 산출물)의 기본 `VIGENT_REQUIRE_TOKEN=1`로 설정했다 — 토큰
미설정 시 기동 자체를 거부한다. **개발 환경(`uvicorn main:app` 직접 실행)은 이 플래그가
설정돼 있지 않으면 기존 동작(무토큰 로컬 허용) 그대로다** — 로컬 개발 편의는 훼손하지
않았다. 토큰 생성·설정 절차는 `md/DEPLOYMENT.md` §VIGENT_API_TOKEN 참고.

### 5. camera_secrets.json 등 비밀 파일 접근 통제 — 앱 수준 암호화는 보류

**결정(2026-08-10)**: `camera_secrets.json`의 앱 수준(코드) 암호화는 하지 않는다 — 복호화
키를 결국 같은 박스 어딘가에 둬야 해서 "암호화했다"는 착시만 주고 실제 방어 효과는 작다
(박스가 통째로 탈취되면 키도 함께 탈취됨). 대신:

1. **OS 파일 권한**: 서비스 계정만 읽기 가능하게 제한(가능한 OS에서 `chmod 600`
   상당) — `data/camera_secrets.json`·`.env` 둘 다 적용.
2. **엣지박스 기종 선정 요구사항**: OS 디스크 전체 암호화(BitLocker/LUKS 등)를 하드웨어
   스펙 요구사항에 포함할 것 — 이러면 박스 자체가 물리적으로 탈취돼도(전원 꺼진 상태)
   디스크 내용을 못 읽는다. 이 항목은 엣지박스 조달 체크리스트(별도 문서, 미작성 —
   조달 단계에서 작성)에 명시할 것.

### 6. ✅ 확인됨(2026-08-11, S3) — go2rtc.log 자격증명 유출 없음(기본 로그 레벨)

**[S3] 엣지박스 리허설에서 실측 확인**: go2rtc(v1.9.14, 기본 로그 레벨)를 실제 기동해
스트림을 등록·조회했으나 `data/go2rtc.log`에 RTSP 자격증명이 평문으로 남지 않았다.
단 이번 확인은 이 desktop의 파일 기반 카메라(`has_creds:false`) 기준이라, **실제
자격증명 있는 RTSP 카메라로 재확인**하는 편이 더 확실하다(로그 레벨이 스트림 종류에 따라
달라질 가능성은 낮지만 규칙7 — 완전히 같은 조건은 아님). `docs/SOAK_24H_CHECKLIST.md`의
확인 항목은 유지(다음 실카메라 소크에서 재확인).

### 7. `/api/streams` 응답의 자격증명 노출 — 알려진 사실, §1의 localhost 제한이 현재 방어선

go2rtc의 관리 API(`GET /api/streams`, 포트 1984)는 등록된 스트림의 원본 소스 URL을
**자격증명 포함 그대로** JSON으로 돌려준다(go2rtc 자체 설계 — 관리 API의 정상 동작이라
우리가 바꿀 수 없음). [S3] 리허설에서 직접 이 엔드포인트를 호출해 실측 확인했다.

**현재 방어선**: §1에서 `api.listen`을 `127.0.0.1`로 고정했으므로, 이 엔드포인트는 같은
머신에서만 호출 가능하다 — 별도 조치 없이 이미 커버돼 있다. **단, 아래는 반드시 지킬
것**:

- §1-1(원격 확대뷰) 절차를 적용할 때도 `api.listen`(1984)은 **절대 127.0.0.1 밖으로 열지
  말 것** — 절차 자체가 이미 "webrtc(8555)만 열고 api(1984)는 유지"로 명시돼 있지만,
  이 섹션 때문에 그 제약이 한층 더 중요해진다(1984가 열리면 `/api/streams`로 카메라
  자격증명이 통째로 노출된다).
- 향후 go2rtc API를 원격에서 호출해야 하는 요구가 생기면(현재는 없음), 이 엔드포인트를
  프록시 뒤에 두거나 별도 인증 계층을 추가하는 설계 검토가 먼저 필요하다 — 지금처럼
  localhost 고정만으로는 안 된다.

## 남은 확인 사항

- 고객사 내부망의 기존 방화벽/VLAN 정책과의 통합 방식은 현장별로 다르므로 별도 협의 필요.
- §1-1(원격 확대뷰) 절차는 이 desktop에서 원격 PC로 실제 검증하지 못했다(단일 머신 환경) —
  최초 원격 배포 시 방화벽 규칙이 의도대로 동작하는지 실측 확인 필요.
- §6은 자격증명 없는 파일 소스 기준 확인이다 — 실제 RTSP 카메라로 재확인 권장.
