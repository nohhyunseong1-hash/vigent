# 저비용 하드웨어 경로 1단계 — 검출 주기 완화 처리량 실측 ([C-1], 2026-08-11)

> **★실측 해석 주의(규칙7)**: 아래 모든 수치는 **개발기 실측**이다 — 배포 박스의 성능치가
> 아니다. 개발기 사양: CPU **AMD Ryzen 9 9900X(12코어/24스레드)** · GPU **RTX 5070 Ti
> (16GB VRAM)**. 이 CPU는 저가 미니PC의 4코어급 CPU보다 훨씬 강하고, 이 GPU도 미니PC용
> 저가 GPU보다 훨씬 강하다 — **절대 대수(몇 대까지 감당하는지)를 그대로 배포 사양으로
> 쓰지 말 것.** 목적은 ①병목 구조 규명(카메라를 늘릴 때 GPU/CPU/메모리 중 무엇이 먼저
> 한계에 닿는지 — 이 구조 자체는 하드웨어와 무관하게 유효) ②CPU 모드 근사치 확보 둘뿐이다.
> 후보 기종 구매 후 `benchmarks/capacity_ramp.py`로 동일 절차 재실측이 다음 단계다.

## 1. 검출 주기 — 이미 카메라별로 설정 가능(코드 변경 없음)

카메라당 검출 주기는 `vigent-core/worker.py`의 `Worker._loop`/`_setup_run`에서
`interval = 1.0 / fps`로 결정된다(`worker.py:717`). 이 `fps`는 카메라별 값으로,
**이미 `POST /cameras {id, source, fps, ...}`로 설정 가능**하고 `data/cameras.json`에
카메라별로 영속화된다(`camera_registry.py:66` `upsert()`). tuning.yaml에는 없지만,
애초에 "카메라별" 값이라 전역 설정 파일보다 카메라 레지스트리가 자연스러운 위치다 —
**새로 설정화할 필요가 없어 코드 변경하지 않았다**(기본값 현행 유지, 규칙6 저하 없음).

전역으로 존재하는 관련 값은 `config/tuning.yaml`의 `worker.fullset_fps`(기본 2) — 이벤트
발생 대상인 "풀세트"(person+ppe+fire) 검출 주기의 **하한 캡**이다:
`_full_interval = max(interval, 1/fullset_fps)`(worker.py:756) — 카메라 fps가
fullset_fps보다 느리면 카메라 자신의 느린 주기를 그대로 따르고(원하는 대로 저빈도 가능),
fullset_fps보다 **빠르게** 설정해도 풀세트 검출은 전역 상한(기본 2fps)에 묶인다. 이 캡은
카메라별이 아니라 전역이라 §4(혼합 구성)의 제약 조건이 된다.

CPU 강제 모드도 이미 존재: `VIGENT_DETECT_DEVICE=cpu`(`vigent-core/device.py`) — 프로세스
시작 시 1회 결정되는 값이라 런타임 전환은 불가(서버 재기동 필요).

**결론: 1번은 코드 변경 없이 바로 2번 실측으로 진행 가능.**

## 2. 처리량 실측

재사용 스크립트: [`benchmarks/capacity_ramp.py`](../benchmarks/capacity_ramp.py) — 파일
카메라(`runs/rfdetr/multi_scene.mp4`, field_eval 9종 원본과 무관한 별도 클립)를 누적
등록해 단계별로 GPU/프로세스CPU%/시스템CPU%/RSS·검출지연(p50/p95, `/rfdetr/frame` 합성
프로브)을 측정하고 병목을 휴리스틱 판정한다. 각 단계: 워밍업 15초 + 측정 45초(5초 간격
샘플, 약 9회 프로브).

|---|---|---|---|---|---|---|---|---|
| 4  | 3.4 | 6.0 | 13.6 | 14.0 | 39.8ms | 303.8ms* | 0/9 | 미포화 |

| 24 | 3.6 | 6.0 | 57.4 | 21.4 | 41.8ms | 50.0ms  | 0/9 | 미포화 |

\* n=4의 p95(303.8ms)는 이 GPU 모드 서버 세션에서 `/rfdetr/frame` 경로가 처음 호출된
샘플(이 서버가 뜬 뒤의 첫 프로브)이 섞인 값으로, 모델 워밍업 잔여 효과로 추정(재현:
n=8부터는 40~50ms대로 안정) — 절대치로 인용하지 말 것.

**24대까지도 GPU 사용률이 3~4%대에서 정체** — 이 GPU(RTX 5070 Ti)는 1fps 저빈도
검출에서 압도적으로 여유롭다. 프로세스 CPU%는 카메라 수에 거의 선형 비례해 증가하지만
(24대에서도 1코어의 57%만 사용, 이 머신은 24스레드 보유) 24대에서도 전혀 포화되지
않았다. **요청받은 4~24대 구간 안에서는 GPU 한계 대수를 찾지 못했다** — 정확한 상한은
이 실측 범위를 넘어서며(수십~수백 대 규모로 추정되나 미검증), 이 desktop만으로 그
지점을 실측하는 것은 비현실적(실제 배포 GPU는 훨씬 약함 — 상한 탐색보다 후보 기종
실측이 더 의미 있음)이라 여기서 멈췄다.

24스레드 중 대부분이 여전히 유휴 상태.

시간 대비 실익이 낮다고 판단해 멈췄다(이 desktop은 배포 후보가 아니라서, 상한을 정확히
찾는 것보다 후보 기종 실측이 더 의미 있음, §해석 주의).

## 3. 원가 표 — 하드웨어 등급 × 감당 카메라 수 × 카메라당 원가

★박스 가격은 전부 **잠정치**(시장조사 미실시, 사용자 제시값)다. "감당 카메라 수"는
**실측 상한이 아니라 실측 하한**이다 — GPU/CPU 둘 다 테스트 범위 안에서 포화점을 찾지
못했으므로(§2), "이 대수까지는 확실히 된다"는 확인된 바닥선이지 "이게 한계"라는 뜻이
아니다. 따라서 카메라당 원가는 **이 이하로 더 내려갈 여지가 있는 상한 추정치**다(사업
결정에 안전한 방향의 오차 — 실제로는 더 저렴할 수 있지만 더 비쌀 가능성은 낮다).

| 하드웨어 등급 | 박스 가격(잠정) | 실측 상태 | 감당 카메라 수(해석) | 카메라당 원가(잠정, 상한) |
|---|---|---|---|---|
| **GPU 미니PC** | 120만원 | 개발기 GPU(RTX 5070 Ti) 실측, 24대까지 미포화 | **≥24대**(실측 하한 — 미니PC용 저가 GPU는 이 dev GPU보다 약하므로 이 수치를 그대로 믿지 말 것, 후보 기종 실측 전엔 참고치) | ≤5.0만원/대(120만÷24) |
| **CPU 전용 미니PC** | 25만원 | 개발기 CPU(Ryzen 9 9900X 12C/24T) 실측, 16대까지 미포화 → 사용자 지정 50% 할인 적용(저가 미니PC CPU가 이보다 약함) | **약 8대**(=16÷2, **추정/미검증** — 실측 아님, 규칙7) | 약 3.1만원/대(25만÷8, 추정) |
| **Jetson Orin Nano Super** | 40만원 | **미실측** — 양자화 필수 전제(TensorRT/INT8 변환 없이는 이 실측 파이프라인(rfdetr, PyTorch)이 이 기종에서 그대로 동작하지 않을 가능성 높음, 별도 이식 작업 필요) | **추정치만, 실측 전** — 감당 대수 불명 | 산정 불가(추정치 없음) |

**해석 지침(규칙7)**:
- GPU 미니PC 행의 "24대 이상"은 이 실측 desktop이 배포 후보보다 훨씬 강력하다는 걸
  알면서도 굳이 적은 숫자다 — **실제 저가 미니PC용 GPU(예: 랩탑용 RTX 3050/4050급)로는
  이 값이 그대로 성립하지 않을 가능성이 크다.** 이 행은 "구조적으로 GPU가 병목이
  아니라는 것"을 보여주는 데 의미가 있지, 실제 배포 대수 산정 근거로 쓰면 안 된다.
- CPU 미니PC 행의 "약 8대"는 실측값(16대)에 사용자 지정 50% 할인을 곱한 **추정치**다 —
  실측이 아니다. 후보 미니PC 기종 확보 후 `capacity_ramp.py`로 직접 재실측하기 전까지는
  참고치로만 쓸 것.
- Jetson 행은 아예 실측이 없다 — 이 행 전체가 "추정"이라는 표시조차 부족할 정도로
  근거가 얕다(양자화 이식 작업 자체를 아직 안 함). 사업 결정의 근거로 쓰지 말 것.

**결론**: 이번 실측에서 가장 확실하게 말할 수 있는 것은 **"카메라당 1fps로 낮추면 GPU도
CPU도 이 개발기 기준 병목이 되지 않는다"**는 구조적 사실이다. 저비용 하드웨어 경로의
전제("저빈도 다중 카메라로 카메라당 원가를 낮춘다")는 구조적으로 타당해 보이지만, **정확한
숫자는 후보 기종을 실제로 사서 재실측하기 전까지는 확정할 수 없다.**

## 4. 예외 설계 노트 — 고빈도가 필요한 규칙과 혼합 구성

### 분류 기준

VIGENT의 규칙(`themes/safety/vision.yaml` `judgment.rules` + `worker.py` 내장 규칙)을
아래 두 조건으로 "고빈도 필요"/"저빈도 충분"으로 나눈다:

1. **지속조건(hold_sec 등) 없이 단발 발생만으로 최고 심각도(critical)가 발동하는가?**
   — "그 순간 놓치면 의미가 없는" 규칙.
2. **물리적 사고 진행 속도가 초 미만 단위(기계 동작 자체가 즉각적)인가?** — 사람이
   위험 상태에 "머무는" 것이 아니라, 그 프레임 자체가 사고 발생 순간인 경우.

| 규칙 | 정의 위치 | severity | 지속조건 | 판정 |
|---|---|---|---|---|
| `guard_bypass`(프레스/전단기 방호구역 손 진입) | `vision.yaml:67` | **critical** | 없음(단발 진입 즉시) | **고빈도 필요** |
| `zone_intrusion`(일반 위험구역 침입) | `vision.yaml:65` | high | 없음(단, 사람이 구역에 최소 수 초는 머무름) | 저빈도 충분 |
| `ppe_missing`(안전모·안전조끼 미착용) | `vision.yaml:66` | medium | 없음(상태가 작업 내내 지속) | 저빈도 충분 |
| `ergonomic_risk`(근골격 위험자세, REBA) | `vision.yaml:74` | — | **hold_sec=3초** 내장 | 저빈도 충분(규칙 자체가 3초 지속을 요구) |
| `rapid_motion`(급격한 이동) | `worker.py:321` | mid | 프레임 간 비교 필요 | 중간(순간 포착엔 유리하나 severity가 낮아 필수는 아님) |
| `crowd_density`(밀집) | `worker.py:130` | mid | 상태형(인원 수는 서서히 변함) | 저빈도 충분 |
| `immobility`(장시간 무동작) | `worker.py:327` | high | "장시간" 자체가 조건 | 저빈도 충분(정의상 저빈도에 최적) |

**결론: 현재 규칙 카탈로그에서 고빈도가 반드시 필요한 것은 `guard_bypass`(프레스/전단기
방호구역) 하나뿐이다.** 나머지는 severity가 낮거나(medium/mid) 규칙 자체에 지속조건이
내장돼 있어 1~2fps로도 판정 품질이 떨어지지 않는다(안전기능 자체는 어차피 인증 하드웨어
1차 책임 — CLAUDE.md "안전·법규 경계" 참고, VIGENT는 보조·감시 계층).

### 혼합 구성 — "고빈도 카메라 1~2대 + 저빈도 다수"

카메라별 `fps`는 이미 개별 설정 가능(§1)하지만, **풀세트(이벤트 발생 대상) 검출은
`fullset_fps`라는 전역 캡에 묶여 있다**(§1) — 즉 지금 구조로 특정 카메라 하나만
`fullset_fps` 전역값보다 빠르게 "이벤트를 발생시키는" 검출을 돌릴 수는 없다(포커스
부스트는 person-표시 전용이고 일시적이라 다름).

프레스/전단기 방호구역 카메라처럼 지속적 고빈도가 필요한 카메라가 있다면, 다음 중
하나가 필요하다(이번 실측 범위 밖 — 설계 노트로만 남긴다):

- **A안(간단)**: `fullset_fps` 전역값을 프레스 구역 요구 수준(예: 5fps)으로 올리고,
  나머지 카메라는 개별 `fps`를 낮게 설정(예: 1fps) — 카메라 자신의 `interval`이 더
  느리면 `_full_interval = max(interval, 1/fullset_fps)` 계산상 카메라 고유 주기가
  그대로 유지되므로(§1), **이미 지금 구조로 가능하다.** 단, 전역 캡을 올리면 다른
  느린 카메라들의 워커 루프 자체 오버헤드는 안 늘어나지만, 풀세트 캡이 상향되므로
  향후 fullset_fps를 참조하는 다른 로직(GPU 예산 계산 주석 등, `tuning.yaml:83-84`
  "GPU 예산 305ms/s" 등)의 전제가 바뀐다 — 실측 재확인 필요.
- **B안(정교, 미구현)**: `fullset_fps`를 카메라별로 오버라이드 가능하게 만든다
  (`cam.get("fullset_fps")` 우선, 없으면 전역값 폴백) — 코드 변경 필요, 이번 스코프
  밖이므로 구현하지 않았다. 프레스 구역이 실제로 배치되면 검토할 후보.

**권장**: 당장은 A안으로 충분하다(코드 변경 0) — `fullset_fps`를 5(또는 필요 수준)로
올리고 일반 카메라들의 개별 `fps`를 1로 낮춰 등록하면, 방호구역 카메라만 사실상 고빈도로
동작한다. 다만 이 desktop 실측(§2)은 fullset_fps=2(기본값) 조건이었다는 점은 유의할 것
— fullset_fps를 올리면 카메라당 처리량도 달라지므로, 프레스 구역이 실배치되면 그 설정
그대로 재실측 권장.

## 재현 방법

```bash
# GPU 모드(일반 기동)
python benchmarks/capacity_ramp.py --steps 4,8,16,24 --fps 1.0 \
  --url http://127.0.0.1:8010 --pid <서버PID> \
  --video runs/rfdetr/multi_scene.mp4 --tag gpu \
  --out benchmarks/results/capacity_gpu.jsonl --cleanup

# CPU 강제 모드(서버를 VIGENT_DETECT_DEVICE=cpu로 재기동한 뒤)
python benchmarks/capacity_ramp.py --steps 1,2,4,6,8 --fps 1.0 \
  --url http://127.0.0.1:8010 --pid <서버PID> \
  --video runs/rfdetr/multi_scene.mp4 --tag cpu \
  --out benchmarks/results/capacity_cpu.jsonl --cleanup

# 더 높은 대수까지 이어서 확장하고 싶으면(누적 아님 — 새 실행은 0부터 다시 등록):
python benchmarks/capacity_ramp.py --steps 10,12,16 --fps 1.0 \
  --url http://127.0.0.1:8010 --pid <서버PID> \
  --video runs/rfdetr/multi_scene.mp4 --tag cpu_ext \
  --out benchmarks/results/capacity_cpu_ext.jsonl --cleanup
```

원시 데이터: `benchmarks/results/capacity_gpu.jsonl` · `capacity_cpu.jsonl` ·
`capacity_cpu_ext.jsonl`.
