# 4채널 벤치 재측정 — GPU 포터블(torch PPE) 30분 × 3회 + 8GB 상한 모사 1회 (I-3, 2026-09-23)

> **측정 기계**: 개발기 `DESKTOP-STLQ1LM` · Ryzen 9 9900X(24스레드) · **RTX 5070 Ti 16GB** · Win11.
> ★파일럿기(RTX 5060 8GB)도 현장 노트북도 아니다. 이 문서가 답하는 것은
> **"I-1·I-2 적용 후 GPU 포터블이 같은 조건에서 얼마나 재현성 있게 도는가"** 다.
> 1회 값으로 결론 내지 않는다 — 3회 편차를 같이 적는다.

### 읽는 법

- **합격선 항목은 3회 모두, 여유 있게 통과**한다. CPU 는 30% 근처에서 sd 0.5%p — 회차 간 차이가 거의 없다.
- **추론 p95 는 회차 간 편차가 크다**(41.6 ~ 77.2ms, sd 15.6). r2 가 유독 빠르다. 원인은 **모른다**(측정 안 함).
  다만 이 편차는 age p95(0.5s 고정)·ok 비율(1.000)에는 전혀 안 비친다 — 2fps 예산(500ms) 대비 한참 작아서다.
  → **p95 한 회차 값으로 "몇 ms" 라고 말하지 말 것.** 범위로 말한다.
- **VRAM 은 두 숫자가 다르다.** nvidia-smi 총점유 ≈ 2.47GB 인데 torch allocated 는 597MB, reserved 862MB.
  차이(≈1.6GB)는 CUDA 컨텍스트·cuDNN·드라이버 몫이다. **"8GB 카드에서 2.5GB 쓴다"는 추정은 하지 않는다** —
  컨텍스트 크기는 카드·드라이버에 따라 다르다. 확실한 것은 **torch 가 쥔 양이 0.9GB 이하**라는 것뿐이다.
- 3회 모두 `age ok 1.000` — H-3 에서 현행 onnx-cpu 가 0.467 이었던 것과 같은 도구·같은 기계다.

## 3. I-2 검증 — 수정 도구 vs 별도 샘플러

| 회차 | RSS 도구(트리) | RSS 샘플러 | 차이 | 코어 도구 | 코어 샘플러 |
|---|---|---|---|---|---|
| r1 | 2,876 | 2,791 | **+3.05%** | 5.35 | 5.33 |
| r2 | 2,877 | 2,790 | **+3.12%** | 5.36 | 5.33 |
| r3 | 2,882 | 2,789 | **+3.33%** | 5.35 | 5.32 |

±5% 안이다. **그러나 그 3% 의 출처를 확인했더니 결함이었다.**

3회의 트리는 `[33816, 36612, 32352, 15112, 26728]` — **5개**. 서버 계열은 스텁+서버 2개여야 한다.
뿌리 33816 은 서버가 아니라 **`bench_4ch.py` 자신**이었다. 조상 오르기가 "부모가 python 이면 계속" 이라
python 런처(벤치 드라이버)까지 올라갔고, 그 드라이버의 **다른 자식(`pilot_load_test.py` = 측정 도구 자신)**
까지 합산됐다. **재는 도구를 같이 잰 것**이다. (같은 계열 결함 **5번째**.)

→ 오르기 규칙을 **"서버 명령줄과 맞는 부모까지만"** 으로 고쳤다(`_server_root`). 테스트
`test_python_launcher_and_its_other_children_are_excluded` 로 고정. 고친 뒤 값은 §4 의 8GB 모사 회차에서
한 번 더 대조한다(3회 재측정은 다시 돌리지 않았다 — 판정 지표에는 영향이 없고, 트리 합산 차이는 도구 자신의 40MB 수준).

## 4. 8GB 상한 모사 1회 + I-2 재대조 + H-3 우회 샘플러 제거 결정

### 4-1. 상한 회차 결과 (run 1–3 표에 합침)

방법: `VIGENT_CUDA_MEM_CAP_MB=8192` → `torch.cuda.set_per_process_memory_fraction(8192/16302.6 = 0.5025)`.
`/health.gpu_mem.cap = {applied: true, cap_mb: 8192, total_mb: 16302.6, fraction: 0.5025, error: null}` —
**6창 전부 같은 값**(걸린 채로 30분을 돌았다). 백엔드도 서버 로그로 torch 확인.

| 지표 | 합격선 | r1 | r2 | r3 | **cap8g** | 3회 편차 |
|---|---|---|---|---|---|---|
| 시스템 CPU 창평균 | ≤ 70% | 30.6 | 29.3 | 30.0 | **31.9** | 29.3~30.6 |
| 시스템 CPU 창평균 최대 | — | 35.29 | 32.21 | 33.14 | 42.03 | 32.2~35.3 |
| 검출 age p95 최악 | ≤ 1.0s | 0.5 | 0.5 | 0.5 | **0.5** | 0.5 |
| age ok 비율 최소 | ≥ 0.9 | 1.000 | 1.000 | 1.000 | **1.000** | 1.000 |
| 경보 p95 최대 | ≤ 5s | 0.18 | 0.16 | 0.25 | **0.17** | 0.16~0.25 |
| 추론 p50 (원시 420행) | — | 35.0 | 27.0 | 37.1 | 42.5 | 27.0~37.1 |
| 추론 p95 (원시) | — | 77.2 | 41.6 | 71.2 | 85.0 | 41.6~77.2 |
| 추론 p99 (원시) | — | 89.0 | 64.7 | 85.8 | 116.0 | 64.7~89.0 |
| 서버 환산코어 (트리) | ≤ 8.0 | 5.35 | 5.36 | 5.35 | **5.35** | 5.35~5.36 |
| 서버 RSS (트리) | ≤ 6GB | 2,876 | 2,877 | 2,882 | **2,826** | 2,876~2,882 |
| VRAM nvidia-smi 최대 | — | 2,492 | 2,469 | 2,469 | 2,913 | 2,469~2,492 |

| **VRAM torch reserved 최대** | — | 862.0 | 862.0 | 862.0 | **862.0** | 862.0 |
| 기동 → ready | — | 13.63 | 11.29 | 12.14 | 12.27 | 11.3~13.6 |
| 기동 → 첫 정상 추론 | — | 17.68 | 14.34 | 15.20 | 15.35 | 14.3~17.7 |

**읽는 법**: 상한을 걸어도 torch allocated 604MB / reserved 862MB 로 3회와 **같다** — 상한(8,192MB)의 1/9 수준이라
할당자가 상한에 닿을 일이 없었고, OOM·에러 0. 합격선 항목은 그대로 통과. 추론 p95/p99 가 3회 범위보다 조금 높다(85/116ms) —
1회 값이라 **편차인지 상한 효과인지 구분 못 한다**(3회 sd 15.6ms 안에 들어가는 폭이다).

★한계를 다시 적는다: 이 상한은 **torch 할당자만** 막는다. CUDA 컨텍스트·cuDNN 워크스페이스·드라이버 몫(nvidia-smi 총점유
2.9GB 중 약 2.3GB)은 못 막는다. **8GB 카드의 완전한 모사가 아니다.** 답한 것은 "torch 할당이 8GB 안에서 OOM 없이 도는가 → 그렇다"
까지다. RTX 5060 실기 값은 여전히 없다.

### 4-2. I-2 재대조 — 고친 도구 vs 별도 샘플러 (같은 30분, 같은 서버)

조상 오르기 규칙을 "서버 명령줄과 맞는 부모까지만" 으로 고친 뒤의 값이다. 트리는 **`[29024]` 한 개**(포트 점유 서버) —
§3 의 5개(드라이버·측정 도구 포함)에서 측정 도구 합산이 사라졌다.

| 항목 | 고친 도구(트리) | 별도 샘플러 | 편차 | ±5% |
|---|---|---|---|---|
| 서버 RSS 평균 | 2,826.2 MB | 2,799 MB | **+0.96%** | ✅ |
| 서버 환산코어 평균 | 5.348 | 5.32 | **+0.53%** | ✅ |

(고치기 전 3회: RSS +3.05 / +3.12 / +3.33% — 그 3%가 `bench_4ch.py`+`pilot_load_test.py` 자신이었다.)
남은 1% 는 표본 시각 차이다 — 샘플러는 15초마다, 도구는 5분 창 경계에서 읽고 RSS 는 창 안에서 2,812~2,834MB 로 흔들린다.

### 4-3. 판정과 H-3 우회 샘플러 제거 결정

- **판정: 통과** — 두 항목 모두 ±5% 이내(최대 +0.96%).
- **결정: H-3 우회 샘플러(`scripts/bench/sample_server_proc.ps1`, `bench_4ch.start_proc_sampler`) 제거.**
  근거 ① 고친 도구가 독립 측정과 1% 안에서 일치 ② 우회 샘플러는 "도구가 틀렸을 때의 임시 대체" 였고 그 결함
  (스텁 -First 1 → 5번째 같은 계열은 런처까지 합산)은 `tests/test_pilot_server_pid.py` 7건으로 고정됐다
  ③ 같은 값을 두 벌로 기록하면 어느 쪽을 믿을지 또 판단이 필요해진다. 우회 코드는 검증되는 순간 빚이 된다.
- 관련 테스트: 샘플러를 참조하는 테스트는 **없었다**(제거할 것 없음). `aggregate_4ch.py` 의 샘플러 열·대조 절 제거.
- 이전 H-3 문서([bench_4ch_2026-09-23.md](bench_4ch_2026-09-23.md))의 `_serverproc.csv` 언급은 **기록으로 남긴다** — 그 측정은 그 도구로 한 것이 사실이다.

### 4-4. 남은 이슈

- **테스트가 기계 상태에 의존했다** — 게이트 재실행 중 `test_field_eval_group` 이 C: 여유 4.0GB(<5GB 임계)로 실패.
  실제 `shutil.disk_usage` 를 읽고 있었다. 여유 100GB mock 으로 고정 + "4GB 면 경고 1건" 반대편 테스트 추가(726 tests).
- C: 여유 하락의 정체: 오늘 `%LOCALAPPDATA%\NVIDIA\DXCache` +4.0GB(ComputeCache 는 비어 있음), `%TEMP%` +1.1GB.
  승인 범위(ComputeCache·24h 이전 TEMP)만 정리 → TEMP 16,695파일/6.53GB 삭제, **DXCache 는 유지**. 정리 후 C: 26.6GB.
  ★정리 **전에** 여유가 4.0→20.0GB 로 이미 올라 있었다 — 원인 미확인(추측: 벤치 종료로 임시 파일 핸들 해제).
- 재발 방지: 사용자 환경변수 `CUDA_CACHE_PATH=D:\cuda_cache`, `CUDA_CACHE_MAXSIZE=4GB`(레지스트리 확인). 단 **DXCache 는 이 변수의 대상이 아니다** —
  DirectX 셰이더 캐시라 별도 조치가 필요하면 결정 사항. `build_portable.ps1` 은 임시 경로 전부 `D:\vigent_portable_cache`(C: 미사용).
- 추론 p95 회차 편차(41.6~85.0ms) 원인 미조사 / RTX 5060·노트북 값 없음 / 모의 카메라(RTSP 없음) / disk 지표 포터블 미측정.

## 5. 아직 모르는 것

- **RTX 5060·현장 노트북 값이 아니다.** 전부 5070 Ti 16GB 다.
- 추론 p95 의 회차 간 편차(41.6~77.2ms) 원인 — 미조사.
- 모의 카메라(파일)라 RTSP 디코드·망 지연이 없다.
- 8GB 모사는 torch 할당자 상한일 뿐이다(위).
- `disk(data/logs MB)` 지표는 저장소 기준이라 포터블 서버에서는 **미측정**.
