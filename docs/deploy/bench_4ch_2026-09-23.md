# 4채널 동시 구동 벤치 — PPE CPU vs GPU (H-3, 2026-09-23)

> **측정 기계**: 개발기 `DESKTOP-STLQ1LM` · Ryzen 9 9900X(24스레드) · **RTX 5070 Ti 16GB** · Win11.
> ★**파일럿기(RTX 5060 8GB)도 현장 노트북(i7-10750H/GTX 1650 Ti)도 아니다.**
> 합격선 판정은 노트북 기준으로 만들어진 것이라, 여기 통과가 현장 통과를 뜻하지 않는다.
> 이 벤치가 답하는 것은 **"같은 기계에서 두 경로 중 어느 쪽이 나은가"** 하나다.

---

## 1. 기동 예열 — 이미 있다. 만들지 않았다

지시는 "없으면 추가하라"였다. **확인 결과 이미 구현돼 있어 아무것도 추가하지 않았다.**

| 무엇 | 위치 | 동작 |
|---|---|---|
| 더미 프레임 예열 | [`readiness.py:124`](../../vigent-core/readiness.py#L124) | `np.zeros((720,1280,3))` 1프레임을 **활성 슬롯마다** 실제 추론 |
| 워커 기동 시점 | [`main.py:507`](../../vigent-core/main.py#L507) | ★**예열이 끝난 뒤에만** 워커를 붙인다 |
| "준비 중" 노출 | [`system.py:259`](../../vigent-core/routers/system.py#L259) | `phase=starting` + **HTTP 503** (로드밸런서·워치독이 기다리게) |
| 예열 실측 기록 | `readiness.snapshot()` | `/health.warmup = {phase, warmup_s, elapsed_s, error}` |

### 기동 → 첫 정상 추론 (실측)

| 조건 | 첫 HTTP 응답 | phase=ready | 서버 보고 `warmup_s` | **기동→첫 정상 추론** |
|---|---|---|---|---|
| torch (PPE GPU) | 9.4s | 16.8s | 13.72s | **20.3s** |
| onnx-cpu (현행) | 9.1s | 12.9s | 9.58s | **12.9s** |

슬롯별 예열 시간: torch `person 21.8s · ppe 2.6s · fire_smoke 2.3s`(첫 회) /
onnx-cpu `person 8.4s · ppe 0.7s · fire_smoke 0.4s`.
→ **기동은 onnx-cpu 가 빠르다**(GPU 커널 컴파일이 없다). 운영 중 성능과는 반대 방향이다.

## 2. 측정 조건

| 항목 | 값 |
|---|---|
| 카메라 | **4대**(모의, 사고영상 파일 루프) · 목표 2fps |
| 구동 | **35분** × 2조건 · 집계 창 5분 |
| 도구 | [`scripts/bench/bench_4ch.py`](../../scripts/bench/bench_4ch.py) → 기존 [`scripts/pilot_load_test.py`](../../scripts/pilot_load_test.py) 재사용 |
| 원시 결과 | `audit/bench4ch_<태그>_<시각>.jsonl` + **`.csv`** + `_serverproc.csv` |
| 통보 | ★**로컬 싱크만**(`http://127.0.0.1:9911/sink`). 외부 전송 0 |
| 판정 제외 | **첫 창(예열 직후)·마지막 창(철수)** — 원시 결과에는 **남긴다** |

- `onnx-cpu` : `.onnx` 가 있는 **ppe·fire_smoke 가 ONNX Runtime CPU**, person 은 torch GPU 폴백
  (= `deploy/portable/portable_overrides.yaml` 이 포터블에 적용하는 실제 설정)

## 3. 결과 (판정 6창 · 첫/마지막 창 제외)

| 지표 | 합격선 | **torch (PPE GPU)** | **onnx-cpu (현행 포터블)** |
|---|---|---|---|
| 시스템 CPU 창평균 | ≤ 70% | **42.1%** (최대 45.5) ✅ | **48.0%** (최대 54.9) ✅ |
| 검출 age p95 | ≤ 1.0s | **0.5s** ✅ | **0.8s** ✅(여유 적음) |
| age ok 비율 | ≥ 0.9 | **1.000** ✅ | **0.467** ❌ **미달** |
| 경보 큐→전송 p95 | ≤ 5s | **0.14s** ✅ | **0.13s** ✅ |
| 서버 환산코어 | ≤ 8.0 | **6.08** ✅ | **7.39** ✅(여유 적음) |
| 서버 RSS | ≤ 6GB | 3,264MB ✅ | 3,406MB ✅ |
| 검출 p95(추론) | (기준 아님) | **59.9ms** 평균 / 113.8 최대 | **797.2ms** 평균 / 825.7 최대 |
| VRAM 최대 | (16GB 카드) | 4,072MB | 4,090MB |

### 읽는 법

**onnx-cpu 는 `age ok 비율` 에서 떨어진다.** 24스레드 개발기에서조차 그렇다.
`age p95` 는 0.8s 로 한도(1.0s) 안이지만, **샘플의 절반 가까이가 0.55s 기준을 넘긴다**
(ok 비율 0.467~0.8). 즉 "가끔 늦는" 게 아니라 **상시 경계선**에 있다.

원인은 추론 시간이다 — **797ms vs 60ms, 13배**. 2fps(주기 0.5s)인데 추론이 0.8초 걸리면
주기를 지킬 수 없다.

**VRAM 은 둘 다 약 4.07GB 로 사실상 같다.** PPE 를 GPU 로 올려도 VRAM 은 안 늘었다
(±18MB). 8GB 카드에서도 여유가 있다는 뜻이다 — 단 **RTX 5060 실측이 아니다.**

## 4. 이 측정이 말하지 않는 것 (정직하게)

- **파일럿기·현장 노트북 값이 아니다.** 24스레드 데스크톱이다. 노트북(12스레드)에서는
  onnx-cpu 의 CPU 압박이 훨씬 크고, torch 경로도 GTX 1650 Ti 에서는 이 값이 안 나온다.
- **추론 p50/p99 는 미측정**이다. `pilot_load_test.py` 가 창마다 **p95 만** 집계하고 원시
  샘플을 남기지 않는다. 지시 항목이었으나 **못 쟀다고 적는다** — p95 만 위 표에 있다.
- **모의 카메라(파일)** 다. RTSP 디코드·네트워크 지연·재접속이 없다.
- 두 조건은 각각 **1회** 돌렸다. 재현 반복이 없다.
- **정확도는 비교하지 않았다.** 속도·자원만 봤다. `.onnx` ↔ `.pth` 출력 동등성은 별도 과제다.

## 5. 시험 경보가 밖으로 나가지 않았다는 근거

| 장치 | 확인 |
|---|---|
| 통보 설정 교체 | `config/notify.yaml` 을 **로컬 싱크 하나만** 있는 파일로 바꿔 실행 |
| **코드로 검사** | `bench_4ch.py` 의 `assert_no_real_channels()` — 텔레그램·SMTP·외부 웹훅이 하나라도 있으면 **시작 자체를 거부**한다(규칙 11: 절차서가 아니라 장치) |
| 수신 확인 | 로컬 싱크가 **108건** 수신. 전부 `127.0.0.1` |
| 원복 확인 | 실행 후 원본 복원, **SHA256 일치 확인**(`A34A16E7…FDD2`) 후 백업 삭제 |
| 잔류 카메라 | `pilot*` 접두만 정리하는 기존 규칙 유지. 종료 후 설정 파일에 `pilot` **0건** 확인 |
